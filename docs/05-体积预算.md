## 1. 现状构成（ADR-072 后实测）

exe = **39,909,888 字节 ≈ 38.06 MiB**（`bin\Release\LilithReader.exe`，2026-10-06 字体裁剪轮后）。

| PE 节 | 大小 | 内容 |
|---|---|---|
| `.data` | 30.42 MiB | **字体数据，占 exe 约 80%**：思源宋体 ttc 23.67 + Noto 保留文种 6.10 + urw/sil 0.91（三项合计 30.68 MiB，与节大小吻合） |
| `.text` | 3.97 MiB | MuPDF + 应用 + ImGui + FreeType 全部代码 |
| `.rdata` | 2.33 MiB | 字体表、常量、字符串 |
| `.rsrc` | 1.15 MiB | 内嵌 UI 字体子集（1.04 MiB，ADR-048）+ 图标 |
| 其它（.pdata/.reloc/头部） | ~0.2 MiB | |

字体明细（libmupdf 1.26.10 资源，经 overlay port 裁剪后编入 exe 的部分）：

| 组成 | 大小 | 说明 |
|---|---|---|
| SourceHanSerif-Regular.ttc | **23.67 MiB** | CJK 兜底主力，内含 KR/K/SC/TC 四个字形面共享轮廓 |
| Noto 保留文种 | 6.10 MiB | 152 个文件：Emoji / Symbols / Symbols2 / **Math（学术数学符号兜底）** / Music + 南亚/东南亚等小文种 |
| urw + sil | 0.91 MiB | Base14 标准字体 + Charis SIL |

## 2. 库级 vs exe 级的重要事实（ADR-072 字节级对照结论）

- **libmupdf.lib 74M → 59M（-15 MiB）**：overlay port 从编译清单剔除了两个 Droid CJK 兜底
  （8.6 MiB）+ 8 个罕用 Noto 文种（唐古特/手语/契丹小字/楔形文字/圣书体/格兰塔/乌尔都
  Nastaliq/安纳托利亚象形文字，6.9 MiB），并同步删除 `font-table.h` 对应回退表项。
- **但 exe 级实际缩减只有 -2.06 MiB**（.data 34.06 → 31.90 MiB）。字节级对照旧 exe 证明：
  **两个 Droid、唐古特、手语在旧 exe 里本来就不存在**（多偏移字节探针 + "Droid Sans Fallback"
  字符串 0 命中双重证实）——它们在链接期未入选，具体机制未深究（按用户决定止步）。
  真正被本次裁剪移出 exe 的是 6 个中等文种：契丹小字、楔形文字、乌尔都 Nastaliq、
  圣书体、格兰塔、安纳托利亚象形文字。
- **overlay port 因此仍有保留价值**：若未来端口/bin2coff 变化使大字体重新进入链接，
  overlay 会继续把它们挡在 exe 之外（防复发）。
- 运行期影响评估：删减只作用于"文档未内嵌字体时的兜底"；内嵌字体的 PDF/EPUB 完全不经过
  兜底链。被移文种中唯一可能被感知的是乌尔都语 Nastaliq 书写风格降级为 Naskh 阿拉伯体
  （保留）；其余为死语言。旧 exe 缺席 Droid 期间用户日常使用未受影响，即当前回退行为
  （(HAN, UNSET) 逐语言尝试 → 思源宋体）已被日常使用实证。

## 3. 为什么不裁思源宋体

那 23.67 MiB 的思源宋体 ttc 是运行期真会走到的 CJK 兜底字体
（`font-table.h` 的 `FONT(han, SourceHanSerif_Regular_ttc, …)`，由 `fz_new_cjk_font`
在 EPUB/HTML 及带语言标记的文档未内嵌中文字体时调用）。砍掉它，中文读者打开大量
PDF/EPUB 会看到空白或方块，与本项目目标用户直接冲突。

## 4. 剩余裁剪手段（按收益排序；落地前先出 ADR）

1. **思源宋体子集化**（≈ **-10~12 MiB**）：ttc 内含 4 个字形面共享轮廓，替换为单个 SC 面
   并按需子集（GB2312 全集 + GBK + Ext A + 假名/谚文/注音/部首，约 3 万字形 vs 全量 6.5 万），
   预计 24.8 → 12~14 MiB。需替换字体资源 + 修正 `font-table.h` 的 subfont 索引 +
   GB2312/GBK 全集覆盖率验收（数学/希腊/西里尔符号走 Noto，不受影响）。**体积上唯一的大杠杆。**
2. 再剔 Noto 保留中的死文字小块（Bhaiksuki/Bamum 等数十个 <100KB 文件，合计 ≈ -1~1.5 MiB）——
   清单长、收益小，性价比一般。
3. 字体资源压缩 + 运行期解压（"字体专用 UPX"，无杀软启发式风险）：≈ -14 MiB，但需改
   第三方端口构建并增加启动耗时，除非极限追求体积否则不推荐。
4. ~~UPX 整包压缩~~：**ADR-072 否决** —— 本应用单文档、每次打开都是冷启动，UPX 的
   全镜像解压既拖慢启动又不省运行内存，还加重杀软启发式风险。

## 5. 安装包体积

`installer\dist\LilithReader-0.6.0-setup.exe` = **24.9 MiB**（26,091,650 字节，0.6.0 打包实测，
对应裁剪前的 40 MiB exe）。

构成：lzma2/max 压缩的 exe + 7 个文件类型关联图标（每个 17 帧，合计约 280KB）
+ 卸载器与向导资源。其中图标帧集由 1 帧扩到 17 帧（ADR-051）使安装包增大约 0.8MB ——
换来的是 100~200% 缩放下图标不再被拉伸发糊，这个代价是划算的。

下次打包（1.0-rc.1）预计随 exe 缩减同步下降（lzma2 对字体数据的压缩比约 0.61，
估算安装包 ≈ 23 MiB 量级，以实测为准）。
