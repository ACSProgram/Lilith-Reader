# Phase 7 稳定性加固（2026-10-06）

> 归档：本文件记录 2026-10-06 这一轮"稳定性加固"的实施过程与决策取舍。
> **当前事实**以 [02-架构设计 §3.4](../../02-架构设计.md) 与 [ADR-077~080](../../03-决策记录.md) 为准；
> 本文件只记录"当时做了什么、为什么这么做"。

## 1. 范围

Phase 7 剩余四项：顶层异常防线、帧级异常边界、压力测试、静态分析（本轮完成前三项）。
对应迁移计划"成熟优化"主线里的"日志与崩溃报告"。

## 2. 目标（用户原话要点）

- 让错误**可追溯**：一个错误不能导致整个程序崩掉，尤其是 C++（异常逃出线程入口就是
  `std::terminate`）。
- ImGui 的 Push/Pop 机制必须有一层包装：异常发生后栈必须能收回来。
- 要有日志，用于定位可能的问题；安插位置由实现方决定；先比较自实现与 spdlog 的实际代价。
- 效率影响必须说清：正常路径不能有可感知开销。
- 完成后**不提交**，留待审核。

## 3. 关键取舍

### 3.1 日志：自实现，不引入 spdlog（ADR-077）

需要的能力只有"等级 + 时间 + 线程 + 模块 + `name=value` 字段 + 后台落盘 + 大小轮转"。
spdlog Release 静态链接是数百 KB 量级，且崩溃路径**不能**用它（堆可能已损坏）——崩溃转储
反正要单独用 Win32 原生 API 写，日志模块的引入价值进一步降低。自实现约 400 行，exe 增量
< 10 KiB。轮转：单文件 2 MiB → `.log.1`（覆盖），磁盘上恒定最多两个文件。

### 3.2 ImGui：RAII 为主，try/catch 只负责截住（ADR-078）

**RAII 保证结构一定收口，局部 catch 保证错误被转成状态，线程边界防 terminate，
进程边界负责最后的转储，日志负责追踪过程。**

尝试"catch 之后补 Pop"被否决：抛出点在哪、压了几层，catch 处无从得知。栈的收口交给
C++ 栈展开——作用域对象析构必然执行。发现并利用了 ImGui 1.93 的官方错误恢复机制
（`ConfigErrorRecovery` + `ErrorRecoveryStoreState/TryToRecoverState`）做帧级恢复，
并把 ImGui 自检出的可恢复错误接到 `lr::log`。

实现中踩到一个认知坑：**不能**用"各层栈是否为 0"当收口判据——`NewFrame()` 会自动开
隐式窗口并压默认字体，帧首的 `id/window/font` 三层天然非 0。可判定的命题只能是
"帧尾 == 帧首"（`stacks_match`）。

### 3.3 线程边界与资源所有权（ADR-079）

工作线程入口 lambda 标 `noexcept`，`run()` 最外层 try/catch 兜底；单页/tile/打开/认证/
辅助/检索各自捕获并转成文档级或页级失败状态。纹理创建先校验 `stride ≥ w×4` 再上传。
MuPDF 区域继续遵守 ADR-009 的 `fz_try/fz_always/fz_catch` 纪律——**不能**把带析构的
C++ 对象放进 `fz_try`（longjmp 会跳过析构），两边纪律不混用。

### 3.4 崩溃防线只记录、不恢复（ADR-080）

use-after-free / 数据竞争 / 栈破坏属于未定义行为，"捕获后继续运行"不可靠。SEH 处理器
只写 MiniDump 与摘要。崩溃处理器里不用 `lr::log`，只用 Win32 原生 API + 栈缓冲。

## 4. 效率影响（设计约束，非实测）

- RAII guard 是栈上小对象，可内联，正常路径无堆分配；C++ 异常的开销在**抛出时**才发生，
  而错误本来就是低频路径。
- 不复制 `shared_ptr`/`ComPtr` 进每帧路径；`PageSlot` 对外仍是非拥有的只读句柄。
- 日志只记低频事件，不进每帧/每页/每 tile 热路径；MiniDump 只在崩溃时执行。
- 明确避免的反模式：每页每帧复制智能指针、每个绘制调用写日志、对整段渲染用 `__try`。

## 6. 实施过程要点（供后人参考）

1. **测试先抓到自己的错**：`render_fault_test` 首版在"失败后再开正常文档"用例里漏了
   `r.open(good)`，于是读到的永远是上一个坏文件的 Failed 状态——诊断信息（`phase=Failed
   detail="cannot recognize archive"`）让根因一目了然。给测试加自描述诊断是值得的。
2. **`stacks_empty()` 是个坏断言**：生产代码里写好却从未被验证，第一次写测试就发现它恒为
   false，随后改为 `stacks_match(base, current)`。教训：防御性断言自己也要有测试。
3. **PowerShell 数组拼接**：`& $cl @(...) + $libdirs` 里的 `+` 会被当作参数（报
   "无法打开输入文件 +.obj"），必须整体包进 `$argv = @(...) + $libdirs` 再 splat。
4. **ImGui 断言很吵但很有用**：headless 测试首跑立刻抓到测试用例自己把 `FramePadding`
   传成了 float（应为 `ImVec2`）——这正是"ImGui 检出的错误必须浮出水面"的价值。

### 6.1 人工试用抓到的两个回归（均已修复并加回归测试）

1. **凭空多出一个关不掉的空 "Debug" 窗口**。根因：`ig::capture_stacks()` 用
   `ImGui::GetCurrentWindow()` 取"当前窗口"，而这个公开 API 会顺手把窗口标记为
   `WriteAccessed = true`。它在 NewFrame 之后、第一个 Begin 之前被调用，标的正是隐式回退
   窗口 `Debug##Default`——EndFrame 见"已写入"就不再按"未使用"隐藏它，于是每帧都渲染出
   一个 400×400 的空 "Debug" 窗口。修复：改用只读的 `ImGui::GetCurrentWindowRead()`。
   回归测试：`imgui_raii_test` 新增"帧首快照不污染回退窗口"。
2. **每次启动都误报"上次运行异常退出"**。根因：`install()` 启动时写 `running.flag`，而
   `take_last_crash()` 排在它之后——看到的是**本次进程自己**刚写的标记，命中"标记残留 =
   强杀"分支。修复：`take_last_crash()` 提前到 `install()` 之前调用（crash.h 注明调用顺序），
   并在内部加 PID 自检兜底（标记里的 pid 等于当前进程则不算残留）。

两条的共同教训：**防御性诊断代码自己也是代码**——它会有副作用，也需要被测试。
