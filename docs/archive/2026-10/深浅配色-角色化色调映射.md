# 角色化色调映射（2026-10-06，UI 优化第二轮）

承接[配色分层与菜单宽度](配色分层与菜单宽度.md)：那一轮把"哪块是照片"的判断下沉到了
MuPDF 设备层，照片问题解决；但 chrome 的着色仍是"给整块调色板乘一个暖化系数"。
本轮的人工实测把那个做法的三个毛病全暴露了出来，于是把它重写成按角色分类的色调映射。

## 1. 实测反馈与取数

人工反馈三条：深色下勾选框是一整块亮奶油色（很违和）；深色整体偏暖、成了"暖深色"；
暖色模式对比偏低、有些地方看不清。

**先取数再推理**：直接从截图采样像素，而不是靠读代码猜。

```
面板底        #24211E     ← 与代码推算一致
勾选框底      #F9E5D2     ← 只有这一项是亮的
勾选框的勾    #C49C6A     ← 强调色，正确
选中页签底    #EFD7C1     ← 其实是页签上的"文字"被采样到了，页签底 #47413C 正常
滑块槽/下拉框  #37322E     ← 与代码推算一致
```

一眼看出可疑项：勾选框底 `#F9E5D2`。顺着它查到 ImGui 的 `Checkbox()` 实现
（`third_party/imgui/imgui_widgets.cpp`）：

```cpp
ImU32 bg_col = GetColorU32(... (mixed_value || checked) ? ImGuiCol_CheckboxSelectedBg : ImGuiCol_FrameBg);
```

**选中态的底用的是 `ImGuiCol_CheckboxSelectedBg`**，而全仓库从未设置过这一项。
在 `imgui_draw.cpp` 里查到它的来源：`StyleColorsLight` 把它设成近白冷白 `(0.95,0.97,1.00)`，
`StyleColorsDark` 设成从 FrameBg 派生的蓝。我们的**浅色分支调用 `StyleColorsLight`（整套重置）**，
**深色分支只逐项覆盖在意的 35 项**（ImGui 共 62 项）—— 于是这一项带着浅色值活到了深色主题里，
再被色调映射成 `#F9E5D2`。

## 2. 三个根因

1. **跨主题残留**：只覆盖"在意的那些"颜色项 → 未覆盖项沿用上一次留下的值。
2. **"全局暖化系数"不分角色**：对每个颜色做同一个"红升蓝降"推拉，于是冷蓝强调被推成脏蓝；
   更关键的是**文字**（亮、面积小、对比强）被染成奶油色 —— 下表是从代码里算出来的
   `sat = 0.22` 时的 r−b 差：

   | 角色 | 色值 | r−b 差 |
   |---|---|---|
   | 画布底 | `#1A1815` | +5 |
   | 面板底 | `#24211E` | +6 |
   | 次要文字 | `#948474` | +32 |
   | 正文 | `#EFD7C1` | **+46** |

   所以"整屏偏暖"其实主要是文字贡献的，把表面调中性并不解决问题。
3. **局部漏改**：`ui.cpp` 自绘的 `col_text / col_dim / col_warn`、危险红、强调色完全没过暖化。

## 3. 改法：按角色分类的色调映射

新增 `src/app/tone.h`（纯函数、不依赖 ImGui / Win32，故可被单测直接断言）：

| 角色 | 判据 | 处理 | 保证 |
|---|---|---|---|
| 中性族 | 色度 < 0.15 | 旋到方案色相 + 补饱和，**保持 WCAG 相对亮度**；中间调再乘 `ink` 压深 | 层次次序逐字不变；次要文字在彩色底上仍看得清 |
| 强调族 | 有色且色相 180°~305° | 换到方案强调色的色相/饱和度，**明度沿用原色** | 常态/悬停/按下关系保留；不再有"页面暖、按钮冷" |
| 语义族 | 有色且非冷色 | 色相向方案色相**拉近 25%** | 红仍是红、橙仍是橙 |

几个容易写错的细节（都踩过）：

- **判"有色"要用色度（max−min）而不是 HSV 饱和度**：近黑正文 `(0.13,0.15,0.18)` 的 HSV 饱和度
  高达 0.28（会被误判成冷色强调），色度只有 0.05 —— 肉眼就是中性。
- **色域上限要降饱和，不能硬钳**：目标亮度可能超出某色相在色域内能达到的上限（越接近白，
  能承载的饱和度越低）。第一版直接把线性 RGB 缩放到超界就钳到 1.0，结果近白的暖白文字与
  亮面板**凭空变暗**（实测 `0.9210 → 0.8855`），"保亮度"这条保证破了。改成在饱和度上二分到
  "亮度恰好等于目标"。
- **二分方向**：对 v=1 的同色相颜色，**亮度随饱和度单调下降**，所以"亮度 ≥ y ⇒ 还能更饱和"
  时应该把 **lo** 上移。第一版把方向写反，收敛到饱和 0（纯白），单测直接报 `0.9210 → 0.9999`。

## 4. 深色的"暖"要压到很低

`sat` 从 0.22 压到 0.08 是关键一步，量化对比：

| sat | 正文 | 面板底 |
|---|---|---|
| 0.22 | `#EFD7C1`（奶油色） | `#24211E` |
| 0.13 | `#E6D9CD` | `#232120` |
| **0.08** | **`#E2DAD2`（近中性浅灰）** | **`#232120`** |
| 0.04 | `#DFDBD7` | `#222121` |

结论：深色主题的暖意**只留在强调色上**（柔沙 `#E0B37B`），中性族基本保持中性。
表面偏一点无所谓，文字偏一点就"整屏变暖"。

## 5. 自动化断言（本轮新增，全绿）

`tests/tone_test.cpp`（113 条）：

- **原色零改动**：逐通道相等（容差 0.5/255）—— 原色是用户认可的基准，顺手调一下就是回归。
- **黄金值**：每套方案 13 个角色色的最终 RGB 逐项钉死。改参数就红，逼你把这张表一起更新 ——
  这张表就是配色的定义。
- **对比度下限**：正文/次要文字/强调色/控件层次分隔各自的 WCAG 对比度。
- **结构不变量**：换色不改变中性族的明暗次序（断言的是**次序关系**而非绝对次序 ——
  深色底与浅色底的次序本来就相反，写死一套换个方案就废）；强调族不再偏冷；
  语义色仍是红/橙且可区分；中性族保亮度 = 原值 × level。

`tests/check_theme_reset.py`（3 条）：断言 `apply_theme_colors` 的两个分支持先
`StyleColorsLight` / `StyleColorsDark` 整套重置，且深色分支显式设置了
`ImGuiCol_CheckboxSelectedBg`。跨主题残留这类 bug **在代码里毫无痕迹**，只能靠这条结构性约束挡住。

`assets/make_font_subset.py`：顺带修掉扫描范围 —— 它会把 `tests/_build/` 里的构建产物
（测试日志、临时脚本）也当"界面文字"统计，制造假失败。现在跳过该目录。

## 6. 教训

1. **看到"某一项颜色不对"时，先问"这一项是谁在画、用哪个颜色项"**，而不是先怀疑自己的
   配色公式。这次的根因根本不在着色逻辑里，而在一项**从未被设置**的颜色上。
2. **"只覆盖在意的那些"是隐藏的跨状态残留源**。凡是"整套样式 + 局部覆盖"的结构，
   都要先整套重置再覆盖。
3. **配色参数要能落到数字上**：把"偏暖"翻译成 r−b 差、把"看不清"翻译成 WCAG 对比度之后，
   才知道该动的是文字而不是表面，也才能把结论写成断言。

### 附：页面墨色的暖度对齐（验证时发现并当场修掉）

验证时人工量到一处**页面**（不是界面）的暖度不一致：

```
深色纸张方案的页面 LUT（document.cpp 的 apply_scheme_lut，mode 1）
  纸面 = 白底映射 → #1F1D1B   r−b 差 4
  正文 = 黑字映射 → #D8D4CE   r−b 差 10   ← 比纸面暖 2.5 倍（实测反馈"正文偏黄"）
  逐通道斜率： R −185 / G −183 / B −179   ← 两端暖度不同的根源
```

这与第 2 节"亮、面积小、对比强的元素，一点色相就非常显眼"是**同一条规律** ——
界面层已按那条规律收了（`sat` 0.22 → 0.08），页面层的墨色端却没有。

**改法（已实施）**：把斜率对齐，`kLight = kDark + (184,184,184)` = `#D7D5D3`。
于是整个映射等价于"按亮度一个标量 + 一个**恒定**暖偏"，两端与中间调暖度一致（r−b 恒为 4）。

**防回归**：新增 `ink_black.pdf` 样本（中央一块纯黑、其余白纸）与两条断言 ——
"正文（纯黑）映射为浅暖灰"、"正文与纸面的暖度一致（差 ≤ 2）"。
只断言纸面（`r<80`）是看不出这个问题的，这正是它此前一直没被发现的原因。
