# 配色按内容分层 + 菜单宽度控制（2026-10-06，UI 优化）

> 归档：过程记录与事故复盘。**可复用的结论已改写进** [架构设计 §6/§7](../../02-架构设计.md)
> 与 [ADR-067](../../03-决策记录.md)，此处只保留"当时怎么发现、怎么排除"的过程。

## 1. 起因（人工反馈）

1. 深色（当时的"反色"）模式把页面里的照片**直接变成负片**；暖色（当时的"护眼"）模式把照片**染黄**，
   而且**界面颜色不跟着变** —— 页面暖、四周冷。
2. 弹出菜单里出现一条特别长的文案（"双页对开（书籍模式）"），把整张菜单撑宽，其余短项显得空荡。

两条的共同点：**局部处理取代了整体设计**。配色被放在"整页位图逐像素套 LUT"这一层，
那里已经不知道"哪块是照片"；菜单宽度被交给"最长的那一项"决定，没人管上限。

## 2. 实施要点

- 新增 `SplitDevice`（逐回调转发的自定义 MuPDF 设备）把页面绘制分流成"纸墨层 / 图像层"，
  `render_page` 跑两遍、写同一张 pixmap；整页扫描件走回退路径。详见 ADR-067。
- chrome 拆成「界面主题（明暗）× 纸张方案（暖化强度）」，暖化变体由 `warm_apply` 现场派生。
- 菜单文案上限 12 个 CJK 列 + `tests/check_menu_width.py` 断言（接进 `run_tests.ps1`）。
- 改名：`ColorMode` → `PageScheme`，显示名"原色 / 深色 / 暖色"；枚举数值与命令表 id 保持不动。

## 3. 事故：自定义设备的双重释放（0xC0000374）

### 症状

`doc_test` 在**第一次非原色渲染**时崩溃，退出码 `0xC0000374`（堆损坏）。
stdout 是块缓冲的，崩溃时缓冲全丢，日志里只剩 MuPDF 的 stderr 警告 —— **看不到进度，等于没有信息**。
（临时给 `main` 加 `setvbuf(stdout, nullptr, _IONBF, 0)` 才拿到"崩在哪一条断言"。）

### 定位过程（用实验代替推理）

先在 `render_page` 里挂一个临时的 `LR_SPLIT_DEBUG` 环境变量开关，一次编译、多次运行：

| 模式 | 做什么 | 结果 |
|---|---|---|
| 5 | **完全不建**分流设备，直接用 draw device | 不崩 |
| 7 | 建设备，**不 close、不 drop**（泄漏） | 不崩 |
| 9 | 建设备，只 close，**不 drop** | 不崩 |
| 8 | 建设备，close + **手工 `fz_free(dev)`** | 不崩 |
| 6 | 建设备，**不 close**，`fz_drop_device` | **崩** |
| 2 | 建设备，**不跑页面**，close + `fz_drop_device` | **崩** |
| 0 | 正常路径（跑页面 + close + `fz_drop_device`） | **崩** |

结论一步到位：**与页面内容、与转发回调全都无关**（模式 2 连页面都没跑）；
**只有 `fz_drop_device` 会崩**，而单独 `fz_free` 同一个指针完全正常。

### 根因

`fz_drop_device` 在调用 `dev->drop_device(ctx, dev)` **之后会自己回收整块设备内存**。
我按"派生设备自己 free"的直觉在 `drop_device` 里写了 `fz_free(ctx, dev)`，
于是同一块内存被释放两次 → 堆损坏。

### 修复与防线

- `split_drop` 改为**空实现**：不碰 `inner`（由调用方 close/drop）、也**不释放自己**（由 `fz_drop_device` 回收）。
- 该纪律写进 `document.cpp` 的代码注释（含症状描述），免得下次有人"顺手补一个 fz_free"。
- 顺带保留 `split_new` 里的整结构 `memset`：`container` 等字段 `fz_drop_device` 回收时会走一遍，
  显式清零比"赌分配器已清零"稳。**注意：这一步与本次崩溃无关**（加了它照样崩），
  别把它当成根因记。

## 4. 另一处自查出的问题（未流出）

第一版把"这一页画了几笔图"的计数写在**放行判断之后**，于是纸墨层（本就该拦下图像）里计数恒为 0，
图像层第二遍永远不跑，照片位置只剩深色纸面。断言 `with_image.pdf 深色：照片仍是红的` 直接把它抓住。
现改为**计数先于放行判断**：计数回答的是"页面画了几笔图"，与"本层放不放行"是两件事。

## 5. 自动化断言（本轮新增，全绿）

`doc_test`：

- `with_image.pdf` 原色：照片为纯红
- `with_image.pdf` 深色：照片仍是红的（未被配色变换）
- `with_image.pdf` 深色：纸面仍被变换为深色
- `scan_only.pdf` 深色：整页扫描件整体变深（未留白）

`check_menu_width.py`：36 条菜单文案全部 ≤ 12 列（当前最长 9 列）。

断言失败时会打印实测 rgb（如 `深色实测 rgb=(228,4,3)`），便于下次一眼看出"是被一起变换了"
还是"图像层根本没画"。

## 6. 人工验证结果（2026-10-06）

- **通过**：12-1（深色下照片不被反相）、12-2（暖色下照片与界面协调）、12-3（深色界面同族）、
  12-4（整页扫描件整体变深）、12-5（切换配色不闪白 / 不重排）、12-7（弹出菜单宽度与对齐）。
  即"照片不被变换"这条主线成立，菜单宽度也不再被单项撑开。
  （12-2 的通过口径曾是"强调色仍是可辨认的蓝"；ADR-068 起暖色的强调色改为赭石，口径随之下移。）
- **12-6（带底图的封面）通过**（2026-10-06，样本由人工提供）：整页底图 + 正文文字，
  文字被重映射、**底图保留原色**。与 12-4（整页扫描件整体变换）互为反例，说明回退判据分得开。
  原验证口径（"做什么 / 算通过"）一并留存于此：

  - **做什么**：打开一份**整页底图 + 正文文字**的封面（杂志/设计类 PDF）。
  - **算通过**：文字被重映射、**底图保留原色**（不被一起变换）。
  - **备注**：这是 12-4 回退判据的反例 —— 两者必须都成立，才说明判据分得开。
    该样本需"整页底图 + 可选中文字"，仓库内一直没有，故由人工另行提供。
- **实测发现三个新问题**（都属观感，自动化没挡住）：

  1. **深色下勾选框是一整块亮奶油色**，与周围完全割裂。从截图取色确认：面板 `#24211E`、
     勾选框底 `#F9E5D2` —— 只有这一项是亮的。根因是 `ImGuiCol_CheckboxSelectedBg`
     **从未被设置**，深色分支只覆盖了在意的 35 项（ImGui 共 62 项），这一项带着浅色主题的
     近白 `(0.95,0.97,1.00)` 活了过来。
  2. **深色整体偏暖，成了"暖深色"**。表面其实只偏一点（r−b 差 6），真正扎眼的是**文字**
     被染成 `#EFD7C1` 那样的奶油色（r−b 差 46）—— 亮、面积小、对比强，一点色相就非常显眼。
     教训：深色主题里"给全体颜色乘同一个暖化系数"必然过量。
  3. **暖色模式对比偏低、有些地方看不清**。界面侧自绘的 `col_text/col_dim/col_warn`、
     危险红、强调色**根本没走暖化**（局部漏改），三层面的明度差也被压平。

  三条都由 ADR-068 处置：色调映射改为**按角色分类**（`src/app/tone.h`），主题切换改为
  **整套重置 + 逐项覆盖**。过程与实测数据见[角色化色调映射](深浅配色-角色化色调映射.md)。
