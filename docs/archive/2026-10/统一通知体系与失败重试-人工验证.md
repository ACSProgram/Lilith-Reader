# 统一通知体系与失败重试 / 帧异常自愈（4-5 / 15-4 人工验证通过）

> 本文件收录「统一通知体系」（ADR-100）这一批的**已通过**人工验证项与实测结论：**4-5 失败重试**
> 与 **15-4 帧异常自愈** —— 它们是 [人工验证](../../04-人工验证.md) 中最后两项待执行项。
> 判据原文见当时的 04，本文件按同样顺序记录实测与判定；相应各节已从 04 移除。
> 归档文件只增不改。

## 背景：4-5 为什么长期悬着

4-5 的判据要求"**从未渲染成功**的失败页显示「渲染失败 · 点击重试」，点击后重新尝试，成功后
占位消失"。它卡住有两个独立原因，本轮才一并拆掉：

1. **触发条件找错了方向**。曾按"损坏样本"设计，但实测三条路全走不通：
   - `truncated.pdf` / `random.pdf` / `empty.pdf` 是**打开即失败**（`Corrupt`），到不了页渲染；
   - **改坏内容流**：MuPDF 对解码错误只往 stderr 打印、照样出图（用同源 PyMuPDF 批量验证过
     损坏 Flate / 截断 zlib / 非流对象 / 损坏 JPEG·JPX·CCITT / 坏字体）；
   - **A0 幅面**：ADR-073 的 tile 分块把峰值压住，只会慢、不会失败。
   真正的闸门在 **app 自己**手里：`render_one_impl` 在调用 MuPDF **之前**先算"页尺寸(pt) × 倍率"
   的输出像素，超过 `kMaxOutputPixels = 2^28 ≈ 2.68 亿` 即 `mark_failed(TooLarge)`。与 MuPDF、
   与分块渲染都无关。
2. **提示本身看不见**。页占位把「渲染失败 · 点击重试」**居中画在整页矩形**上，而能触发失败的
   页面必然**远大于视口**（输出像素 ≥ 2^28），文字必然落到视口外 —— 用户只看到一块淡红色块。
   这一条由 ADR-100 的呈现契约修正（见下）。

## 4-5 失败重试（通过）

### 样本（已做成可复现）

`tests/make_samples.py` 第 8 节生成两个静态样本，二者都在 `tests/samples/`（生成物不入库）：

| 样本 | 页尺寸 | 默认 fit-width | 走哪条路径 |
|---|---|---|---|
| `renderfail_toobig_tall.pdf` | 200 × 600000 pt | **即失败**（输出 3.98e8 ~ 4.64e9 像素） | 从未渲染成功 |
| `renderfail_toobig_square.pdf` | 20000 × 20000 pt | 正常（输出 1.56e6 像素） | 放大到约 75% 以上才失败（100% 时 4.0e8） |

### 实测与判定：**通过**（2026-10-07，用户实测）

| 判据 | 实测 |
|---|---|
| 从未渲染成功的失败页出提示 | 画布**左上角**出现「渲染失败 · 点击重试」小标（锚在页角，页面再大也在视口内）；状态栏左侧出现「第 1 页：页面尺寸超出渲染上限 · 点击该页重试」 |
| 点击重试 | 点击页面触发重试，日志再出一条 `page too large`，**不出现无限重试** |
| 缩小后恢复 | 缩放到 50% 后正常渲染（可见页面顶部蓝条 / 红条 / 文字），小标与状态栏提示一并消失 |
| 保留旧图（曾渲染成功过的页） | 方形样本放大到 100% 时画面整体变糊（网格变粗、红块边缘发毛），**不闪白、不出现小标**；状态栏出现「…，当前显示低清版本 · 点击该页重试」 |
| 改倍率重试 | 缩到 75% 后恢复清晰、提示消失 |
| **点击重试后"成功"、提示消失** | **需临时注入**（文件驱动做不到，见下），已验通过 |

### 一条固有边界：文件驱动无法演示"点击即成功"

唯一的文件驱动失败触发是 `页尺寸 × 倍率 > kMaxOutputPixels`，**失败与倍率绑定** ——
`retry_page` 用 `last_wants` 同倍率重投，必然再失败。故"点击重试后成功"只能靠**临时注入**：
Debug 构建里让页渲染**一律失败直到用户点击**（点击即解除），失败走真实终态
（`mark_failed` → `set_failed` 定格）。实测：普通小页面打开即显示小标 + 状态栏
「第 1 页：**文档解析内部错误** · 点击该页重试」（错误码取自注入，**顺带证明文案来自
`describe(slot.error)` 而非写死**）；点击后小标与状态栏提示**双双消失**、页面正常渲染。

## 15-4 帧异常自愈（通过）

- **做法**：Debug 构建下在 `draw_shell()` 的 `##shell` 窗口**内**、画布与状态栏**画完之后**
  抛异常 —— 此刻 window / clip / style 栈都已压过，RAII 回滚与帧尾栈比对才真正被走到。
  触发方式最终定为**按住 F9**（按住期间每帧抛，松开即恢复），而不是"第 N 帧抛一次"。
- **实测与判定**：**通过**（2026-10-07，用户实测）。按住 F9 期间画面**立刻冻结**（滚动 / 缩放
  无反应，窗口不卡死、不闪黑、不弹"未响应"）；松开 F9 **立刻恢复**绘制；可反复按住/松开。
  日志成对出现 `FORCED frame abort START` / `END aborted_frames=N`，帧数与按住时长匹配；
  **没有** `IMGUI STACK LEAK`（帧尾栈比对无差异）。进程始终不退出。

## 附一：临时注入的方法教训（可复用）

两处注入（4-5 / 15-4）第一版都用**环境变量 + 固定帧号**，实测**不可行**，教训有二：

1. **触发条件不能依赖"外部配置是否到位"**。第一版 4-5 用 `LR_FORCE_PAGE_FAIL=<页号>`，实测
   **一次都没触发**（日志无 `FORCED page fail`）；且"打开文档后显示的是不是第 0 页"还受阅读
   位置恢复影响。最终把条件收成"**恒生效 + 不挑页**"（打开任何文档、所有页一律失败），
   才不再依赖任何前提。
2. **触发时机要由人直接掌握，不能靠猜时序**。第一版 15-4 用 `LR_FORCE_FRAME_ABORT=900`，日志
   证明它**确实抛了**（`frame aborted: test`），但抛在**打开文档之前**的空态 —— 画面本来就不变，
   人眼无从分辨。改成"按住 F9"后，可以在"正在滚动/缩放"时冻结，一眼可见。

另两条实现要点：

3. **注入点必须覆盖所有渲染路径**。4-5 第一版写在非分块路径的渲染循环里，一旦"页尺寸超过档位
   tile 单边"就会走 `render_one_tiled` 提前 return、注入被整条绕过。移到 `render_one_impl`
   开头（`plan_render` 之后、任何分块判定与 MuPDF 调用之前）两条路径都必经。
4. **注入必须复刻被测语义，否则改变被测行为**。4-5 不能直接 `mark_failed` 了事：
   `plan_render` 对"Failed + 同倍率 + 额度未用尽"会放行（`kMaxAutoRetries = 1`），于是调度器
   每次重算 wants 都会再渲一次、再失败一次。注入必须同样**消耗自动重试额度**、用尽后才定格。

> 注入代码**已全部移除**（`src/render/render.cpp` / `src/app/ui.cpp` / `src/app/main.cpp`），
> Debug 与 Release 均重新构建（0 警告 / 0 错误），`tests/run_tests.ps1` 全绿。
> 两个失败样本作为回归夹具保留在 `tests/make_samples.py`。

## 附二：本批的呈现契约（ADR-100）

4-5 的硬伤（提示落到视口外）由 **ADR-100「统一通知体系」**修正，实测确认生效：

- **状态栏是唯一文案面**：左侧常驻告警（`NoticeId`：`SaveFailed` / `PageRenderFailed` /
  `OpenFailed`）、中间瞬时 toast、右侧格式。
- **画布只留作用域标记**：渲染失败页 = 极淡填充 + 醒目描边 + **左上角小标**（锚在页角）；
  曾渲染成功过、本次重渲失败而保留旧纹理时**不加标记**（旧图仍有内容，盖标记反而更糟），
  但**状态栏照常告知** —— 否则用户只看到画面变糊、无从解释（人工反馈后补上）。
- **全屏下只要有活动消息，底栏强制滑出**。

> 说明：落盘失败提示（原 16-1）改由同一通知模型承载（`persist_failed` → `NoticeId::SaveFailed`），
> 呈现通道与文案不变，本轮**未单独复测**；16-1 已于同日通过，见
