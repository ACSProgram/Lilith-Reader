## ADR-010

摘自 ADR-010「vcpkg 依赖落地：libmupdf 静态端口 + 安装根目录移出含空格路径」的原始背景：

- **背景**：
  1. 项目路径 `F:\programs\Lilith Reader` **含空格**；vcpkg 的 meson 端口（harfbuzz）生成
     链接命令行时未给 `/libpath:` 加引号，路径从空格处被截断成两个参数 → `LNK1181`。
  2. vcpkg 的 MSBuild 集成把 triplet 拼了两次：传给 vcpkg 的 `--x-install-root` 已含
     triplet（`…\vcpkg_installed\x64-windows-static\`），vcpkg 内部（`scripts/ports.cmake`）
     又拼一次 `CURRENT_INSTALLED_DIR = ${_VCPKG_INSTALLED_DIR}/${TARGET_TRIPLET}`；
     而 MSBuild 侧 `_ZVcpkgInstalledDir` 的默认值里已经带了 triplet，导致实际写入
     `…\x64-windows-static\x64-windows-static\`，而 MSBuild 读 include/lib 也走
     `_ZVcpkgCurrentInstalledDir = VcpkgInstalledDir + triplet`，两侧错位。

## ADR-011

摘自 ADR-011「gumbo 覆盖端口：修正上游归档哈希」的原始背景：

- **背景**：构建时 `gumbo` 端口报 `download … had an unexpected hash`。实测
  codeberg 的 `https://codeberg.org/gumbo-parser/gumbo-parser/archive/0.13.2.tar.gz`
  与 `refs/tags/0.13.2.tar.gz` 两个 URL 返回同一份、`gzip -t` 通过的归档，
  SHA512 = `9f5996…`，而 vcpkg 内置端口钉的是 `1513e8…`。
  即 Forgejo 的 tag 归档**不是字节稳定的**（tag 重指或服务端重新打包都会改变字节），
  vcpkg 里钉的哈希已过期——非网络问题（手工完整下载可复现同一哈希）。

## ADR-015

摘自 ADR-015「用 MuPDF 自己的识别结果做实测，而不是自己写 magic 表」的调研方式、实测值表与识别机制：

- **调研方式**：项目纪律不允许"开发中运行软件做测试"，但**允许自动化测试**。因此写了
  一次性探针放在 `build/mupdf-probe/`（该目录被 gitignore，不进仓库）：① `make_samples.py`
  用 Python 合成 20 余个样本（合法 PDF/EPUB/FB2/XPS/CBZ、图片与 zip 的各种改名组合、
  空文件、截断文件）；② `probe.cpp` 直接调 MuPDF 打印 `FZ_META_FORMAT`/页数/首页尺寸；
  ③ `probe2.cpp` **链接项目自己的 `lilithreader.document` 模块**，对同一批样本跑真实的
  `Document::open()`。要复现，按下面表格重建样本即可。

- **实测值（1.26.10）**（决策正文引用）：

  | 样本 | MuPDF 上报 | 页数 |
  |---|---|---|
  | 正常 PDF / EPUB / FB2 / XPS | `PDF 1.4` / `EPUB` / `FictionBook2` / `XPS` | 正确 |
  | 正常 CBZ（zip 图集） | `zip`（归档格式名，不是 "cbz"） | 图片条目数 |
  | PNG 改名 `.pdf` / `.epub` / `.cbz` | `Image` | 1 |
  | EPUB 改名 `.pdf` / `.xps` | `EPUB` | 正确 |
  | FB2 改名 `.epub` | `FictionBook2` | 正确 |
  | **zip 图集改名 `.epub` / `.pdf` / `.fb2`** | **`zip`** | **图片条目数（假的）** |
  | zip 改名 `.cbz`（内含 PDF 或 txt） | `zip` | **0** |
  | 纯文本改名 `.pdf` / 空文件 / 截断 PDF | 打开失败 | — |

- **识别机制（为什么会出现上面这些"能打开"）**：MuPDF 给每个处理器同时算内容分与
  扩展名分：`recognize_content` 的内容分可达 25~200，而扩展名命中只给 **1** 分（弱信任），
  两者都命中才是 `100+内容分`。于是"内容分 25 的 CBZ"会压过"扩展名分 1 的 EPUB"，
  zip 图集就这样以漫画身份被打开。详见 `source/fitz/document.c` 的
  `do_recognize_document_stream_and_dir_content`。

## ADR-041

摘自 ADR-041「加密文档"解锁后整页空白"：认证成功后不得再问 `fz_needs_password()`」的原始背景排查证据：

- **背景**：人工验证 `tests/samples/enc_aes256_user.pdf`（口令 `lilith`）时，解锁后页面全白。
  排查（`doc_test` 新增加密样本渲染断言 + `mupdf_probe` 增强为"解锁并渲染"）得到决定性证据：
  - 样本本身有内容（纯 MuPDF 渲染出 769 个深色像素）；
  - 仅**在认证成功之后**多调一次 `fz_needs_password()`，同一份纯 MuPDF 复现出的深色像素就变成 0
    （`dark` 769→0），即内容流被静默解出乱码、渲染成空白；去掉该调用即恢复。

## ADR-043

摘自 ADR-043「反色模式：柔化暗色映射 + **整窗深色**」的第二条勘误原文（结论已保留在台账）：

- **勘误（2026-10-06，UI 优化第二轮）**：第 1 条的**亮端端点**由 `#D8D4CE` 改为 `#D7D5D3`。
  原亮端的 r−b 差是 10，而暗端（纸面）`#1F1D1B` 只有 4 —— 正文（黑字）比纸面（白底）
  暖 2.5 倍，深色下正文发黄（人工实测反馈，实测值 `(216,212,206)`）。
  根因是逐通道斜率写成了三个不同的值（R −185 / G −183 / B −179）；
  改为 `kLight = kDark + 184` 后三者等斜率，整个映射等价于
  "按亮度一个标量 + 一个**恒定**暖偏"，两端与中间调暖度一致（r−b 恒为 4）。
  `doc_test` 补 `ink_black.pdf` 样本与两条断言钉住这一点。

## ADR-049

摘自 ADR-049「三段外壳改为显式布局：状态栏被子窗口间距挤出窗口底部」的原始背景根因定位：

- **背景**：人工验证反馈"下方的字太靠近边缘，不舒服"。截图逐像素量取后定位到真实原因：
  状态栏文字的墨迹底边**正好落在窗口最后一行**（y=1078/1079），下缘已被裁掉 —— 不是配色或
  内边距审美问题，而是**布局溢出**。根因：顶栏/画布/状态栏是 `##shell` 内的三个**同级子窗口**，
  `ImGui::EndChild()` 会 `ItemSize()` 为每个子窗口记一个 item，于是相邻子窗口之间被插入一份
  `ItemSpacing.y`（实测 ≈8.8px，与界面缩放同比例）。三段高度之和因此比客户区多出一个间距，
  状态栏被推出窗口底部。

## ADR-063

摘自 ADR-063「阅读数据可管理：清单窗口 + 通用确认弹窗」的勘误原文（结论已保留在台账）：

- **勘误（2026-10-06 同日）**：管理界面最初做成**独立浮动窗口**，由「设置 → 阅读 → 管理…」打开。
  实测发现它在界面上**根本看不到**：该窗口先于设置窗口绘制，而设置窗口（600×700、居中）正好
  把它整块盖住，ImGui 的 z 序又把持有焦点的设置窗口留在最前 —— 表现为"点了没反应"。
  改为**设置窗口的第 5 个分栏**（界面 / 阅读 / 性能 / 按键 / 阅读数据），「阅读」分栏的
  「管理…」按钮改为切到该分栏（`g_settings_open_tab = 4`），原独立窗口与 `g_show_reading_data`
  一并删除。**教训**：一个界面"打开"另一个界面时，后者要么是前者的一部分，要么必须显式置顶；
  另开浮动窗口而不处理 z 序，等于没做。

## ADR-064

摘自 ADR-064「弹窗关闭路径的致命缺陷：透明度归零使 Begin 返回 false、模态永久残留」的原始定位方法、
探针输出与根因分析：

- **定位方法**：不启动主程序，写了一个 **headless ImGui 探针**（把 `draw_confirm_popup` 与
  `popup_anim_apply` 原样搬进一个无后端的小程序，`NewFrame` 循环 60 帧逐帧打印
  `anim.value / Begin 是否返回 true / IsPopupOpen`）。结果一目了然：

  ```
  frame 39 | g_open=0 | value 0.000244 | Begin true | IsPopupOpen 1
  frame 40 | g_open=0 | value 0.000000 | Begin FALSE| IsPopupOpen 1   ← 从此永久
  ```
- **根因**（`third_party/imgui/imgui.cpp` 的 `Begin()`）：
  1. `if (style.Alpha <= 0.0f) window->HiddenFramesCanSkipItems = 1;`
     —— **`style.Alpha` 恰好为 0 时，窗口被判为 Hidden**；
  2. 由 Hidden 推出的 `skip_items` 在 `AutoFitFrames > 0` 时被豁免；而
     `AlwaysAutoResize` 窗口在稳态下 `AutoFitFrames == 0`，**不走豁免**；
  3. `Begin()` 结尾 `return !window->SkipItems;` → 返回 **false**；
  4. `BeginPopupModal` 见 `!is_open` 便 `EndPopup()` 后返回 false —— 而 `EndPopup()` 只弹
     `BeginPopupStack`，**不清 `OpenPopupStack`**；`ClosePopupToLevel` 只在 `is_open` 为真时调用。
  5. 于是"动画收敛后再 `CloseCurrentPopup()`"这一行（写在 `if (BeginPopupModal(...))` 为真的
     分支里，ADR-059/061 的既定手法）**永远执行不到**：弹窗已经看不见，却作为**模态永久留在栈里**，
     挡住整个窗口的全部输入 —— 表现为"卡死"。
  ADR-061 的"始终套用动画样式"正是把收敛帧的 `style.Alpha` 推成 0 的那一步。

## ADR-065

摘自 ADR-065「阅读数据：一条记录 = 若干位置（列表）；管理分栏改卡片式」的原始背景与查明过程：

- **背景**：第二轮人工实测反馈（原文）："你这个排版不对啊，太丑了，而且也表达不出来某个文件
  下面有若干路径的视觉感受，按钮也很丑，而且其他内容甚至直接未知"，并附图。截图里 10 条记录
  有 8 条标题是"（未知文档）"、行尾清一色的灰方块 `×`。
- **查明**（三条各自独立，只有第 1 条是数据缺陷，其余是表达与观感）：
  1. **"未知文档"不是排版问题**：直接解析 `bin/Release/reader_state.bin` 确认，那 8 条的
     `key == path_key` 且 `page_count == 0` —— 正是 **v1 记录迁移后的形态**。v1 的键是
     "路径 + 大小 + 修改时间"的哈希，**路径本身从来没存过**，所以它们永远还原不出文档名。
  2. **一条记录只留最后一个路径**（ADR-062 的 `last_path` 是单值）：同一份内容复制出第二份后，
     新路径把旧路径顶掉，"一份数据、若干路径"这个事实在数据里就不存在，界面自然表达不出来。
  3. 行尾删除用的是 ImGui **默认按钮** —— 浅色主题下就是一块灰方块。

## ADR-066

摘自 ADR-066「输入与观感三处收敛」的原始背景与查明过程：

- **背景**：第三轮体感反馈三条（原文）：①「按键设置界面少了一些操作的介绍，比如按住 ctrl
  然后滚轮可以缩放，这种功能也可以自定义，比如改成按住 alt 之类的，哪怕不适合自定义按键的
  功能，也要在界面列出，不然用户不一定知道」；②「渲染的时候我感觉好像没有页面预加载，
  我按照正常速度浏览，每次到换页的时候都有轻微闪烁，说明是我看到页面的一瞬间才开始加载的」
  ；③「跳转窗口出现和右键菜单出现的时候，上方栏也会跟着出现，可以去掉吗」。
- **查明**：
  1. **不是没有预加载**：预加载自 Phase 4 起就在（可见行 ±1 行、**方向感知**，ADR-032），
     每次翻页时下一页的纹理**早已备好**；代价也只有"多驻留约一个视口的纹理"（几页到十几页，
     远在 512MiB 字节预算内），不存在"代价很大"的问题。
  2. 换页闪烁的真实来源是**页面淡入的触发条件**：原实现是"本页第一次被画到就从 alpha=0 渐显
     0.18s"，而**边框与投影是全不透明度先画**的 —— 于是翻页时先出现一个空白的页框，
     内容才慢慢浮出来，观感正是"看到页面的一瞬间才开始加载"。
  3. 顶栏被唤醒的来源是 `top_bar_should_show()` 里的两项：`g_open_jump / g_open_password`
     与 `IsPopupOpen(AnyPopup)` —— 后者把**画布右键菜单**也算作"菜单"，于是一右键就把顶栏
     滑出来。
  4. `Ctrl+滚轮` 的修饰键是**写死的 `io.KeyCtrl`**，不在命令表里，既不能改也列不出来。

## ADR-068

摘自 ADR-068「色调映射按角色分类；主题切换必须整套重置 ImGui 样式」的原始背景与根因分析：

- **背景**：ADR-067 落地后人工实测，三条反馈：
  1. **深色下勾选框是一整块亮奶油色**，与周围完全割裂；
  2. **深色整体偏暖，"变成暖深色了"**，希望再中性一点；
  3. **暖色模式对比偏低**，有些地方看不清；顺带"颜色可以再丰富一点，但简洁为主"。
- **根因**（三条各自独立，都不是"参数没调好"）：
  1. **跨主题残留**。`apply_theme_colors()` 的浅色分支调 `StyleColorsLight`（整套重置），
     深色分支却只**逐项覆盖我们在意的 35 项** —— 而 ImGui 有 62 个 `ImGuiCol_*`。
     未覆盖的项沿用上一次留在 style 里的值：`ImGuiCol_CheckboxSelectedBg`（勾选框**选中态**的底，
     浅色是近白 `(0.95,0.97,1.00)`）就这样带着浅色值活到了深色主题里，再被色调映射成 `#F9E5D2`。
     实测从截图取色确认：面板 `#24211E`、勾选框底 `#F9E5D2` —— 只有这一项是亮的。
  2. **"全局暖化系数"只改色相、不分角色**。它对每个颜色都做同一个"红升蓝降"的推拉，于是：
     - 冷蓝强调（勾/滑块/选中下划线）被推成**脏蓝**，而不是变成该方案该有的强调色；
     - **文字**（亮、面积小、对比强）被染成 `#EFD7C1` 那样的奶油色（r−b 差 46），
       而表面只差 6 —— 视觉上"整屏偏暖"其实主要是文字贡献的。
  3. **局部漏改**。`ui.cpp` 里自绘的 `col_text()` / `col_dim()` / `col_warn()`、危险红、强调色
     **完全没过暖化**，深色/暖色下这几处仍是冷灰/冷蓝；暖色的三层面（画布/顶栏/面板）暖化后
     明度差也被压平，整屏一片黄。

## ADR-070

摘自 ADR-070「Phase 8 实测反馈修复轮」的原始背景逐条定位、本轮证据与勘误细节：

- **背景**：ADR-069 落地后第一轮实测反馈六条，其中两条是缺陷、两条是手感、两条已确认正常
  （复制文本/图片/链接、链接跳转均可用）。逐条定位到四个**接线处**的原因：

  1. **光标移出文字后不复原**（"整页都是 I 型"，无文字文档反而正常）。
     原因：`char_index_at` 选行时"y 落在行框内优先，否则取行中心最近的一行"，且行内选字符
     "否则取 x 距离最近的一个" —— **两者都没有距离上限**。于是一页只要有文字，页面上任何
     一点都能返回一个字符下标，悬停处处命中 → 光标一直是 I 型。
  2. **`Ctrl+F` 只唤出侧栏、不切到「搜索」分栏**。
     原因：ImGui 的 `TabBar` 有自己的选中态；只写 `g_sidebar_tab` 不会切换分栏，
     必须给该分栏传 `ImGuiTabItemFlags_SetSelected`。
  3. **侧栏顶部的分栏标题栏"点不准、容易唤出菜单栏"**。
     原因：标题栏落在顶栏的**自动唤出带**（距窗口顶端 `kTopBarH + 4 = 44px`）内；鼠标一进
     这个带顶栏就滑出，而顶栏滑出会把整条侧栏（连同标题栏）**推下去 40px** —— 正要点的
     分栏跳走，落点变成刚滑出的顶栏。
  4. **搜索"搜不到东西"**。
     端到端核查（见下"证据"）：`document::search_page`、`render` 的增量检索通道、
     PDF/EPUB/FB2 三种格式**都正常**。剩下的可能是**触发路径**：中文输入法下第一次回车是
     "上屏"，未必送到输入框；而当时唯一的触发方式就是回车。加上 3 的"点不准"，用户在
     输入框里打字/按回车都可能没有真正生效，于是表现为"搜索无效"。

- **证据（本轮）**：
  - 编译：Release **0 警告 0 错误**。
  - `tests/run_tests.ps1` **全部通过**：`doc_test` 71 通过 / 0 失败 / 1 跳过（XPS 样本首页只有
    一个三角形，无文本层，属预期）、`render_search_test` 10 通过 / 0 失败，其余（canvas 126 /
    page_cache 32 / reader_state 110 / tone 113 / page_map 26 / 资源类）不变。

## ADR-076

摘自 ADR-076「持续集成：GitHub Actions 跑构建与回归」的两条勘误原文：

- **勘误（2026-10-06）**：首次真实运行即失败（C1083：`mupdf/fitz.h`、`ft2build.h`）。根因是决策 1
  漏了一个隐式前提——vcxproj 依赖**经典 vcpkg MSBuild 集成**注入 include/lib 路径，而该集成在本机
  来自开发机跑过 `vcpkg integrate install` 留下的 `%LOCALAPPDATA%\vcpkg\vcpkg.user.props`（机器级
  状态，不在仓库里）；VS 18 的 C++ targets 已不再自动导入 bundled vcpkg 的经典集成。runner 上没有
  这个文件，工作流传的 `/p:VcpkgEnableClassic`、`/p:VcpkgInstalledDir` 没有任何 targets 消费，等于
  死参数。修复：工作流新增「Enable user-wide vcpkg MSBuild integration」步骤，在定位 vcpkg 后执行
  `vcpkg integrate install`。教训：**本地能编过的前提里凡属机器级状态的，CI 都必须显式重建。**
- **勘误二（2026-10-06）**：构建通过后测试步骤再挂——`make_samples.py` 打印中文日志抛
  `UnicodeEncodeError`。同一教训的第二个实例：Python 子进程 stdout 为管道时用**系统 ANSI 代码页**
  编码（开发机 zh-CN=GBK 恰好能编中文，runner=cp1252 编不了），`[Console]::OutputEncoding`
  管不到它。修复：`run_tests.ps1` 顶部设 `$env:PYTHONUTF8 = "1"`，由回归唯一入口统一约束所有
  Python 子进程的编码，本地与 CI 同源；脚本内所有文本 IO 本就显式 `encoding="utf-8"`，不受
  默认编码变化影响。
