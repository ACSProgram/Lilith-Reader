# 阅读数据：内容指纹身份、管理入口与位置列表（2026-10-06）

> 归档：本文件记录 2026-10-06 这一轮"阅读数据"的设计过程、**三轮人工实测反馈**及其根因、
> 以及验证结论。**当前事实**以 [02-架构设计](../../02-架构设计.md) §5/§6/§7 与
> [ADR-062~065](../../03-决策记录.md) 为准；本文件只记录"当时发生了什么"。

## 1. 起因

用户提问：阅读数据是不是基于文件路径的？文件移动了会怎样？并提出方案 —— 打开后在后台算哈希，
同时存哈希与路径，识别到新路径但哈希相同时询问用户是否同意共享阅读数据。

现状核实（`src/state/reader_state.cpp`）：

- `document_key` = FNV-1a64(路径的 UTF-16 码元 ‖ 文件大小 ‖ 最后修改时间)；
- 记录表是 `vector<pair<uint64_t, DocRecord>>`，**记录里连路径都不存**，只有这个 64 位键；
- ADR-034 已把"文档改名/移动后阅读位置丢失"明确记为**可接受的代价**。

核实中还发现一个比记录里更宽的缺陷：**mtime 参与哈希**。所以不只是移动/重命名——
重新下载、解压、备份还原、git checkout、复制到新位置，只要 mtime 变了，**即使路径一字未改**
也会丢进度，而且用户完全不知道为什么丢。

## 2. 四轮落地

| 轮次 | 内容 | ADR |
|---|---|---|
| 一 | **身份改内容指纹**：稀疏采样（头 128KB + 中 64KB + 尾 128KB，≤320KB，与文件大小无关）叠上文件大小，FNV-1a 64；由 render 的工作线程在打开前算好随 `DocState` 发布；路径键降为迁移/兜底；**智能匹配三态**（关/询问/自动） | ADR-062 |
| 二 | **管理入口**：设置里的阅读数据分栏（单条删除 / 全部清空）+ 一处实现多处复用的**通用确认弹窗** | ADR-063 |
| 三 | 首次实测：**关闭确认弹窗后整窗卡死** + 弹窗无版式 → headless 探针定位根因并修复 | ADR-064 |

## 3. 三轮人工反馈与根因

### 3.1 第一轮：「选完之后直接页面卡死，无法进行任何操作」

**根因不在"选择"，在弹窗永远关不掉**。用一个 **headless ImGui 探针**（把 `draw_confirm_popup`
与 `popup_anim_apply` 原样搬进一个无后端的小程序，`NewFrame` 循环 60 帧逐帧打印状态）一次复现：

```
frame 39 | value 0.000244 | Begin true  | IsPopupOpen 1
frame 40 | value 0.000000 | Begin FALSE | IsPopupOpen 1   ← 从此永久
```

链条：动画收敛把 `style.Alpha` 推成 0 → ImGui 的 `Begin()` 里 `if (style.Alpha <= 0.0f)
window->HiddenFramesCanSkipItems = 1;` 把窗口判为 Hidden（`AlwaysAutoResize` 窗口稳态下不走
`AutoFitFrames` 豁免）→ `Begin()` 末尾 `return !window->SkipItems` 返回 **false** →
`BeginPopupModal` 返回 false → 写在 `if (BeginPopupModal(...))` 体内的
`if (!alive) CloseCurrentPopup()` **永远执行不到**；而 `EndPopup()` 只弹 `BeginPopupStack`，
**不清 `OpenPopupStack`**。结果是：**弹窗已经看不见，却作为模态永久留在栈里，挡住整个窗口的
全部输入**。详见 ADR-064（含复现配方）。

修法：`popup_anim_apply` 给套用的透明度留下限 `kPopupMinAlpha = 1/255` —— 肉眼不可见，但收敛帧
仍是"真实帧"，关闭逻辑照常执行。跳页框、密码框共用同一条关闭路径，一并修好。同时把确认弹窗
改为**自绘版式**（原先直接暴露 ImGui 标题栏并显示内部名"确认"，长路径还把窗口撑变形）。

### 3.2 第二轮：「排版不对 / 表达不出一个文件下有多条路径 / 按钮也很丑 / 其他内容甚至直接未知」

四条里只有一条是数据缺陷，其余是表达与观感。**直接解析 `bin/Release/reader_state.bin` 定案**：

```
0 key=ff3b4d71093b731f pathkey=2632a24f44c18b88 pc 361 page 56  path= C:\...\VISIONS 2025 ... - 副本.pdf
1 key=36360fa197527bc4 pathkey=36360fa197527bc4 pc   0 page  2  path=
...（共 8 条 pc=0 且 path 为空）
```

`key == path_key` 且 `page_count == 0` 正是 **v1 记录迁移后的形态** —— v1 的键是
「路径+大小+修改时间」的哈希，**路径本身从来没存过**，所以它们永远还原不出文档名。
这是**数据**问题（无从恢复），不是排版问题。

另外三条：

- 一条记录只留**最后一个**路径（ADR-062 的 `last_path` 是单值），复制出来的第二份会把第一份
  顶掉 —— "一份数据、若干路径"在数据里根本不存在，界面自然表达不出来；
- 行尾删除用的是 ImGui **默认按钮**，浅色主题下就是一块灰方块；
- 弹窗的明细行与列表的长路径都靠折行处理，长路径的相同前缀堆在一起像糊成一团。

- **版式与观感无自动化覆盖**（app 层），故 10-1 / 10-5 只能人工执行。

## 6. 遗留与已知限制

- **10-4 未执行**（修改时间变了也不丢）。理论路径：内容指纹不含 mtime，mtime 变化后指纹不变 →
  内容指纹层命中；`locations` 存的是**纯路径字符串**（不含 size/mtime），故 `relocated` 为假、
  不再询问。**注意**：「智能匹配 = 关」时只走路径键层，而路径键含 mtime，会被判为不命中。
- **升级前就已经移动过的 v1 记录找不回来**（一次性迁移限制）：v1 里既没有路径也没有指纹可比对。
  未移动过的旧记录在第一次打开时经路径键命中并完成迁移。界面已为这类记录单独设区
  （"位置未知的旧记录 · N 条"）并给出解释与清理入口。
- 「另起一份」拆开后的两条记录**都不再认内容指纹**（只能按路径认），从此各自移动位置会丢进度 ——
  这正是"用户说它们不是同一本书"的应有代价。
- 内容被改动（哪怕只改一字节）的文档视为新文档、进度不继承 —— 刻意如此（ADR-062）。

## 7. 状态文件格式演进

| 版本 | magic | 变化 |
|---|---|---|
| v1 | `LRS1` | 每文档：键（路径+大小+mtime 的哈希）+ 阅读状态 + 书签 |
| v2 | `LRS2` | 增 `path_key` / `page_count` / `last_path`（单条，UTF-8） |
| v3 | `LRS3` | `last_path` → `locations` **位置列表**（最近在前、去重、上限 8 条） |

v1/v2 均可解码并自动迁移：v2 的单路径填进 `locations[0]`，v1 的键填进 `path_key`、位置留空。
写入仍是"临时文件 + `MoveFileExW` 原子替换"。
