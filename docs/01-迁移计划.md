# Lilith Reader 迁移计划

> 来源：`F:\programs\Lilith\Lilith\Modules\Document\MuPDF\`（MuPDFCore + MuPDFViewer）
> 制定日期：2026-10-05
> 原则：**分阶段可验证、每阶段可运行、稳定性优先于功能堆叠。**

**纪律（2026-10-05 起）：开发过程中不实际运行本软件做测试（编译与自动化测试除外）。需要人工运行确认的验收项，统一记录在 [人工验证](04-人工验证.md)，写明"做什么、做到什么样算通过"，由人工按文档执行。**

**提交纪律（2026-10-05 起）：每个 Phase 收尾（编译零错、测试通过、文档同步完成）必须立即 git 提交，不得带入下一阶段。**

## 0. 现状与差距分析

### 0.1 可直接继承的资产（已验证可用）

| 资产 | 位置 | 说明 |
|---|---|---|
| MuPDF 封装 | `MuPDFCore.ixx/.cpp` | `fz_context`/`fz_document` RAII 封装、`fz_try/catch` 错误处理模式、display list 能力 |
| 页面渲染管线 | `Document::renderPage` | 96dpi 基准渲染 → 位图；骨架正确，细节需改造 |
| 并发模型 | `MuPDFViewer` | ThreadPool + LRU 页缓存 + Loading 占位 + 相邻行预加载 + `viewing` 标记防止释放正在浏览的页 |
| ImGui 全套 | `Lilith/ImGui/` | 1.91.9 含 freetype、DX12/Win32 后端；换 DX11 后端即可 |
| 模块化风格 | 全项目 `.ixx` | C++20 modules 组织方式直接沿用 |

### 0.2 必须抛弃/重做的部分

| 问题 | 现状 | 处理 |
|---|---|---|
| OpenCV 中间层 | `pixmapToMat` RGBA→BGR 逐像素拷贝，再转纹理 | **删除**。MuPDF 直接生成 RGBA pixmap，`fz_pixmap_samples` 一步上传 GPU 纹理 |
| ImPlot 画布 | 用 ImPlot plot 当网格画布，坐标系绕（y 轴负方向、PlotToPixels 换算） | **删除**。自研画布（见架构文档 §2） |
| 固定 96dpi 渲染 | 放大只做纹理拉伸 → 模糊 | **重做**。按当前 zoom 渲染对应 DPI，防抖后高清换入 |
| 双 Document 绕线程限制 | `file_`/`file_render_` 两个 context 回避 fz_locks | **重做**。规范线程模型：每工作线程 `fz_clone_context`，或配置 `FZ_LOCKS` |
| 渲染失败态缺失 | 渲染任务抛异常后 `status_` 永远停在 Loading（白屏） | **补齐** `Failed` 状态 + 错误占位 + 有限重试 |
| 缓存预算按页数 | `MAX_COLUMNS * (MAX_LINES + 3)` | **改为按字节预算**（如 512MB），高 zoom 下单页可达几十 MB |
| 宿主依赖 | bass/Live2D/Qt/nvml/spdlog/Http 等 | 全部不带入 |

### Phase 2：MuPDF 文档核心移植（✅ 完成 2026-10-05，记录见 [history/phase2](history/phase2-文档核心.md)）
- [x] 移植 `Document` 类：去 OpenCV、`renderPage` 返回 RGBA8 零拷贝视图（PIMPL 隔离 fz 类型）

- [x] `fz_try/catch` 全覆盖审查：任何 fz_* 失败不得逃逸出模块边界；补齐了原版遗漏的 `fz_close_device`
- [x] 打开失败/损坏文件：结构化错误码（NotFound/NotOpen/Unsupported/NeedsPassword/Corrupt/TooLarge/Internal）
- [x] 依赖落地：vcpkg `libmupdf` 1.26.10 静态库；`VcpkgInstalledDir` 移出含空格路径；gumbo 覆盖端口
- 验收（编译）：Release 0 警告 0 错误；exe 仅依赖系统 DLL。**运行期验收待人工执行**（04-人工验证 · Phase 2）
- 实测：exe 40.4MB，其中约 34MB 是 MuPDF 内置 CJK 兜底字体（体积预算见 §4）

### Phase 3：自研画布（✅ 完成 2026-10-05，记录见 [history/phase3](history/phase3-画布.md)）
按架构文档 §2 实现，三步全部落地：
- [x] 3a 单页视口：fit-width/fixed-zoom 两模式、连续滚动、滚轮滚动、键盘翻页
- [x] 3b 缩放：Ctrl+滚轮以鼠标为中心缩放，150ms 防抖触发按新 zoom 的高清重渲染，
      期间显示低清占位（旧纹理双线性放大，不闪白）
- [x] 3c 多列网格：1~4 列，列间距/页间距统一布局函数；网格模式下按行滚动
- [x] 配套：`PageBitmap` → D3D11 纹理上传；`DocSession` 临时线程被 render 调度层取代
- **验收**：布局为**纯函数**，61 例自动化断言全通过（`tests/canvas_test.cpp`）；
  1000 页文档滚动/缩放不卡帧、缩放无闪白属人眼项，见 [04-人工验证](04-人工验证.md)。
- 决策：坐标/缩放语义（ADR-018）、纹理生命周期（ADR-019）、渲染调度层（ADR-020）、
  移除 ImPlot（ADR-021）。

### Phase 4：渲染调度与纹理管理（下一阶段）
- [ ] 页缓存 LRU 改为**字节预算**（默认 512MB，设置可调 128MB~2GB）
- [ ] 纹理延迟释放队列：删除的纹理必须先经历"帧末从 draw list 解除引用 → 下一帧释放"，杜绝悬空纹理句柄
- [ ] 渲染失败状态机：`Unloaded→Loading→Loaded/Failed`，Failed 显示错误占位 + 点击重试，最多自动重试 1 次
- [ ] 预加载策略：可视行 ±1 行；方向感知（向下滚动只预加载下方）
- **验收**：连续快速滚动 10 分钟，内存曲线平稳有界；任务管理器无 GDI/句柄泄漏。

## 3. 风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| MuPDF AGPL 协议 | 闭源商业分发受限 | 当前自用/开源无碍；若商用换 PDFium（BSD），Core 层接口按此预留抽象 |
| vcpkg 静态库构建问题（已发生并解决） | Phase 2 一度阻塞 | 两个坑：① 项目路径含空格导致 meson 端口的 `/libpath:` 被截断（LNK1181）；② MSBuild 集成把 triplet 拼两次。统一解法：`VcpkgInstalledDir` 指向无空格、不含 triplet 的独立根目录（ADR-010）。另 gumbo 上游归档哈希失效，用覆盖端口解决（ADR-011） |
| epub 排版质量不佳 | 多格式体验参差 | epub 渲染缺陷记录在案，不承诺完美；PDF 优先级永远最高 |
| 自研画布交互手感不及 ImPlot 成熟 | 体验打折 | 先复刻 ImPlot 行为基线，再做平滑动画增强 |
| 大页面（A0/长图式 PDF）内存峰值 | OOM/卡顿 | 渲染尺寸上限钳制 + 分块渲染预留（tile 接口） |
| Windows Defender 误报 exe（R6，已发生） | 用户首次运行被拦截/删除 | 短期：本机排除 + 向微软上报误报；中期：Phase 7 加版本资源/图标；根治：代码签名证书（详见 README 已知问题） |

## 4. 体积预算（Phase 2 实测更新）

原预估值严重低估了 MuPDF 的内置字体资源体积，据实修正：

| 组成 | 原预估 | Phase 2 实测（Release x64） |
|---|---|---|
| MuPDF 静态库（含内置字体资源） | 15~25 MB | **≈ 38 MB**，其中内置 CJK 兜底字体占绝对主体：`SourceHanSerif-Regular.ttc` 24.8MB + Droid 两个 8.7MB |
| ImGui + ImPlot + freetype | ~1 MB | ≈ 1 MB（`implot` Phase 3 落地自研画布后可移除） |
| 嵌入 UI 字体子集 | 1.5~2 MB | 未做（Phase 6） |
| 静态 CRT + 其余代码 | ~2 MB | ≈ 2 MB |
| **exe 合计** | 目标 < 30 MB | **40.4 MB**（`bin\Release\LilithReader.exe`） |

- `.data` ≈ 34MB、`.text` ≈ 3.8MB、`.rdata` ≈ 2.4MB；依赖表只有系统组件。
- **为什么不裁**：那 24.8MB 的思源宋体是运行期真会走到的 CJK 兜底字体
  （`font-table.h` 的 `FONT(han, SourceHanSerif_Regular_ttc, …)`，由 `fz_new_cjk_font`
  在文档未内嵌中文字体时调用）。砍掉它，中文读者打开大量 PDF/EPUB 会看到空白或方块，
  与本项目目标用户直接冲突。
- **Phase 7 的裁剪手段**（按收益排序，届时逐项评估并出 ADR）：
  1. 用 `TOFU_CJK_LANG` 走 Droid 兜底（约 -24MB，代价是汉字字形观感下降）
  2. 去掉罕用 Noto 文种（SignWriting 2.8MB、Tangut 2.0MB 等，约 -5MB）
  3. UI 字体子集化 + UPX 压缩（-数 MB）
  4. 仅保留 PDF 解析器（-5~8MB，与"多格式"目标冲突，优先级最低）
- 结论：**体积目标由 "< 30MB" 调整为 "< 45MB"**，Phase 7 再争取压到 20MB 量级。
