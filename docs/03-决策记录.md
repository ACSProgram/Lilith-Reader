## ADR-001 自研画布替代 ImPlot（2026-10-05）

- **背景**：Lilith 的 PDF 查看器用 ImPlot 当网格画布（多列并列 + 缩放查看）。
- **决策**：不引入 ImPlot 作产品画布，用纯 ImGui + ImDrawList 自研（缩放/平移/网格布局自管）。
- **理由**：缩放手感完全可控（以鼠标为中心的平滑缩放、惯性滚动）；网格、单列滚动、双页对开统一一套代码；减少一个依赖。
- **后果**：需自写约 300~500 行交互代码；ImPlot 仍下载引入，作为交互参考基准与调试可视化备用。

## ADR-002 D3D11 替代 D3D12（2026-10-05）

- **决策**：图形后端用 D3D11（FLIP_DISCARD 翻转模型）。
- **理由**：初始化与纹理管理大幅简化；单窗口阅读器性能与 D3D12 无差别；降低崩溃面（Lilith main.cpp 中 D3D12 的长 RAII 释放链即复杂度代价）。
- **后果**：放弃 D3D12 独占的特性（无需理会）。

## ADR-003 保留 MuPDF 多格式支持（2026-10-05）

- **决策**：MuPDF 静态链接，保留 PDF/epub/mobi/fb2/cbz/xps 多格式。
- **理由**：MuPDF C API 已有成熟使用经验；多格式是差异化功能。
- **风险**：epub/mobi 排版质量不完美，PDF 永远最高优先级；AGPL 协议——自用/开源无碍，闭源商用需商业授权或换 PDFium（Core 层接口预留抽象）。

## ADR-004 C++20 modules 组织（2026-10-05）

- **决策**：沿用 Lilith 的 `.ixx` modules 风格（stdcpp23，`import std` 可用）。
- **理由**：与现有代码风格一致，原模块搬运改动最小；单人 Windows 项目无兼容性顾虑。

## ADR-005 去除 OpenCV 中间层（2026-10-05）

- **决策**：渲染管线改为 MuPDF RGBA pixmap → 直接上传 GPU 纹理，删除 `pixmapToMat`。
- **理由**：原管线含一次全页 RGBA→BGR 逐像素拷贝，纯浪费；体积也大幅缩小。

## ADR-006 线程模型规范化（2026-10-05）

- **决策**：废弃"双 Document（两个 fz_context）绕线程限制"的做法，改为渲染线程 `fz_clone_context`（或 fz_locks），优先单渲染线程串行化。
- **理由**：原方案是脆弱的隐式约定，扩展即踩坑。

## ADR-007 静态链接单 exe（2026-10-05）

- **决策**：vcpkg manifest + `x64-windows-static` triplet + MSVC `/MT`，产出单文件 exe（目标 < 30MB）；UI 字体子集化嵌入 exe（约 1.5~2MB 常用汉字 + Latin，imgui_freetype 渲染），可选运行时 fallback 系统 msyh.ttc 补生僻字。
- **理由**：便携、零依赖、`exe <路径>` 直接打开。

## ADR-008 最新工具链（2026-10-05）

- **决策**：使用 VS 18 (2026) Community，PlatformToolset v145（MSVC 14.51），不使用 VS2022/v143。
- **理由**：机器已装最新版本（14.44/14.51 并存，取 14.51）；C++23 `import std` 支持更完善。

## ADR-009 MuPDF 异常模型约束：setjmp/longjmp，不是 C++ 异常（2026-10-05，Phase 2）

- **背景**：`mupdf/fitz/context.h` 中 `fz_try/fz_catch` 定义为
  `if (!fz_setjmp(*fz_push_try(ctx))) …`，即 C 的 `setjmp/longjmp`。
  MuPDF 以 C 编译（vcpkg 端口 glob `source/**/*.c`），不存在任何 C++ 异常互通。
- **决策**：在 `src/document/document.cpp` 中强制两条纪律，并在文件头写明：
  1. **`fz_try` 块内绝不构造带析构函数的 C++ 对象**（`std::string`/`std::vector`/`std::optional`…），
     跨越 `fz_try` 存活的对象同样禁止——`longjmp` 不调用析构函数，会直接泄漏。
     所有需要 C++ 对象的准备工作放在 `fz_try` 之外，块内只出现 `fz_*` 裸指针与 POD 缓冲（`char[]`）。
  2. 跨 `fz_try`/`fz_always`/`fz_catch` 使用的局部变量一律用 `fz_var()` 标记
     （MuPDF 官方要求的防寄存器优化破坏手段）。
- **附带修正**：`fz_drop_device` **不会**隐式关闭设备（device.h 明确写 "This is NOT called
  implicitly on fz_drop_device"）。Lilith 原版 `createPageDisplayList`/`renderPage` 都漏了
  `fz_close_device`，Phase 2 一并修正。错误路径上 `fz_always` 内不调用可能抛异常的
  `fz_close_device`，直接 drop（MuPDF 会给出 "dropping unclosed device" 警告，不泄漏）。
- **后果**：新增 fz 调用时必须遵守上述两条，否则是"能跑但会漏内存/偶发错值"的隐性缺陷。

## ADR-010 vcpkg 依赖落地：libmupdf 静态端口 + 安装根目录移出含空格路径（2026-10-05，Phase 2）

- **背景**：项目路径 `F:\programs\Lilith Reader` 含空格，触发 vcpkg 的 meson 端口未给
  `/libpath:` 加引号而截断（`LNK1181`）；且 vcpkg 的 MSBuild 集成与端口脚本各拼一次
  triplet，导致安装根错位。（两条缺陷的详细机制见 [归档](archive/2026-10/ADR-过程记录归档.md#adr-010)。）
- **决策**：
  - 依赖端口用 vcpkg 官方 `libmupdf`（1.26.10，Windows 下强制静态库），覆盖
    PDF/XPS/HTML(reflow → epub/mobi/fb2)/CBZ/SVG，与 `x64-windows-static` + `/MT` 完全匹配。
  - 在 vcxproj 显式设 `<VcpkgInstalledDir>F:\programs\.Environment\vcpkg-roots\LilithReader</VcpkgInstalledDir>`
    ——**不含空格、不含 triplet**。于是"传给 vcpkg 的安装根"与"MSBuild 读取的
    `根\ triplet`"两种口径同时成立，两个问题一并消除。
  - 镜像 libmupdf 端口的 **PRIVATE** 编译定义（`FZ_ENABLE_ICC=0` 等）到本项目。
    该端口没有把这些宏传播给消费方，而 `FZ_ENABLE_ICC` 会影响 `fz_context` /
    `fz_colorspace` 的结构体布局。当前代码只通过指针传递这些不透明类型、未访问任何
    受保护成员，故今天无实际暴露；镜像取值属于低成本消除隐患。
- **后果**：vcpkg 安装产物在项目之外（`F:\programs\.Environment\vcpkg-roots\LilithReader`），
  项目内不再生成 `vcpkg_installed/`（`.gitignore` 条目保留以防回退）。升级 libmupdf 端口后
  需复核其 PRIVATE 定义是否变化。

## ADR-011 gumbo 覆盖端口：修正上游归档哈希（2026-10-05，Phase 2）

- **背景**：构建时 `gumbo` 端口报 `download … had an unexpected hash`；实测为 Forgejo 的
  tag 归档**不是字节稳定的**（tag 重指或服务端重新打包都会改变字节），vcpkg 内置端口钉的
  哈希已过期——非网络问题。（实测哈希与复现过程见 [归档](archive/2026-10/ADR-过程记录归档.md#adr-011)。）
- **决策**：新增覆盖端口 `overlay-ports/gumbo/`（配 `vcpkg-configuration.json` 注册），
  改为按**提交号** `322c54c178590ba42b8b04e8c0e4840595a1f717` 拉取自包含归档（锚定
  不可变对象），并把 SHA512 换成实测值；`port-version` 递增到 1。
- **备选与放弃**：全局关掉下载校验（`--x-no-verify-downloads`）会削弱全部依赖的
  供应链校验，不可接受；降级到 Google 镜像上的 gumbo 0.10.1 属于无必要降级。
- **后果**：新增 3 个端口文件 + 1 个配置文件；上游若再次改动归档需重算哈希并递增
  port-version。若将来 vcpkg 内置端口自行修正，可删除覆盖端口。维护说明写在
  `overlay-ports/gumbo/portfile.cmake` 头部。

## ADR-012 文档核心的线程归属、零拷贝渲染结果与错误码（2026-10-05，Phase 2）

- **决策**：
  1. **线程归属**：`fz_context` 以 `nullptr` locks 创建（单线程上下文），`Document`
     实例**非线程安全**，约定"一个实例只属于一个线程"。Phase 2 起 UI 线程永不触碰
     `fz_*`，打开动作经一个专用工作线程串行执行；ADR-006 里"线程池 + `fz_clone_context`"
     的路留待确有并发渲染需求时再启用。
  2. **零拷贝**：`render_page` 返回 `PageBitmap`（RGBA8，4 字节/像素，行主序），
     直接指向 `fz_pixmap` 内部缓冲，可直接上传 `DXGI_FORMAT_R8G8B8A8_UNORM`，
     全程无像素拷贝（落实 ADR-005）。清屏用不透明白底（`fz_clear_pixmap_with_value(…, 0xFF)`）：
     目标 alpha 恒为 255，页面内容以 SRC_OVER 合成后 alpha 仍为 255，无需反预乘。
  3. **错误码**：`DocError { Ok, NotFound, NotOpen, Unsupported, NeedsPassword, Corrupt,
     TooLarge, Internal }`，分类优先用 MuPDF 的 `fz_caught()` 错误码，仅在
     `FZ_ERROR_GENERIC` 时回退到消息特征（加密 PDF 走的就是 GENERIC + "password"）。
     任何 `fz_*` 失败都以错误码出模块边界，不逃逸。
  4. **尺寸钳制**：`render_page` 接受单边像素上限（默认 8192），超限时等比下调实际
     scale，并通过 `PageBitmap::effective_scale()` 告知真实值——只缩不放，保证不 OOM。
  5. **PIMPL 隔离**：`fz_*` 类型完全不出现在模块接口，为换 PDFium 留出解耦（ADR-003）。
  6. **context 共享所有权**：MuPDF 没有 `fz_keep_context`（context 不可引用计数），
     而释放 `fz_pixmap` 必须用创建它的 context。若 `PageBitmap` 只存裸 `fz_context*`，
     一旦比 `Document` 活得久就是 use-after-free。因此 `fz_context` 由
     `shared_ptr<CtxHandle>` 持有，`Document` 与 `PageBitmap` 各持一份，
     **ctx 必定后于所有位图析构**，从结构上消除悬垂指针（而非依赖"调用方注意顺序"的约定）。
     代价：Document 关闭后若仍有位图存活，ctx（及其内部 store，上限 128MB）会延后释放。
- **已知取舍**：UI 线程为即时反馈仍会做 `GetFileAttributesW` 之类的元数据调用（微秒级、
  不读文件内容）；网络路径下可能变慢，属可接受的有界例外。Phase 3 起并入调度层的
  任务队列后再统一评估。

## ADR-013 格式闸门用扩展名白名单，而不是"全交给 MuPDF"（2026-10-05，Phase 2）

- **背景**：`fz_register_document_handlers` 实际还会注册 img（png/jpeg 嗅探）、html/xhtml、
  gz 等处理器。若一律交给 MuPDF，拖入 `.png` 会当成文档打开、`.gz` 也可能被接受，
  与 README 承诺的格式集合不符，且行为不可预测。
- **决策**：`utils` 里的扩展名清单（pdf/epub/mobi/fb2/cbz/xps）作为**策略闸门**：
  不在清单内直接判"暂不支持"，不进后台线程。清单内的文件再交给 MuPDF，
  此时 `DocError::Unsupported` 仅用于"后缀对但内容不对"的情况。
- **理由**：行为可预测、与文档承诺一致、UI 反馈无需线程往返。
- **后果**：想放开更多格式只需改 `utils.ixx` 里的一张常量表；若将来做"任意格式"开关，
  闸门处留一个入口即可。

## ADR-014 改名为受支持扩展名的图片，按内容当单页文档打开（2026-10-05，Phase 2 修订）

- **背景**：ADR-013 的后果里写"后缀对但内容不对"→ 报损坏，人工验证项 2-8 也据此要求
  "PNG/JPG 改名 .pdf 必须报损坏"。实测（Phase 2 手工验证）发现 MuPDF 会按内容嗅探，
  一张 PNG 改名 `.pdf` 会被 img 处理器接走，正常打开成 1 页文档，不报任何错。
- **决策**：**接受这一行为**，为此专门做内容签名比对（magic 白名单）不值当：
  ① 阅读器多支持一种"单页图片文档"对用户只有好处，没有正确性损失；
  ② txt 改名 `.pdf` 依然会报损坏——MuPDF 没有纯文本处理器，"能打开"不等于"什么都能开"，
     策略闸门仍然有效；
  ③ 内容签名比对会引入"用户明明有张图却打不开"的负面体验，以及一张需要长期维护的
     magic 表（PDF 变体、EPUB 的 zip、MOBI 的 PDB 头各有各的偏移）。
- **边界（要说清的三条）**：
  1. 闸门仍是**扩展名**白名单：原生 `.png` / `.jpg` / `.txt` 一律"暂不支持"，不进后台线程；
     只有"图片被改名成受支持扩展名"才会走内容嗅探这条路。
  2. 于是任何文件只要 MuPDF 认得出（图片、html 等），改名后都可能被打开——
     这是**有意**的宽松，不再视为缺陷。
  3. 不引入新的 `DocError`，`Corrupt` 只用于"MuPDF 也认不出"的情况（空文件、截断、
     纯文本、无效 zip）。
- **对既有文档的修订**：ADR-013「后果」中"后缀对但内容不对即报损坏"的表述作废；
  `docs/04-人工验证.md` 的 2-8 判据已同步改为"应能正常打开"，2-10（纯文本改名）保留
  "报损坏"作为兜底验证。
- **后续修订**：本 ADR 的「边界 3」（不引入新 `DocError`）已被 **ADR-016** 取代 ——
  归档类错配（zip 图集冒名单文档）必须拒绝。其余内容仍然有效。

## ADR-015 用 MuPDF 自己的识别结果做实测，而不是自己写 magic 表（2026-10-05，Phase 2）

- **背景**：要做"内容与扩展名是否相符"的判定，先得知道 MuPDF 到底把文件认成了什么。
  MuPDF 公开 API 里唯一能问出这件事的就是 `FZ_META_FORMAT` 元数据，但各处理器实现不一，
  必须先摸清实测值（哪些格式会上报、上报成什么字符串、查不到时怎么办）。
- **决策**：判定依据用 `fz_lookup_metadata(doc, FZ_META_FORMAT)`（MuPDF 各处理器上报的
  格式串），**不自己写内容签名表**。（调研方式、实测值表与识别机制见
  [归档](archive/2026-10/ADR-过程记录归档.md#adr-015)。）
- **理由**：① 该元数据是 MuPDF 的权威结论，比自己嗅探字节准确、且不随格式演进腐化；
  ② 处理器没实现该元数据时返回 `-1`，天然提供了"无法判定 ⇒ 不拦"的保守回退；
  ③ 顺带得到 `DocumentInfo::format`，UI 能如实显示"实际格式"，比只显示扩展名更诚实。
- **后果**：`document.ixx` 暴露 `format_matches_extension()`（纯提示用）；判定与提示共用
  同一张"格式族"映射表，位于 `document.cpp`；`utils.ixx` 的扩展名白名单仍需同步维护
  （`.mobi` 等未实测格式串的扩展名一律"不判定"）。

## ADR-016 内容优先：能认出格式就打开，只拦"归档冒充单文档"（2026-10-05，Phase 2）

- **背景**：ADR-014 的宽松与 ADR-015 的实测共同暴露了一个口子：内容能认出来就照认出的
  格式打开（图片、改名文档都无害），但**归档（zip/tar）冒充单文档**是有害的 ——
  CBZ 处理器把归档条目当页，于是 zip 图集改名 `.epub` 会显示"2 页电子书"，
  用户完全被误导；Phase 3 渲染时还会得到一堆与预期无关的图片。
- **决策**：**内容优先，只拦会骗人的**：
  1. 能识别出格式 ⇒ 打开，不管扩展名写什么；UI 在"扩展名与实际不符"时如实标注
     （`已打开 · 实际格式 EPUB（扩展名 .pdf 不符）`）。图片改名、文档互相改名都属于这类。
  2. 拒绝只有两种情形，都归入新的 `DocError::Mismatched`（中文文案
     **"这是压缩包，不是单个文档"**）：
     - 实际是 `zip`/`tar` 归档，而扩展名不是 `.cbz`；
     - 扩展名是 `.cbz`（归档类），但归档里一个可显示图片页都没有（页数 0）。
  3. 连 MuPDF 都认不出的（空文件、截断、纯文本改名 `.pdf`、坏 zip）仍是
     `DocError::Corrupt`，文案不变。
  4. 两侧任一无法判定时一律放行（不设"扩展名契约"，避免误伤）。
- **理由**：与用户口径一致 ——"能认出格式就无所谓后缀，除非有影响"。"有影响"的判据取
  "页数/内容类别会被处理器凭空编造"，即归档类；其余错配内容能如实呈现，拦下来只是添堵。
- **代价**：`DocError` 增加一个枚举值（`Mismatched`），`DocumentInfo` 增加 `format` 字段；
  UI 的 `draw_failed` 为 `Mismatched` 专门给一句中文建议
  （"若是图片集，请把扩展名改回 `.cbz`"）。C++ 侧所有 `switch (DocError)` 都必须覆盖新值
  （`to_string` / `describe` 已补；GCC/Clang 下请留意 `-Wswitch`）。
- **已知缺口**：`.mobi` 的上报格式串未实测（无法程序化构造样本），故 `.mobi` 不做任何
  判定 —— 极端情况下"zip 改名 `.mobi`"仍会以漫画打开。把关方式：真实 `.mobi` 用例
  （已归档，见 [archive/2026-10/phase2-文档核心.md](archive/2026-10/phase2-文档核心.md) 2-16h）+ 该缺口记录在此。
- **未做（留待决策）**：扩展名白名单（ADR-013）仍会拦下**原生** `.png`/`.jpg`，因此按

## ADR-018 画布坐标模型与缩放语义（2026-10-05，Phase 3）

- **背景**：自研画布需要一套可预测、可单测的坐标/缩放约定。架构文档 §2.1 只列了
  `zoom/scroll_y/columns/page_gap/fit_width`，未定义坐标单位、留白语义与缩放锚点算法。
- **决策**：
  1. 文档内部坐标以**点（pt）**为单位；`zoom` 表示"每点多少屏幕像素"
     （`zoom = 1.0` 即 72dpi 原始尺寸）。屏幕坐标 = 内容点坐标 × zoom + 原点偏移。
  2. `margin_px`/`gap_px` 是**屏幕像素**常量，换算进文档坐标时除以 zoom
     （`margin_pt = margin_px / zoom`），使缩放时页间距在视觉上恒定。
  3. `fit_width` 模式下 zoom 派生：
     `zoom = (viewport_w − 2·margin_px − (cols−1)·gap_px) / (cols · max_page_w_pt)`。
     该式保证 `content_width_px` 恒等于 `viewport_w`（实测断言见 canvas_test）。
  4. 内容窄/矮于视口时**居中**；否则按 scroll 偏移。`scroll_x/scroll_y` 钳制到
     `[0, content − viewport]`。
  5. **以鼠标为锚的缩放**：记下锚点对应的文档点，缩放后令其仍落在同一屏幕点
     （`scroll = doc_pt · z_new − anchor`），再钳制；缩放即切到固定模式。
  6. 派生量（内容尺寸、行顶前缀和）做**可失效缓存**；滚动**不**使缓存失效
     （滚动只影响原点，不影响布局），保证每帧滚动仍是 O(1) 查询。
  7. 本期**所有页面按统一尺寸布局**（取首页尺寸）。异构尺寸页的逐页布局留待后续：
     接口 `set_page_sizes` 已就位，布局函数无需改动。
- **与架构文档的偏差**：新增 `scroll_x`——放大到超过视口宽度后横向平移是必需的；
  已在 [02-架构设计](02-架构设计.md) §2.1 同步。
- **后果**：布局是**纯函数**，可脱离 UI 单测（`tests/canvas_test.cpp`，61 例）。

## ADR-019 纹理生命周期：渲染线程建纹理 + 帧首退役队列（2026-10-05，Phase 3）

- **背景**：架构文档 §2.3/§3.3 要求画布**不持有裸纹理指针**，且不能删除
  "正在被本帧 draw list 引用"的纹理。
- **决策**：
  1. 渲染线程用 `ID3D11Device` 直接建纹理（`CreateTexture2D` + 初始数据，
     `D3D11_USAGE_IMMUTABLE`；device 方法 free-threaded，可跨线程调用），
     上传完成即释放 `PageBitmap`。
  2. 被替换/逐出的纹理进**退役队列**；UI 线程在**帧首** `drain_retired()` 统一 `Release`。
  3. 正确性依据：帧 N 引用的纹理若在帧 N 期间被退役，只会在帧 N+1 帧首（即帧 N
     `Present` 之后）释放；D3D11 的 `Release` 在 GPU 仍在用时由运行时延迟回收，
     故不存在悬空引用。**不引入** D3D11 延迟上下文，保持简单。
  4. 画布只读快照 `PageSlot{status, texture, …}`；`texture` 以**不透明 `void*`** 暴露
     （UI 侧转 `ImTextureID`），所有权始终在渲染层。
- **后果**：Phase 4 的"纹理延迟释放队列 + 错误占位 + 重试"在本接口上完整化。

## ADR-020 渲染调度层取代 DocSession；Phase 3 用"保留窗口"缓存（2026-10-05，Phase 3）

- **决策**：
  1. 新增 `lilithreader.render`：单工作线程独占 `Document`（延续 ADR-006/ADR-012），
     UI 线程零 `fz_*`、零阻塞。**Phase 2 的 `DocSession` 临时线程随之删除**。
  2. 页状态机 `Unloaded → Loading → Loaded / Failed`；渲染请求**去重**
     （同页同倍率不重复渲染）。
  3. 缓存：Phase 3 用**保留窗口**（可见 ± 预加载，外扩 `kRetainMargin = 4` 页）
     逐出窗口外的已加载页；Phase 4 改为**按字节预算的 LRU**，本层接口不变。
     **勘误（2026-10-05，Phase 4）**：接口确有新增 —— `set_cache_budget` / `cache_stats` /
     `retry_page`（失败重试需要）。"不变"指的是 `PageSlot` / `RenderWant` / `DocState` 等
     既有契约不变，逐出策略的替换对上层透明；详见 [ADR-030](#adr-030-页缓存改为字节预算-lru策略抽成零依赖纯模块2026-10-05phase-4)。
  4. `set_wanted` 与上次请求相同则不去重投递，避免每帧空转唤醒渲染线程。
  5. 接口不引入 `d3d11.h`：设备以 `void*` 传入（模块内不透明），保持后端解耦

- **后果**：Phase 4 的失败重试、方向感知预加载、字节预算在本层落地；
  `Renderer` 必须在 D3D11 设备之前销毁（main 中已保证）。

## ADR-022 画布按**逐页真实尺寸**布局（2026-10-05，第三轮调试）

- **背景**：实测发现"**部分 PDF 渲染有形变**"。画布用**首页尺寸**对全部页做
  统一布局（`set_uniform`），而渲染层用 `fz_bound_page(page)` 各自的 bounds 出图。
  两者纵横比一致时无事；**PDF 允许各页 MediaBox 不同**（封面页、横向插页、扫描裁切
  不一），此时纹理被拉伸进"首页纵横比"的矩形 → 形变。
  （测试样本生成器曾因 `Kids` 偏移生成非法 PDF、掩盖了该问题，过程见归档 §8.1。）
- **决策**：
  1. `Document::info()` 额外探测**逐页**尺寸：每页一次 `fz_load_page` + `fz_bound_page`
     （不跑内容流、不解码图像），结果放进 `DocumentInfo::page_sizes`（点，长度 = 页数）。
  2. 探测放在 `fz_try` **之外**（要构造 `std::vector`，longjmp 不会析构它）；
     **每页一个独立 `fz_try`**（`bound_page_pt`），单页损坏只让该页回退为 `{0,0}`，
     绝不把整篇 `info()` 拖成错误 —— 与渲染路径的容错粒度一致。
  3. 上层用 `canvas.set_page_sizes()` 逐页布局：**列宽取最宽页、行高取行内最高页、
     每页按自身纵横比绘制**。尺寸为 0 的页回退到首页尺寸（画布已有该回退）。
  4. 页 0 复用 `info()` 已取到的 bounds，省一次 `load_page`。
  5. **页数上限**：页数 > `kMaxSizeProbePages`(10000) 时**整表留空**（上层回退统一尺寸布局）。
     理由是探测为 O(页数)，而损坏/构造的文档可能上报天文数字的页数，不设上限会在"打开"
     阶段长时间卡住。实测成本约 **20µs/页**（1000 页 ≈ 18ms，PyMuPDF 同源函数实测），
     真实书籍远低于阈值，故该上限不构成实际影响。
- **理由**：这是唯一能同时消除形变**并**让异构文档排版正确（行高、页间距）的做法；
  `set_page_sizes` 接口本就在 Phase 3 备好，布局函数无需改动。
- **代价**：打开时多 N 次 `fz_bound_page`（后台线程，不阻塞 UI；1000 页约 18ms 量级）。
- **后果**：`doc_test` 新增"逐页尺寸"断言表（均匀页 + 异构页各 1 例），
  把"逐页尺寸"本身钉成规格；形变在自动化层面有了防线。

## ADR-023 翻页改用**显式阅读游标**（2026-10-05，第三轮调试）

- **背景**：实测发现"**左右翻页连续按到某一页会卡住**"。根因：翻行以 `visible_first()`
  为游标，而 `visible_first()` 由滚动位置反推。当**视口比"一行"还高**时（横向页 /
  缩小 / 多列），末尾若干行的 `row_top` 会超过 `max_scroll_y`，**无法**被对齐到视口顶部；
  滚到底后 `visible_first()` 仍停在倒数第二行 → 连续按右键不再有进展。
- **决策**：
  1. 画布引入唯一的有状态成员 `nav_row_`（**阅读游标**）：`current_row()`/`current_page()`
     直接读它；`scroll_rows(dir)` 在游标上推进一行，再 `scroll_to_page(目标行)`。
     **游标推进与滚动钳制解耦**：即使 `scroll_y` 被钳到 `max_scroll_y`，游标仍前进一步，
     因此末尾几行（此时必然已整行可见，不漏内容）能逐页走完并在末行正确终止。
  2. 游标**不参与任何布局计算**，只在"到底"时有一个语义特例：`row_from_scroll()` 在
     `scroll_y ≥ max_scroll_y` 时返回**末行** —— 这样页码显示的是末页而非倒数第二页。
  3. 回同步点（手动滚动 / 缩放 / fit）统一走 `sync_nav_row()`；显式跳页
     （`scroll_to_page`）直接把游标设为目标行。
- **与架构文档的偏差**：ADR-018 声称画布"无隐藏状态"。现修正为：**布局**无隐藏状态
  （仍是纯函数 + 可失效缓存），**阅读游标**是唯一的有状态量，且只服务翻页与页码指示。
  已在 [02-架构设计](02-架构设计.md) §2.1 同步。
- **后果**：`canvas_test` 新增 3 组用例（矮页视口、多列按行推进、游标与手动滚动同步），
  含"恰好 N 次下翻走到末页、再多按无操作"这类**可程序判定**的回归断言。

## ADR-024 重渲染时**保留旧纹理**（2026-10-05，第三轮调试）

- **背景**：实测发现"**缩放时有时会闪烁**"。根因在 `render_one`：进入 `Loading` 时用
  `PageSlot{}` 覆盖整个槽位，**旧纹理立刻从快照消失** → UI 先退回"载入中…"占位框，
  等新纹理就绪再换入，肉眼就是闪一下。同一个覆盖动作还导致旧 SRV 指针被直接丢弃、
  未进退役队列 —— **每重渲染一次泄漏一个纹理**（缩放越频繁，显存涨得越快）。
- **决策**：
  1. `mark_loading(page)` **只改状态，绝不动 `texture`/`scale`**。UI 在重渲染期间继续
     显示旧纹理（双线性放大，略糊但不闪），新纹理就绪时在**同一把锁内原子替换**。
     这正是架构文档 §2.4"防抖期间用现有纹理显示（不闪白、不错位）"的原意，此前未落地。
  2. 替换路径统一 `retire_locked(旧纹理)` 入退役队列（由 UI 帧首 `drain_retired()` 释放）。
  3. `mark_failed(page, err)` **保留已有纹理**：宁可继续显示旧图，也不要闪回"渲染失败"
     占位框；从未成功渲染过的页 `texture` 为空，UI 自然显示失败占位。
- **后果**：缩放不再闪烁；纹理泄漏消除（配合 ADR-019 的退役队列）。
  Phase 4 的失败重试/退避在此语义上继续演进。

## ADR-025 界面按 DPI 缩放 + 预留字号设置（2026-10-05，第三轮调试）

- **背景**：实测反馈"**字有点小，怀疑没考虑屏幕缩放**"。核查：字体固定 18px、
  ImGui 样式与自绘像素常量都不随 DPI 变化；而进程是 Per-Monitor V2 DPI aware，
  ImGui 的 `DisplaySize` 是**物理像素**，故在 125%/150% 显示器上文字相对变小。
- **决策**：
  1. `style.FontScaleDpi = 窗口所在显示器 DPI 缩放`（`ImGui_ImplWin32_GetDpiScaleForHwnd`），
     `WM_DPICHANGED` 时刷新并重建样式（消息在帧间到达，改样式安全）。
     1.92 起的动态字体系统会按新尺寸重新栅格化，不必手工重载字体。
  2. `style.ScaleAllSizes(dpi × user)` 缩放内边距/间距/滚动条；每次都从**留底的基准样式**
     重算，避免多次缩放累积。
  3. 本项目自绘的像素常量（状态栏高、画布留白/间距、滚动步长、居中文本偏移、最小窗口
     尺寸）统一过 `px()`；`ScaleAllSizes` 管不到它们。
  4. 引入 `g_user_scale`（**字号/界面主缩放**，现固定 1.0）→ `style.FontScaleMain`：
     这是将来"全局设置"的接入点，与 DPI 自动缩放正交。
  5. 基准字号 18 → **20**（直接回应"字有点小"）；状态栏 30 → 34，画布留白 16/12 → 18/14。
- **后果**：100%/125%/150%/200% 下视觉大小一致；F3 调试浮层新增 `dpi/ui/font` 显示。
  将来加"全局设置"只需驱动 `g_user_scale` 并重算一次样式。

## ADR-026 阅读态快捷键**不再依赖 ImGui 窗口焦点**（2026-10-05，第四轮调试）

> **重要澄清（同日修订）**：本条记录的是一处**旁路隐患**，**不是**"按 1/2/3/4 不切列"的根因
> —— 根因见 **ADR-028**（输入法吞键）。第四轮实测中 `focus 1`（画布有焦点）时数字键仍无效，
> 已证伪本条的因果假设。之所以仍保留这条决策，是因为它本身确实是一处会让快捷键**静默失效**
> 的缺陷，值得修掉并留档。

- **缺陷**：`handle_canvas_input` 开头有 `if (!focused) return;`，其中
  `focused = ImGui::IsWindowFocused(RootAndChildWindows)`。
- **它为什么会是 false**：窗口结构是「无边框 shell 根窗口 + `##canvas` 子窗口」，两者都带
  `ImGuiWindowFlags_NoNav`，而 **`NoNav` = `NoNavInputs | `NoNavFocus`**；`NoNavFocus`
  使 ImGui 在窗口出现时**不**把它设为 `g.NavWindow`（`Begin()` 里的 `want_focus` 被否），
  于是**启动后、首次点进画布之前 `IsWindowFocused()` 恒为 false** —— 这段时间内所有
  画布快捷键（1~4 切列、F、G、F11、方向键…）全是死的。调试浮层/弹窗取得焦点时同样会让
  快捷键莫名失效。
- **决策**：阅读态的键盘快捷键改为**应用级**处理，只以「阅读态（调用方保证）+ 无弹窗
  （`g_open_jump`）+ 无文本输入（`io.WantTextInput`）」为门，**不再看 ImGui 窗口焦点**。
  鼠标（滚轮/拖拽）仍要求悬停在画布上。
- **理由**：整个窗口只有一个阅读视图，快捷键本就是应用级语义；把它绑在 ImGui 的窗口焦点上
  既脆弱又不可见（用户看到的只是"按键没反应"）。`io.WantTextInput` 已足以在文本输入时让路。
- **代价**：将来若加入需要独占方向键的 UI 控件（列表 / 滑块），需在此处补
  `io.WantCaptureKeyboard` 或按控件状态放行 —— 已在代码注释中标注。F3 浮层新增
  `canvas hover / focus / text-input` 三项，便于下次"某个键没反应"时一眼定位。

## ADR-027 快捷键语义：不区分主键盘与小键盘（2026-10-05，第四轮调试）

- **背景**：用户明确要求"小键盘的数字也要能切列"，暴露出一个更普遍的问题：
  用 `ImGuiKey_N` 只能匹配主键盘，用 `ImGuiKey_KeypadN` 只能匹配小键盘。
- **决策**：**凡有"数字/算术"含义的快捷键，一律同时接受两套键**：
  - 列数：`ImGuiKey_1..4` 与 `ImGuiKey_Keypad1..4`（见 `pressed_column_key()`）
  - 缩放：`ImGuiKey_Equal`/`ImGuiKey_Minus` 与 `ImGuiKey_KeypadAdd`/`ImGuiKey_KeypadSubtract`
- **理由**：小键盘数字在 ImGui 里与主键盘数字**是不同的键**，不是同一键的不同扫描码；
  只判一套就会出现"主键盘行、小键盘不行"（或反之）这种看起来像玄学的缺陷。
- **后果**：新增带数字语义的快捷键时，必须两套都判 —— 已写入 `docs/02-架构设计.md` 的按键表。
- **实测澄清**：在 ADR-028 修复前，小键盘数字**同样被输入法吞掉**，所以这条改动当时看不出效果；
  脱离输入法之后它才真正生效。

## ADR-028 阅读窗口**脱离输入法**：VK_PROCESSKEY 吞掉字母/数字键（2026-10-05，第四轮调试）

- **背景**：用户反馈"按 1/2/3/4 不切换列数（主键盘与小键盘都不行），**但其他快捷键貌似能用**"。
  后半句很关键 —— 它否定了 ADR-026 的焦点假设：若焦点是原因，方向键会一起失效。
- **根因**：**Windows 输入法接管了字母/数字键**。输入法启用时，系统会把这类键的
  `WM_KEYDOWN` 的 `wParam` 换成占位码 **`VK_PROCESSKEY (0xE5)`**（真实键码只交给输入法），
  同时用 `WM_CHAR` 把字符交给应用。而 ImGui 的 win32 后端
  `ImGui_ImplWin32_KeyEventToImGuiKey()` 的 switch **没有 0xE5 这个 case**（已全文件检索确认），
  于是 `key == ImGuiKey_None` → `AddKeyEvent` 被跳过 → **`ImGuiKey_1..4` 根本不置位**。
  字符则经 `io.AddInputCharacter` 正常入队 —— 表现为"**字符到了、按键没到**"。
- **影响面**：不止数字键 —— **所有字母键（`G` 跳页、`F` 回 fit-width）以及数字键**都被吞；
  只有 F 系列、Esc、方向键、PgUp/PgDn 等"输入法不接管"的键能穿透。
- **决策**：窗口创建后立即 `ImmAssociateContext(hwnd, nullptr)` —— **让阅读窗口脱离输入法**，
  键盘回归原生语义。
- **理由**：
  1. 本阶段**没有任何需要输入法的文本输入**（唯一的文本框是纯数字页码），输入法关联在这里
     只有害处没有用处。
  2. 这是唯一能让**所有**键（含将来的快捷键）可靠工作的做法，且不依赖"输入法是否把字符透传"；
     改从 `io.InputQueueCharacters` 判快捷键的字符兜底方案，换一个输入法就不保证成立。
  3. 改动最小、可逆：一行调用 + 链接系统库 `imm32.lib`。
- **代价与后续（重要）**：整窗脱离输入法意味着**将来加入中文输入（搜索框/批注）时必须重新关联**。
  届时做法是"仅在文本输入激活时关联"（`io.WantTextInput` 变化时在
  `ImmAssociateContext(hwnd, saved)` / `nullptr` 之间切换），或按控件粒度处理。
  **这条约束写在这里，避免将来有人加了中文输入框却忘了这回事。**
  另：切换输入语言（`WM_INPUTLANGCHANGE`）会让系统重新关联输入法，需再脱离一次（代码已处理）。
- **验证**：修复后 F3 读数从 `WM_KEYDOWN: E5` 变为真实键码（定位过程与实测读数见归档 §9）。
- **教训**：症状"某些键不响应"时，**先在窗口消息层取原始数据**，不要在应用层推理。
  本轮第一次修复（ADR-026）方向错了，代价是一轮返工。

## ADR-029 页/列间距改为**列宽比例**（随缩放变化）（2026-10-05，第四轮调试续）

- **背景**：ADR-028 修复并实测通过后，用户反馈"**页面的间隔貌似是固定的**，理想情况最好
  随着缩放改变，不然页面缩小的时候感觉上的间距会显得太大"。
- **根因**：`gap_px` 原本是**屏幕像素常量**，`ensure_layout` 里除以 zoom 换算进文档坐标 ——
  于是屏幕间距恒为 `gap_px`，与缩放无关。缩小时页面变小而间距不变，视觉比例失衡。
- **决策**：把间距从"屏幕像素常量"改为"**列宽（最宽页）的比例**"：
  `gap_pt = gap_ratio × max_page_w_pt`，屏幕间距 = `gap_pt × zoom`，**严格正比于 zoom**。
  - `CanvasState::gap_px` → `gap_ratio`（默认 0.013）；`set_margin_gap(margin_px, gap_ratio)`。
  - `fit_width` 方程把间距项放进**分母**：
    `zoom = (viewport_w − 2·margin_px) / (cols·max_page_w_pt + (cols−1)·gap_pt)` ——
    "内容宽度恰等于视口宽"的不变量**仍然严格成立**：把
    `content_w_px = inner_w_pt·zoom + 2·margin_px` 代回即得 `viewport_w`。
  - 留白 `margin_px` **保持屏幕像素**：它是"窗口边缘的呼吸空间"，属界面 chrome，不该随缩放。
- **为什么用比例而不是固定 pt**：固定 pt 无法同时保住不同页幅文档的观感 —— 例如取 16pt 时，
  1191pt 宽的扫描件在 fit-width 下间距恰好（约 21px），而 A4 会变成两倍（约 42px）。
  比例则让任何页幅的文档视觉比例一致；且在 fit-width 单列下屏幕间距 = 比例 × 视口宽，
  与本轮修改前的观感一致（约 1.3% 视口宽），**默认视图无可见回归**。
- **代价**：低倍率下间距会很小（zoom 0.2 时约 1.6px）。**刻意不加屏幕下限**：间距出现在
  fit-width 方程的分母里，加了下限后方程不再自洽（会破坏"内容宽恰等于视口宽"的不变量）。
  低倍率下页面本就很小，细缝是正常观感；将来若确需下限，应改为"限制缩放范围"或把下限并入方程求解。
- **验证（自动化，无需人工）**：`canvas_test.cpp` 新增 `test_gap_scales_with_zoom`（5 例）：
  间距 = 比例×页宽×zoom、zoom 翻倍则间距翻倍、fit-width 视口减半则间距约减半、
  含间距后 fit-width 仍严格铺满视口宽。同时把 7 处按旧语义写死的期望值改为**按定义独立重算**
  （测试装置里加了 `gap_at(zoom)` / `fit_zoom(cols)` 两个独立推导的辅助函数）。

## ADR-030 页缓存改为**字节预算 LRU**，策略抽成零依赖纯模块（2026-10-05，Phase 4）

- **背景**：Phase 3 的缓存是**保留窗口**（可见 ± 预加载外扩固定页数）逐出窗口外的页，
  预算以**页数**计。但单页纹理大小随渲染倍率变化极大：A4 在 zoom 1.0 约 2MB、zoom 4.0
  约 32MB，A0 海报可达数百 MB。按页数计预算会在高倍率下 OOM、低倍率下浪费显存；
  且"保留窗口"与滚动速度无关，快速滚动时窗口频繁移动、反复重渲。
- **决策**：
  1. 缓存改为按**字节预算**的 LRU：默认 **512MiB**，可设范围 **128MiB~2GiB**。
     逐出时先按 LRU（最久未用先出）逐出**非本帧需要**的页，直到驻留总量降到预算内。
  2. **本帧需要的页（可见 + 预加载）pinned，永不逐出**。因此当可见页自身的字节数就
     超过预算时，总量会短暂高于预算 —— 这是**有意**的：宁可超预算，也不能把正在显示的页
     抽走（抽走会闪回占位框）。预算的真正作用是给"窗口外的历史页"设上限。
  3. 逐出选择抽成**零依赖纯模块** `lilithreader.page_cache`（`select_evictions`）：
     输入是 `CachePageView[]`（字节数/LRU 序号/pinned）+ used + budget，输出逐出下标表。
     这样"选谁逐出"可脱离 D3D11/线程单测（`tests/page_cache_test.cpp`），
     与 canvas 把布局纯函数化同一思路（ADR-018）。
  4. 预算可由 exe 同目录 ini 的 `[cache] BudgetMB` 配置（缺省 512），
     `Renderer::set_cache_budget` 统一钳制到合法区间；调小会立即触发一次逐出。
- **理由**：字节预算是唯一能在"高倍率不 OOM"与"低倍率不浪费"之间自洽的口径；
  LRU 比"保留窗口"更贴合真实阅读（跳读、回翻都不再反复重渲）。
- **代价**：需在渲染线程维护 `used_bytes` 与 LRU 时钟（O(1) 记账 + 逐出时 O(N) 扫描，
  N = 页数，可接受）；`select_evictions` 每次逐出扫描一次视图数组。
- **后果**：`CacheStats`（预算/驻留字节/驻留页数/累计逐出）经 F3 浮层可见；
  逐出与重试的规则进入自动化断言，回归有防线。

## ADR-031 渲染失败状态机：自动重试 ≤1 + 点击重试（2026-10-05，Phase 4）

- **背景**：Phase 3 的 `mark_failed` 只把页标为 `Failed`，但 `handle_wants` 的跳过条件
  只认 `Loading`/`Loaded` —— 于是**每次 wants 变化都会重渲失败的页**。快速滚动时
  wants 每帧变，等于对确定性失败的页（损坏、超大页分配失败）无限重试，白耗渲染线程。
- **决策**：
  1. **自动重试上限 1 次**（`kMaxAutoRetries`）：初次渲染失败后立即自动再试一次
     （可救"瞬时"失败，如一时分配不到显存）；仍失败则**定格为 `Failed`**，不再自动重试。
     **"定格"绑定失败时的倍率**：同倍率的重复请求被抑制，倍率一变即视为**新请求**、
     重置额度。否则"曾成功渲染过、重渲失败仍保留旧纹理"的页会永久卡在旧倍率上
     （旧纹理还在，点击重试又无从触发）。
  2. `Failed` 页显示**错误占位**（"渲染失败 · 点击重试"）；用户点击占位 →
     `Renderer::retry_page(page)`：重置自动重试计数并重新排队。
  3. 判定规则抽成纯函数 `should_render_failed(manual, auto_retries_used)`（同 ADR-030 模块），
     手动重试恒真、自动重试受上限约束，进入自动化断言。
  4. 重试/加载期间**保留旧纹理**（沿用 ADR-024）：曾成功渲染过的页即使重渲失败也继续
     显示旧图，只有"从未成功渲染过"的页才显示失败占位（此时才有得点）。
- **理由**：区分"瞬时失败可自愈"与"确定性失败需人判断"，既避免空转，又给了用户出口；
  上限为 1 是因为更激进的重试对确定性失败无益，反而拖慢滚动。
- **代价**：`Entry` 增加 `auto_retries` / `manual_retry` 两个字段；`retry_page` 需重新
  武装一次调度（否则 `set_wanted` 的去重会拦住"同参数"的再次投递）。
- **后果**：失败页不再随滚动无限重渲；`Failed` 成为**可终止**状态，由用户或文档切换解除。

## ADR-032 预加载改为**方向感知**（2026-10-05，Phase 4）

- **背景**：Phase 3 的 `emit_wants` 无条件预加载可见行**上下各一行**。滚动有方向，
  反向那一行在下一帧多半就被逐出，等于白渲染。
- **决策**：预加载仍为"可见行 ±1 行"，但**只在与滚动方向一致的一侧**多取一行 ——
  向下滚只预取下方、向上滚只预取上方；**方向未定**（刚打开 / 跳页后）时两侧都预取，
  避免首个方向反转时出现空档。方向由内容坐标 `scroll_y` 的变化判定（阈值 0.5px 抑制抖动）。
- **理由**：与用户直觉一致（往下翻就该先备好下面），且直接减少渲染线程与显存的无效占用。
- **代价**：新增 `g_scroll_dir` / `g_prev_scroll_y` 两个 UI 侧状态（打开文档与跳页后复位）。
- **后果**：滚动时 wants 的页数近似减半；配合字节预算 LRU，快速滚动下缓存更稳。

## ADR-033 纹理退役改为**两段式队列**（2026-10-05，Phase 4）

- **背景**：ADR-019 定下"渲染线程只入队、UI 帧首 `drain_retired()` 释放"。原实现是
  单队列：退役即入 `retired`，下一次帧首整体释放。正确性依赖"drain 恰好在帧首"这一约定 ——
  一旦有人把 drain 挪到帧末（或插入别处），就可能释放"本帧 draw list 仍引用"的纹理。
- **决策**：改为**两段式**：渲染线程把退役纹理放入 `retired_pending`（本帧）；
  `drain_retired()` 先释放 `retired_ready`（上一帧的 pending），再把 pending 移入 ready。
  于是任何纹理都**至少活过一个完整帧**才被 `Release`。
- **理由**：把"帧内引用安全"从**约定**升级为**结构不变量** —— 不依赖调用位置，
  将来挪动 drain 也不会引入悬空句柄。
- **代价**：显存回收延迟约一帧（对阅读器无感）。
- **后果**：配合 D3D11 `Release` 自身对在途 GPU 引用的延迟回收，悬空纹理从机制上被排除。

## ADR-034 阅读状态持久化：reader_state.bin 的键、格式与原子写入（2026-10-05，Phase 5）

- **背景**：Phase 5 要"记住每本书读到哪、有哪些书签、用什么视图参数"，需要一个持久化载体。
  `LilithReader.ini` 是 `GetPrivateProfileStringW` 的键值文本，不适合存"每文档一条、含变长书签表"的结构。
- **决策**：新增**零依赖模块** `lilithreader.reader_state`，独立二进制文件
  `reader_state.bin`（exe 同目录）：
  1. **键 = 路径 + 文件大小 + 修改时间 的 FNV-1a 64 哈希**（`document_key`）。这样文件被替换/改名后
     不会串到别的记录上；哈希冲突只会让两个文档共享一条记录（代价可接受，不会损坏用户文件）。
     取不到属性（文件不存在）返回 0，视为无效键、不参与存取。
  2. **格式**：magic `LRS1` + u32 版本 + u32 条数 + 逐条记录（全小端）。含阅读位置
     （页/缩放/列/旋转/对开/fit/配色）与书签表。上限（条数/书签数/标签长度）写死在接口里。
  3. **解析失败一律安全拒绝**：magic/版本不符、截断、超限 → 返回空状态且**不改动输出**。
     阅读状态是"锦上添花"，绝不能因它损坏而崩溃或影响打开文档这条主路径。
  4. **原子写入**：写同目录临时文件 → `MoveFileExW(REPLACE_EXISTING)`。与架构文档 §5 的承诺一致。
  5. **纯序列化与磁盘 I/O 分离**：`encode_state`/`decode_state` 不碰 Win32，可脱离磁盘单测
     （`tests/reader_state_test.cpp`，43 例）——与 canvas 布局纯函数化、page_cache 纯策略同一思路。
- **理由**：二进制 + 版本号是"变长结构 + 向前兼容"的最省心做法；哈希键省掉一张需要维护的
  "路径→记录"映射；纯序列化单测把"坏输入必须拒绝"钉成规格。
- **代价**：文档改名/移动后阅读位置丢失（键含路径）——可接受，且不会误配到别的文档。
- **后果**：`reader_state.bin` 与 `LilithReader.ini` 并列，都在 exe 同目录。

## ADR-035 目录（outline）展平为前序序列（POD 缓冲 + `fz_page_number_from_location`）（2026-10-05，Phase 5）

- **背景**：MuPDF 的 `fz_outline` 是 `next`（同级）/`down`（子级）构成的树；UI 侧需要能直接线性绘制。
  且 `fz_outline::page` 在 1.26 是 `fz_location{chapter,page}`（不是裸 int），epub 有章节维度。
- **决策**：
  1. `Document::outline()` 把树**展平为前序序列** `std::vector<OutlineItem>{title,page,depth}`：
     depth 表层级，顺序即阅读顺序。UI 只需一次线性遍历（缩进按 depth），接口不引入递归容器。
  2. 遍历用 `walk_outline` 写入**预先分配的 POD 缓冲**（`new (nothrow) OutlinePOD[]`，
     raw 指针跨 `fz_try` 安全）；转 `std::vector<OutlineItem>` 一律在 `fz_try` **之外**完成。
     严格遵守 ADR-009：`fz_try` 内不构造任何需析构的 C++ 对象，连"跨块存活的 C++ 对象"也不引入。
  3. 页号解析：优先用 MuPDF 已解析的 `fz_location`（`fz_page_number_from_location`）；
     无目标时退回按 `uri` 解析（`fz_resolve_link`）。两者都解析不出则 page = -1。
  4. 上限：节点数 2048、深度 32（防病态文档深树递归爆栈），超出截断。
  5. 加载时机：打开/解锁成功后由**工作线程**一次性加载，存入 `Renderer` 的 `outline_` 快照；
     UI 进入阅读态时取一次（**不得每帧调用**，会拷贝整张表）。
- **理由**：展平让 UI 侧零递归、零树遍历；POD 缓冲让 ADR-009 纪律在"要建容器"的场合也成立。
- **代价**：目录表在 `Renderer` 里常驻一份（通常几百项，可忽略）；节点数超上限会截断（真实书籍远未及）。
- **后果**：`doc_test` 用带两级目录的合成 PDF（`outline.pdf`）把"顺序/层级/页号"钉成规格。

## ADR-036 旋转与配色在渲染层完成，变化即整篇重渲（2026-10-05，Phase 5）

- **背景**：需要页面旋转（0/90/180/270）与配色（正常/反色/护眼）。纹理是
  `IMMUTABLE` 且零拷贝上传，"像素进 GPU 后"无法再改属性。
- **决策**：
  1. **旋转在光栅化阶段完成**：`render_page` 的 ctm 加入旋转
     （`fz_pre_rotate(fz_scale(s,s), deg)`；等比缩放与旋转可交换，顺序无关）。
     `clamp_scale` 按**旋转后**包围盒钳制——否则 8000×100 的横幅旋转后会得到 8000 高。
  2. **配色在像素上传前完成**：反色逐像素 `RGB ← 255−RGB`、护眼用 LUT 把黑/白线性映射到
     暖色端点（`#2B2318`/`#F6EEDC`）。**不用** `fz_invert_pixmap`/`fz_tint_pixmap`：这两者面向
     RGB/Gray，对**带 alpha 的 4 分量 RGBA** 行为不在公开契约里；自写逐像素变换（只改 RGB、
     保留 alpha）行为完全可控且可单测（`doc_test` 断言背景白→黑、alpha 不变、护眼 R>B）。
  3. **旋转/配色是文档级视图状态**（`Renderer::set_view_transform`）：任一变化即
     **让全部页纹理与缩略图失效并整篇重渲**（变换已固化进像素）。失效走既有的两段式退役队列。
  4. 旋转折算成**页尺寸宽高互换**交给画布：画布本身不感知旋转，布局/翻页/缩放全部复用。
- **理由**：把变换放在唯一的像素入口（渲染线程）而非 UI 叠加 shader，最省心且与"UI 线程零阻塞"一致；
  自写配色变换消除对 MuPDF 未定义行为的依赖。
- **代价**：切换旋转/配色会触发一次整篇重渲（可见页优先，预加载随后）；频繁切换有短暂重渲。
- **后果**：`doc_test` 断言 0°/180° 尺寸不变、90° 宽高互换、反色/护眼的背景像素与 alpha。
- **勘误（2026-10-05，人工验证）**：本 ADR 第 2、3 条已被 ADR-042/043 修订——
  反色不再是 `RGB ← 255−RGB` 的纯反相（改为柔化暗色映射），且"任一变化即全部纹理失效"
  收窄为"旋转失效重渲；仅配色变化保留旧纹理原地换入"。旋转部分不变。

## ADR-037 缩略图走**独立通道**，不占页缓存预算（2026-10-05，Phase 5）

- **背景**：侧栏缩略图需要低 DPI 页面图像。若复用页纹理槽位，缩略图与正文会互相覆盖倍率。
- **决策**：`Renderer` 增加一条**并行的缩略图通道**：
  1. `set_thumbs_wanted(pages, target_px)` 声明需要的页与目标最长边；工作线程按
     **旋转后**页尺寸算目标倍率（最长边 ≈ target_px）渲染，存入独立的 `thumbs[]` 缓存。
  2. 缩略图**独立字节记账**（`thumb_bytes`），不参与页缓存的 LRU/预算——缩略图很小，
     挤占正文预算不合理。
  3. 缩略图渲染**不自动重试**（侧栏是辅助视图，失败留空占位）；视图变换变化或重开文档会重置状态自然重试。
  4. 侧栏只请求**当前页 ±40 页**一段，随当前页滚动扩展，避免一次性渲染整本书。
- **理由**：与页缓存解耦后，缩略图的存在与否不影响正文的清晰度策略与逐出行为。
- **代价**：`Renderer` 多一份缓存与一条处理分支；缩略图请求按 (页列表, target_px) 去重。
- **后果**：F3 浮层/调试可扩展显示缩略图状态（当前仅接口就位）。

## ADR-038 双页对开（书籍模式）＝ 2 列 + 封面单独成页（薄扩展，复用网格）（2026-10-05，Phase 5）

- **背景**：Phase 3 已有 1~4 列**均匀网格**（`row=i/cols, col=i%cols`）。Phase 5 计划另列"双页对开（书籍模式）"。
  两者**不是同一件事**：真实书籍装订是封面单张、正文成对——网格会把封面与第 2 页凑成一对。
- **决策**：**不重写布局**，在网格上加一个薄层：
  1. `CanvasState::spread` 开关；开启时**等效 2 列**（columns 被忽略）。
  2. index→slot 映射改为：页 0 独占第 0 行；页 i≥1 → `row = 1+(i-1)/2, col = (i-1)%2`。
     第 0 行页数恒为 1，其余行最多 2。
  3. 映射集中在 `eff_cols/row_first_page/row_page_count/row_of` 四个函数里分支；
     缩放/滚动/钳制/游标/翻页全部复用网格逻辑。
  4. 单独成页的行（封面、末页）在**整行宽度内居中**，避免单独一页贴左。
  5. **`spread=false` 时映射与行为逐位不变**——由 `canvas_test` 的回归守卫钉死。
- **理由**：与既有网格共享 95% 逻辑，风险最小；差异只在"奇偶偏移 + 单独页居中"。
- **代价**：`page_rect`/行高计算改为按"该行页数"而非固定列数；切换对开时按当前页重新锚定
  （锚点页须仍在可见范围内）。
- **后果**：`canvas_test` 新增 27 例对开断言（映射/居中/翻页/回归守卫/切换锚定）。
- **勘误（2026-10-05，第五阶段人工验证）**：原文第 1 条"spread 开启时 columns 被忽略"只描述了
  **布局求值**，未规定**状态转换**，导致 `set_columns` 在对开期间不生效——用户必须先按 `D`
  关闭对开才能切列，产生"对开高于列数"的错觉（与"二者同层级"的心智模型不符）。现明确：
  1. `set_columns` **显式退出对开**（`state_.spread = false`），即便目标列数与当前 `columns`
     相同也照退（否则早退逻辑会让对开关不掉）；布局求值仍按本条对开映射。
  2. 对开期间 `columns` **保留原值**，仅被暂时覆盖；按 `D` 关闭对开后即恢复（"模式 + 记忆偏好"，
     与只关对开、不改列数的路径一致）。
  3. 二者仍是"同一件事的两种表达"（对开 = 2 列 + 封面偏移），不存在"3 列对开"，
     故"平行"只能实现为**同层级互斥**，而非可叠加。回归守卫见 `canvas_test` `test_spread_book_mode`。

## ADR-039 加密文档密码框 + 权限位读取（2026-10-05，Phase 5）

- **背景**：Phase 2 已实现加密识别（`DocError::NeedsPassword`）与 `Document::authenticate`，
  但缺 UI；且 PDF 标准加密可声明"禁复制/禁打印"，UI 层应尊重。
- **决策**：
  1. `UiDoc::Kind` 增加 `NeedsPassword`：打开返回该错误时弹**模态密码框**，
     提交 → `Renderer::authenticate(pwd)`（文档仍处于打开态）；失败重弹并提示"密码错误"；
     取消/Esc → 关闭文档回引导页。
  2. `DocumentInfo` 增加 `can_copy`/`can_print`（`fz_has_permission`）。无加密或无法判定时
     **一律 true**（保守放行，避免误禁）。当前尚无复制/打印功能，字段先就位供后续置灰。
  3. 密码输入为 UTF-8 明文缓冲（`char[256]`），提交后立即清零。
- **理由**：识别与 authenticate 早已就位，本阶段只补 UI 接线，改动面小。
- **代价**：`UiDoc::Kind` 增加一个枚举值，所有 switch 需覆盖（调试浮层名字表已补）。
- **后果**：`doc_test` 的加密三态断言（Phase 2 已建）覆盖解锁路径；密码框为交互项，入人工清单。
- **勘误（2026-10-05，人工验证）**：解锁链路有两处修复，见 ADR-041/044——
  1) `Document::info` 曾在认证成功后调用 `fz_needs_password()`，在 MuPDF 1.26.10 上会破坏解密 →
     整页空白；现改为读缓存值（ADR-041）。
  2) 密码框原先提交即关、失败再开（且 `Renderer::authenticate` 未置 `Opening`，存在相位竞态），
     会闪烁/误判；现保持弹窗打开、显示"验证中…"（ADR-044）。

## ADR-040 输入法关联随"文本输入激活"切换（落实 ADR-028 的后续要求）（2026-10-05，Phase 5）

- **背景**：ADR-028 让阅读窗口**整窗脱离输入法**（否则输入法吞掉字母/数字键），并明确要求
  "将来加入中文输入时必须改回仅在文本输入激活时关联"。Phase 5 引入了密码框等文本输入。
- **决策**：启动时保存默认输入法上下文（`g_saved_ime = ImmAssociateContext(hwnd, nullptr)`），
  之后每帧按 `io.WantTextInput` 切换：文本输入激活 → 关联回来（可输入中文），否则 → 脱离
  （快捷键回归原生语义）。`WM_INPUTLANGCHANGE` 后按当前状态重新应用（系统会重新关联）。
- **理由**：同时满足两个互相冲突的需求——快捷键可靠 + 中文可输入；且这是 ADR-028 预留的既定路径。
- **代价**：每帧一次状态比较（无变化即不调用 Win32）；`io.WantTextInput` 用上一帧状态，切换有 1 帧延迟
  （对输入法关联无实际影响）。
- **后果**：ADR-028 的"后续约束"解除；将来加搜索/批注框无需再处理此事。

## ADR-041 加密文档"解锁后整页空白"：认证成功后不得再问 `fz_needs_password()`（2026-10-05，第五阶段人工验证）

- **背景**：人工验证 `tests/samples/enc_aes256_user.pdf`（口令 `lilith`）时，解锁后页面全白。
  排查得到决定性证据：样本本身有内容（纯 MuPDF 渲染出 769 个深色像素），而**在认证成功之后**
  多调一次 `fz_needs_password()`，同一份纯 MuPDF 复现出的深色像素即变成 0（内容流被静默解成
  乱码）。（定位过程与实测读数见 [归档](archive/2026-10/ADR-过程记录归档.md#adr-041)。）
- **决策**：
  1. `Document::Impl` 缓存 `int needs_password`：`open()` 探测时写入，`authenticate()` 成功后清 0；
  2. `Document::info()` **不再调用** `fz_needs_password()`，改读缓存值；
  3. 该纪律写进 `authenticate()`/`info()` 注释，并让 `mupdf_probe` 记录同一条禁忌。
- **理由**：这是 MuPDF 1.26.10 的行为（`fz_needs_password` 在已认证的 PDF 上破坏解密状态），
  非本项目逻辑可绕开；缓存是最小且语义等价的规避。加密 PDF 在应用里的链路恰是
  `authenticate() → info() → render_page()`，故必然踩中。
- **代价**：`needs_password` 多一份需维护的缓存状态（随 `destroy()` 复位）。
- **后果**：`doc_test` 的加密用例新增"解锁后必须渲染出深色像素"断言，把此回归钉死。

## ADR-042 配色（反色/护眼）切换不闪白：保留旧纹理，标记 stale 原地换入（2026-10-05，第五阶段人工验证）

- **背景**：人工验证反馈"开反色/护眼会使整页刷新产生闪烁"。原实现（ADR-036 第 3 条）在任一
  视图变换变化时 `invalidate_all`：退役全部纹理并置 `Unloaded`，UI 立刻改画占位/背景 → 白闪，
  待异步重渲完成才恢复。
- **决策**：**区分两类变换**：
  1. **旋转**：会交换版面宽高，旧纹理贴进新框会拉伸错位 → 仍整体失效重渲（保持原行为）；
  2. **仅配色**：版面不变 → **保留全部已驻留纹理继续显示**，只把条目标记 `stale=true` 并原样
     重新投递请求；`handle_wants`/`handle_thumbs` 对 stale 条目强制重渲，`publish_loaded`
     原地换入新纹理（旧纹理照常进两段式退役队列）。全程无空白帧。
- **理由**：这与 ADR-024"重渲染时保留旧纹理"同一精神，只是把 stale 从"倍率不够"扩展到"视图变换已变"；
  代价仅是 `Entry` 多一个 bool。
- **代价**：配色切换瞬间会短暂显示"旧配色"的图（约一次重渲时间），随后整屏切到新配色。
- **后果**：缩略图同规则；`last_wants`/`last_thumb_pages` 不变（去重语义不变）。

## ADR-043 反色模式：柔化暗色映射 + **整窗深色**（2026-10-05，第五阶段人工验证）

- **背景**：人工验证反馈"纯反色辣眼睛"，且"反色只作用于页面像素、窗口四周仍亮，实际作用不大"。
- **决策**：
  1. 反色像素变换由 `RGB ← 255−RGB` 改为**柔化的暗色映射**：白 → 深暖灰 `#1F1D1B`、
     黑 → 浅暖灰 `#D8D4CE`，逐通道线性 LUT（等价于"反相后把对比度压到 [暗,亮]"），避免 #000/#FFF 的刺眼对比；
  2. **反色模式下整套 chrome 转深色**：画布背景/页面描边/状态栏/占位色走可切换调色板 `g_pal`
     （浅/深两套），ImGui 控件配色同步切到深色主题（`apply_theme_colors`）。由 `sync_theme(g_color_mode)` 每帧按需应用。
- **理由**：暗色阅读的价值在于"整屏暗"，只反页面而留亮边框反而更累眼；柔化端点则直接缓解刺眼。
  像素侧仍只改 RGB、保留 alpha，可单测。
- **代价**：UI 颜色不再写死常量，改为调色板 + 主题函数（多一层间接）。
- **后果**：`doc_test` 反色断言由"背景变黑"改为"背景变深灰且非纯黑（8 < R < 80）"。
- **勘误（2026-10-06，UI 优化）**：第 1 条的"反色"已按内容分层（ADR-067）——
  变换**只作用于纸墨层**，照片与插图改为原样保留（仅按 `kImageDim` 轻微压暗），
  模式名也由「反色」改为「深色」。第 2 条的"反色强制深色 chrome"保留，并扩展为
  "纸张方案决定 chrome 的明暗与暖化强度"（ADR-067 第 4 条）。
- **勘误（2026-10-06，UI 优化第二轮）**：第 1 条的**亮端端点**由 `#D8D4CE` 改为 `#D7D5D3`，
  并令 `kLight = kDark + 184` 使逐通道等斜率，两端与中间调暖度一致（避免深色下正文发黄）；
  `doc_test` 补 `ink_black.pdf` 样本与两条断言钉住这一点。（实测值与根因见
  [归档](archive/2026-10/ADR-过程记录归档.md#adr-043)。）

## ADR-044 密码框：认证期间保持打开，消除闪烁与相位竞态（2026-10-05，第五阶段人工验证）

- **背景**：人工验证反馈"密码输入错误会导致整页刷新闪烁"。原实现 `submit_password` 提交即
  `g_open_password=false` 且 `kind=Opening`，失败再由 `poll_document` 重开弹窗并切回
  `NeedsPassword` → 弹窗"关→开"跳变 + 背景 `draw_opening`/`draw_failed` 切换，即闪烁。
  另发现：`Renderer::authenticate` 未像 `open` 那样把 `doc.phase` 置 `Opening`，UI 可能读到上一次
  失败的残留 `Failed`，把"在途认证"误当成结果（时序竞态）。
- **决策**：
  1. `Renderer::authenticate` 投递命令时置 `doc.phase=Opening` 并清 error/detail，与 `open` 一致；
  2. 应用侧新增 `g_auth_pending`：提交后**保持 `NeedsPassword` 与弹窗**，禁用输入并显示"验证中…"；
     结果由 `poll_document` 接收（成功则关弹窗进阅读态，失败则只更新"密码错误"提示）；
  3. `poll_document` 的入口条件放宽为"Opening 或 NeedsPassword+在途"；在途时忽略 Esc。
  4. 明文密码缓冲的**清零时机随之后移**：提交时不再清（弹窗保持、便于改错重试），改为在弹窗
     真正关闭时清——成功走 `poll_document` 的 Ready 分支，取消/关闭走 `reset_doc_state`；
     两处均为整缓冲 `memset`，维持 ADR-039"提交后即清"的安全承诺，避免明文残留。
- **理由**：把认证做成"弹窗内的一次异步等待"，视觉上无跳变；相位置位消除竞态，语义与 `open` 对齐。
- **代价**：新增一个在途标志，需在 `reset_doc_state`/`request_open_document` 复位（已覆盖）；
  密码缓冲的清零点从"1 处（提交）"变为"2 处（成功/取消）"，改动时勿遗漏。
- **后果**：密码框为交互项，其"错误密码不闪烁"入人工清单待复验。

## ADR-045 Phase 6 界面外壳与图标体系（2026-10-05，第六阶段）

- **背景**：Phase 5 以前界面只有顶栏一个汉堡按钮 + 画布右键菜单雏形，控件间距/图标/
  弹窗观感都没有统一基准。Phase 6 要把"能读"做到"顺手、耐看"，且明确要求：
  命令集中（不堆按钮）、多用图标与右键菜单、有设置界面与快捷键帮助界面。
  实测反馈三条：**按钮图标有点歪**、**弹出菜单手感不自然**、**字体间距没把控好**。
- **决策**（分条，均已在代码中落地）：
  1. **图标来源与度量校正**：图标取自系统 `Segoe MDL2 Assets`（PUA 码位表见 `main.cpp` 顶部），
     `MergeMode` 合并进微软雅黑同一字体；只用 `ImFontGlyphRangesBuilder` 烘实际用到的几十个字形。
     启动时用 GDI `GetGlyphIndicesW` 逐个校验字形存在（避免不同 Windows 版本静默回退成 "?"）。
     **度量**：`GlyphMinAdvanceX = 基准字号`（每图标占一个 em，宽度一致 → 方形按钮内水平居中、
     图标↔文字间距恒定）；`GlyphOffset.y = +4`——**实测**：MDL2 字形以基线为锚、向上长出，
     光学中心比汉字高约 6px（在 150% DPI、有效字号 30px 下逐像素量取图标/汉字墨迹中心所得）；
     折算到 20px 基准字号为 4px，故取 +4（该值由 ImGui 随有效尺寸等比缩放）。
  2. **命令集中**：顶栏只留图标按钮（菜单/侧栏/书签/缩放/设置/帮助），状态栏**只读**；
     全部命令进「主菜单（☰）」与「画布右键菜单」两处。视图类命令（列/对开/旋转/配色）
     一律是**带勾选的语义项**，不做成一排看不出状态的按钮。
  3. **扁平按钮**：顶栏按钮默认**无底色**（否则一排按钮就是一排灰块），仅悬停/按下/激活时
     浮现柔和底色；`active` 用低透明强调色底表示"已开启"。
  4. **弹窗观感**：`MenuItemRounding = 6`；弹出菜单统一 `WindowPadding = 8`；
     **菜单项高完全由 `ItemSpacing.y` 决定**（`Selectable` 的高度 = 文字高，**不吃 `FramePadding`**；
     悬停高亮向外扩半个间距、正好铺满整个间距），故取 `kMenuItemGapY = 10` → 30px 项高、
     相邻高亮连续无死区。浅色主题文字由纯黑改为近黑 `(0.13,0.15,0.18)`——
     子菜单箭头用的是 `ImGuiCol_Text`，纯黑下过重。
  5. **间距集中命名**：`kChromePadX / kChromeGapX / kPopupPadXY / kMenuItemGapY`（100% 缩放基准值，
     用前过 `px()`），替换顶栏/状态栏原先各自手调的 `10/14/6/7`。
  6. **设置窗口**：正文放 `BeginChild`（高 = 窗口高 − 底栏），**底栏（恢复默认值/关闭）固定**，
     内容多时只滚动正文；设置项表格 `CellPadding.y` 收窄到 3（控件自身已有 `FramePadding`）；
     设置/帮助窗口默认尺寸按视口 90% 钳制后居中，小屏不越界。
  7. **主题**：浅色/深色/跟随系统三档（`[ui] Theme`），反色模式下强制深色（沿用 ADR-043）；
     图标与字体随主题不换（同一套字形）。
  8. **微动效**：页面首次出现淡入、滚动指示条浮现后渐隐、顶栏自动隐藏（鼠标停在顶部即重现）。
     统一由 `[ui] Motion` 开关，关掉即全程直切。
  9. **应用图标**：`src/app/app.rc` 引 `assets/icon.ico`（exe/窗口/任务栏共用）。
 10. **右键菜单的键盘等价入口**：`Shift+F10` / 菜单键打开同一菜单（标准 Windows 习惯，
     也是无鼠标场景的兜底）。实现为 `g_open_canvas_ctx` 标志 + 画布窗口作用域内 `OpenPopup`，
     与右键**共用同一 ID**。
- **理由**：图标度量不统一是"歪"的根因，靠像素量取而非目测；菜单项高交给 `ItemSpacing.y`
  是因为 `Selectable` 不吃 `FramePadding`（读 ImGui 1.93 源码确认）；命令集中在菜单里
  才不至于把工具栏做成按钮堆。
- **代价**：图标校验与合并增加启动期几十毫秒；`GlyphMinAdvanceX/GlyphOffset` 会让 ImGui 走
  逐字形偏移的较慢路径（本项目字形数量极小，无实感）。菜单项高不再随全局 `FramePadding` 联动，
  调整需改 `kMenuItemGapY`。
- **后果**：界面观感有了统一基准，后续加控件应复用上述常量而非再手调数值。
  排查"右键菜单没反应"时，F3 浮层的 `canvas hover / r-click down/up` 读数可一眼区分
  "输入没到"与"被条件挡住"（本轮实测过程见 [归档](archive/2026-10/ADR-过程记录归档.md#adr-045)）。

> **勘误（2026-10-06）**：本 ADR 第 1 条提到的 `main.cpp` 顶部图标码位表与 `kIconGlyphOffsetY`，
> 已随 ADR-046 的应用层拆分迁至 `src/app/app_internal.h`（图标与度量常量）与
> `src/app/platform.cpp`（`kIconGlyphs` 与启动校验）。文件名已变，内容不变。

## ADR-046 应用层文件划分与死代码清理（2026-10-06，重构）

- **背景**：Phase 6 收尾时 `src/app/main.cpp` 达 2584 行（占全部源码 1/3 强）。一个匿名命名空间里
  同时住着 D3D11/ImGui 引导、约 60 个文件作用域全局量、文档状态机、视图变换、画布输入与全部
  ImGui 绘制。功能虽全，但违反"一事一档"：任一关注点的改动都要在近三千行里定位，且分不清哪些
  是跨模块共享状态、哪些是局部量。同时审计发现一批**从未被调用**的接口与一处补丁残留。
- **决策**：
  1. **按单一职责拆为四个普通翻译单元**，共享声明集中在一份内部头：
     - `app_internal.h`（306 行）：跨 TU 共享的状态与函数声明（平台/会话/绘制分区标注）
     - `main.cpp`（196 行）：入口、进程 DPI 感知、窗口类/创建/恢复、消息循环、窗口过程
     - `platform.cpp`（400 行）：D3D11、ImGui 引导、DPI/界面缩放、主题、图标字体、输入法、偏好、全屏
     - `session.cpp`（411 行）：文档状态机、阅读位置/书签、视图变换、逐页尺寸、画布输入、渲染请求
     - `ui.cpp`（1131 行）：全部绘制（外壳/画布/侧栏/菜单/设置/帮助/弹窗/引导页）
  2. **app 层刻意不做成 C++20 模块**：这里是 Win32/D3D11/ImGui 直连代码，不被复用、也无法脱离
     外部系统单测；真正需要隔离与可测的纯逻辑层（utils/document/canvas/render/state）已经是模块。
     用普通 TU + 内部头即可，"模块边界铁律"（ADR-003/009 等）一条未放松。
  3. 共享状态沿用 **inline variable** 声明在内部头，取代单文件的匿名命名空间：只增可见性，
     不改变任何行为。全部代码为**原样搬移**（仅调命名空间与共享声明），保证"只能编译+单测、
     不能跑程序"的纪律下行为逐字不变。
  4. **删除确认无用的接口/实现**（死代码与重复实现）：
     `Canvas::fit_width_zoom`（无人调用，且与 `ensure_layout` 里的 fit 解重复）、
     `Canvas::row_page_begin`（`first_page_in_row` 的别名）、`Canvas::row_col_of`（私有未用）、
     `PageBitmap::components`/`size_bytes`、`Document::page_size`（`info().page_sizes` 已覆盖同一信息）、
     `Renderer::page_count`/`rotation`/`color_mode`（无人调用）；`canvas.cpp` 里遗留的
     `(void)col_pitch_pt` 补丁变量与随之无用的 `col_w_pt`。
  5. `utils` 的窗口版 `read_ini_int` 收敛为 `read_ini_int_ex(section="window")`（消除重复实现）。
  6. 图标表只保留**实际用到**的 22 个码位（删去 11 个"准备了却从未使用"的字形），
     使"表里就是本项目用到的字形"这句注释与代码一致。
  7. 构建移除 `third_party/imgui/imgui_demo.cpp`（594KB）：本项目从不调用任何
     `ShowDemoWindow`/`ShowStyleEditor`，F3 调试浮层是自绘的。
- **理由**：拆分按"变更频率 + 单一职责"，不按行数硬切，也不引入 `App` 结构体大改——
  后者在无法运行验证的前提下回归风险过高。寻址"重复实现/死代码/与事实不符的注释"时以
  代码为准逐一核对，而不是凭印象清理。
- **代价**：跨文件调用需经 `app_internal.h` 声明；共享全局仍是全局（单窗口应用可接受）。
  新增界面代码应在 `ui.cpp` 既有分区内落位；新状态须先想清归属 TU 再进内部头。
- **后果**：app 层任一关注点的改动都收敛在单个文件（最大 ui.cpp 1131 行，仍可一屏检索到分区）；
  死接口清理缩小了眼面；文档中的"代码起点"（`docs/README.md` 导航表、`04-人工验证.md` 6-1 备注）
  已同步到新文件名。exe 实测 40,802,816 字节（见体积预算）。

## ADR-047 视图动效：一阶滞后插值，画布保持纯函数（2026-10-06，第六阶段人工验证）

- **背景**：第六阶段虽已落地"微动效"（页面淡入、滚动指示条渐隐），但人工验证反馈是
  **"看不到任何动画、过渡或平滑，界面都是生硬的立即改变"**。根因是：真正决定体感的三件事
  ——缩放、滚动、翻页跳转——当时全是**直接改画布状态**，0.18s 的页面淡入根本掩盖不了它们。
  规划里"缩放平滑插值"本就是第六阶段未完成项。
- **决策**：
  1. **动效只发生在 app 层写入画布之前**：画布仍是"状态唯一真源 + 纯函数布局"，不引入任何
     时间/插值概念。理由：`canvas_test` 的 92+ 例断言、"滚动不重算布局"的 O(1) 性质、
     以及"同 seed 逐位一致"的纪律都建立在画布无隐藏状态之上，插值一旦进画布就全被污染。
  2. **统一用一阶滞后（帧率无关的指数趋近）**，不用补间：无过冲、必然收敛、不需要维护速度
     状态，且连续输入自然叠加（补间则每次输入都要重排时间轴，快速连按时会出现"追赶-重启"的顿挫）。
     `approach(cur, target, rate, dt) = target + (cur-target)·e^(−rate·dt)`，收敛阈值 0.5px 内吸附。
  3. **三条路径**（`session.cpp`）：
     - 滚轮 / 方向键 / 整屏滚动 → 增量进 `g_scroll_pending`，逐帧消耗（22/s ≈ 45ms 时间常数）；
     - 显式跳页（跳页框/目录/书签/缩略图/翻行）→ **先让画布算出目标位置**（对开/网格/钳制的
       唯一真源），再回退到起点交给动效滑行。动画结束后**重新钉一次游标**：滑行途中
       `scroll_by` 会把阅读游标同步到"视口顶部所在行"，而末尾几行够不到视口顶部时这个反推值
       会落到末行，与"显式跳页应显示目标行"（ADR-023）冲突；
     - 缩放（Ctrl+滚轮 / ± / 菜单档位 / 适合宽度）→ 显示倍率指数趋近目标倍率，锚点固定不动。
       连续输入基于**目标倍率**累乘，否则倍率会被插值滞后吞掉。
  4. **缩放防抖改为盯"目标倍率"**：原先盯显示倍率，插值期间每帧都在变，防抖会被动画不断重置，
     高清重渲要等动画结束后再等 150ms 才开始；盯目标倍率则"最后一次缩放意图后 150ms"即触发，
     正好在动画收敛时换入高清纹理。
  5. **左键拖拽平移刻意不做平滑**：直接操纵必须 1:1 跟手；拖动开始即掐掉滚轮的平滑尾巴。
  6. **顶栏自动隐藏改为滑出/滑入**：顶栏高度按一阶滞后插值，内容按整条高度排布后整体上移，
     于是收起是"推上去"而不是原地被裁。`[ui] Motion` 关闭时全部路径直切（等价于动效前行为）。
- **理由**：体感问题的成本集中在"输入 → 显示"的链路上，而不是动效的复杂度；把插值放在 app 层
  可以用一处 `approach()` 覆盖全部路径，同时把可单测的模块原样保住。
- **代价**：新增 5 个全局动效状态量（`g_scroll_pending / g_zoom_anim / g_zoom_to /
  g_jump_repin_page / g_top_bar_h`）与一条"动画结束要重新钉游标"的隐式约定；滚动/跳转的最终
  落点由画布算、过程由 app 插值，读代码时需要同时看两处。
- **后果**：F3 调试浮层新增动效读数（`pending / zoom→ / topbar / bar drag`），
  验证"动效是否真的在跑"不必靠肉眼猜。主观动效验收列入人工清单（`04-人工验证.md` 7-1~7-3）。

## ADR-048 UI 字体子集内嵌 + FreeType 装载器（2026-10-06，第六阶段收尾）

- **背景**：界面文字一直用系统 `C:\Windows\Fonts\msyh.ttc`。两个问题：① 观感随机器/系统版本
  漂移，缺该字体时界面直接退化；② 与"单 exe、零外部依赖"的项目目标不符。规划里的做法是
  "常用 3500 汉字 + Latin + 标点子集，`pyftsubset` 生成，约 1.5~2MB"。
- **决策**：
  1. **源字体取 Noto Sans SC Regular（OFL 1.1，思源黑体同源）**，不是微软雅黑：
     雅黑不可再分发/嵌入；OFL 允许子集化嵌入。源字体约 8.3MB，**不入库**（可再取），
     只提交生成物 `assets/ui_font_subset.otf`。
  2. **字符集四项并集**（`assets/make_font_subset.py`）：
     ① 源码（**去注释后**）里出现的每一个非 ASCII 字符；② ASCII 可见区；
     ③ GB2312 一级字表 3755 常用字（由 Python 的 `gb2312` 编解码器离线枚举，不依赖外部字表）；
     ④ 常用标点/符号区段（拉丁补充、通用标点、箭头、数学、圈号、几何、CJK 标点、全角形式）。
     去注释是必要的：第一版把注释里的 `☰` 计入硬约束，而源字体没有该字形，导致误报缺字。
  3. **"界面自述文字不依赖系统字体"变成可程序判定的证据**：
     `assets/check_font_coverage.py` 读子集 cmap，断言"源码非 ASCII 字符集 ⊆ 子集"与
     "GB2312 一级字表 ⊆ 子集"，接入 `tests/run_tests.ps1`（退出码参与总判定）。
     这样"缺字显示豆腐块"这类问题在**提交前**就会被拦住，而不是等肉眼发现。
  4. **内嵌方式用 `.rc` 的 RCDATA**，不用 `#embed`：① 不要求 `/std:c++latest`；
     ② 资源在进程生命周期内始终映射，配合 `FontDataOwnedByAtlas=false` 正合
     ImGui 1.92+ "字体数据须全程有效"的要求，零拷贝、零释放。
  5. **装载器换 FreeType**（`io.Fonts->SetFontLoader(ImGuiFreeType::GetFontLoader())`）：
     内置 stb_truetype 只支持 TrueType，而子集是 CFF/OTF；且小字号 CJK 的栅格化质量明显更好。
     用运行时选择而不是在 `imconfig.h` 里 `#define IMGUI_ENABLE_FREETYPE` —— 不改第三方文件。
     freetype 本身**已经是 libmupdf 的传递依赖**（vcpkg 已装、`VcpkgAutoLink` 自动链接），
     所以没有新增任何外部依赖，只是把 `misc/freetype/imgui_freetype.cpp` 加进构建。
  6. **生僻字 fallback**：把系统 `msyh.ttc` 以 `MergeMode` 合并进同一 ImFont，只兜子集没有的字形
     （文件名、PDF 目录标题可能含生僻字）。合并顺序即优先级，常规字仍走内嵌子集；
     系统缺该字体时 ImGui 静默跳过，界面自述文字不受影响。
     字形**按需栅格化**（DX11 后端声明了 `RendererHasTextures`，走动态图集），故 ranges 传 `nullptr`
     不会预烘整本字库。
- **理由**：用"源码字符集"而不是"猜一个常用字表"来定硬约束，是因为前者可以被自动断言、
  且直接对应"界面会不会出现豆腐块"这个真实风险；后者只能靠体感。
- **代价**：exe +1.06MB（见体积预算）；UI 字体观感与微软雅黑不同（主观项，入人工清单）；
  新增两个脚本与一条测试项；`assets/ui_font_subset.otf` 入库（1.04MB 二进制）。
- **后果**：界面观感固定、不再依赖系统字体；图标度量不受影响（两个字体的归一化 ascent 几乎相同：
  雅黑 2167/2703 = 0.8017 em、Noto Sans SC 1160/1448 = 0.8011 em，故 ADR-045 的
  `kIconGlyphOffsetY = 4` 无需调整）。

## ADR-049 三段外壳改为显式布局：状态栏被子窗口间距挤出窗口底部（2026-10-06，第六阶段人工验证）

- **背景**：人工验证反馈"下方的字太靠近边缘，不舒服"。逐像素量取后定位为**布局溢出**（非配色/
  内边距问题）：顶栏/画布/状态栏是 `##shell` 内的三个同级子窗口，`EndChild()` 会在相邻子窗口
  之间插入一份 `ItemSpacing.y`，三段高度之和因此比客户区多出一个间距，状态栏被推出窗口底部。
  （量取数据与根因细节见 [归档](archive/2026-10/ADR-过程记录归档.md#adr-049)。）
- **决策**：
  1. **三段改为显式定位 + 显式高度**：`draw_shell` 自己算 `top_h / body_h / status_h` 并用
     `SetCursorPosY` 落位，画布/侧栏的高度由调用方传入；**中间不留缝**，三段恰好铺满客户区。
     不再依赖 ImGui 的"相邻项自动间距"。
  2. **状态栏高度 30 → 34（基准像素）**：ImGui 的 `GetTextLineHeight()` 只是名义行高（= 字号），
     而 CJK 字体的实际墨迹盒（ascent+descent）≈ 1.32 em —— 20px 基准字号下约 26px 墨迹。
     30 的条高只剩 1~2px 气口，34 则上下各留约 4px。**这个常量必须按墨迹盒而不是行高来定**。
  3. **顶栏高度为 0 时不创建子窗口**：`BeginChild` 把 `size.y == 0` 当作"自动高度"，会吃掉整个
     客户区；这条陷阱写在 `update_top_bar_height` 的注释里，避免后来者重踩。
- **理由**：显式布局把"三段几何"变成一眼可读的算术（`body_h = client_h − top_h − status_h`），
  并且顺带让顶栏的滑出动效（ADR-047 第 6 条）成为可能 —— 隐式堆叠下高度归零会留下一条间距缝。
- **代价**：`draw_top_bar / draw_canvas_area / draw_sidebar` 的签名各多一个高度参数；
  新增分区时必须自己在 `draw_shell` 里让位。
- **后果**：状态栏文字上下留白均衡（实测墨迹上下各约 10px @110% 缩放），
  "文字贴边/被裁"这一整类问题（含未来加高状态栏）从机制上消失。

## ADR-050 自绘滚动条改为可拖拽：几何与命中测试同源（2026-10-06，第六阶段人工验证）

- **背景**：人工验证反馈"右侧滚动条无法拖动，实际会触发页面拖动"。根因清楚：
  那条"滚动条"是 `draw_scroll_indicator` **纯装饰性**绘制（没有命中区），而画布左键拖拽 = 平移，
  于是按住它拖动自然就变成了拖页面。这是"只画不响应"的必然结果。
- **决策**：
  1. 抽出 `scroll_bar_geom(origin, size) -> ScrollBarGeom{active, track, thumb, travel}`，
     **绘制与命中测试共用同一份几何**（早期两处各算一次是这类缺陷的温床）。
  2. 交互（`update_scroll_bar`）：按住滑块 → 保持抓取点拖动；按轨道空白 → 滑块中心跳到该处并
     转为拖拽（系统滚动条的习惯）；拖拽中鼠标移出轨道仍继续跟随；释放即结束。
     拖拽是**直接定位**，故同时清掉平滑滚动尾巴（避免"松手后还在飘"）。
  3. **命中区比可见滑块宽**（12px vs 5px，悬停/拖拽时滑块加宽到 7px 作反馈）：
     细滑块好看但 4px 宽的目标很难按中。
  4. **拖拽期间抑制画布平移**（`g_scroll_drag` 门，在 `handle_canvas_input` 里判断），
     并且滚动条交互**先于**画布的失败占位点击测试，避免一次点击被两处消费。
  5. 浮现/渐隐沿用原有节奏（滚动中/悬停/拖拽全显，静止后渐隐），由 `[ui] Motion` 开关。
- **理由**：自研画布是 `NoScrollbar`（滚动反馈自己画），那就必须自己补齐滚动条的**输入**部分；
  把几何抽成纯函数是本项目"布局是纯函数"的同一思路在交互上的延伸。
- **代价**：右侧 12px 宽的一条区域不再能触发画布平移（与系统滚动条行为一致）；
  滚动条几何每帧算两次（命中一次、绘制一次），成本可忽略。
- **后果**：拖拽滚动条、点轨道跳转、悬停高亮均可用；F3 浮层的 `bar drag` 读数可直接确认
  "拖动时确实进入了滚动条拖拽态"。主观手感验收列入人工清单（`04-人工验证.md` 7-4）。

## ADR-051 文件类型图标：完整帧集 + 按尺寸分级原生绘制（2026-10-06，Phase 7 发布打包）

- **背景**：人工验证反馈"Explorer 里的文件图标发糊、外围一圈灰边"。**先取原始数据再推理**：
  解析 `installer/icons/*.ico` 目录结构，发现每个文件**只有 1 帧，且是 16×16**，Explorer 拿到
  48px 槽位时只能放大，故模糊且灰边被拉粗。（调查过程见
  [归档](archive/2026-10/ADR-过程记录归档.md#adr-051)。）
- **决策**：
  1. **保存时以最大帧为基准图**。Pillow 的 `IcoImagePlugin._save` 对"目标尺寸 > 基准图尺寸"的
     槽位直接 `continue`；原脚本把 16px 帧当基准图，于是 20/24/…/256 全被跳过，只写出 16×16
     一帧。以 256 为基准 + `append_images`，Pillow 才能为每个槽位取到尺寸精确匹配的原生帧。
  2. **帧集覆盖非整数缩放率**：16/20/24/28/32/36/40/48/56/64/72/80/96/128/160/192/256
     （125% 要 20px、150% 要 24px、175% 要 28px……缺帧就会被拉伸）。
  3. **超采样原生绘制**：每个尺寸在 T×SS 的画布上按比例作画、再 LANCZOS 降到 T×T。
     PIL 的 `ImageDraw` 不做抗锯齿，直接按目标尺寸画会锯齿；而"画 256 再缩到 16"会把细节糊成
     一团。超采样 + 按尺寸分级简化，两头都避开。
  4. **按尺寸分级**：≤28 不放幽灵、不写色带文字、轮廓更浅更细（16px 下 1px 线已占图标宽 6%，
     深灰会缩成一圈"脏灰圈"）；32~64 加幽灵与格式缩写；≥72 再加投影、纸面渐变、色带渐变/高光。
  5. **所有绘制统一裁到纸面轮廓**：纸面是"整块画布"填白/填渐变，色带也是整条矩形，
     两者不裁就会出两种事故 —— 色带在底部两角溢出纸面（人工反馈的"色块填充溢出"），
     以及整张图标带**不透明白底**（人工反馈的"Explorer 选中时露白底"）。
     绘制末尾统一 `putalpha(multiply(alpha, page_mask))` 裁到轮廓；裁掉的是"纸以外"的部分，
     纸面本身仍为实心（**不要把图标做成空心**）。
  6. **自动化断言**：`assets/check_icons.py` 断言每个 `.ico` 的帧集、**每帧位图的真实解码尺寸**
     （防"小图塞进大槽位"）、帧非全透明、**四角透明**（防"选中露白底"回归），
     接入 `tests/run_tests.ps1`（当前 824 项）。
- **理由**：帧集不全与"小图塞进大槽位"是 ICO 最容易出的两类错，且**只在特定 DPI 下才暴露**，
  看截图不一定看得出；解析 ICO 目录来断言比肉眼看可靠。
- **代价**：单个 `.ico` 从 330 字节涨到约 40KB（17 帧），7 个格式合计约 280KB，安装包随之增大。
- **后果**：Explorer / 任务栏在 100~200% 缩放下都能命中尺寸精确的帧，小尺寸不再有灰圈。
  主观观感验收列入[人工验证](04-人工验证.md)。

## ADR-052 安装器改为每用户安装：数据可写与 HKCU 关联 hive（2026-10-06，Phase 7 发布打包）

- **背景**：原脚本 `DefaultDirName={autopf}\Lilith Reader` 且默认管理员安装，即装到
  `C:\Program Files\Lilith Reader`。但程序把 `LilithReader.ini` 与 `reader_state.bin` 写在
  **exe 同目录**（ADR-034 与[架构设计 §5](02-架构设计.md)）：x64 进程没有 UAC 文件虚拟化，
  普通权限对 Program Files 的写入会失败，而两处写入路径都不检查返回值
  （`WritePrivateProfileStringW` / `CreateFileW` 的结果被丢弃）——结果是**设置与阅读进度静默不落盘**。
  另外关联按官方推荐写 HKCU，而提权安装时 HKCU 指向管理员账户，关联会写到错的用户下。
- **决策**：`PrivilegesRequired=lowest`，不再提供"为所有用户安装"
  （去掉 `PrivilegesRequiredOverridesAllowed`），安装到 `%LOCALAPPDATA%\Programs\Lilith Reader`。
- **理由**：程序的数据模型（exe 同目录、便携）决定它必须装在**当前用户可写**的目录；
  关联写 HKCU 也要求不处于提权上下文。两条约束都指向"每用户安装"，而不是在别处打补丁。
- **代价**：不再支持"一台机器装一次、所有用户共用"；多用户机器需各自安装。
- **后果**：设置与阅读进度可正常落盘；关联写在正确的用户 hive 下。对**旧版曾按管理员装到
  Program Files** 的机器：检测到旧目录不可写时回落到每用户目录，并明确告知旧目录不会自动删除
  （刻意不做"静默调用旧卸载器"——见 ADR-053）。

## ADR-053 升级就地覆盖，卸载的数据询问收敛为一次（2026-10-06，Phase 7 发布打包）

- **背景**：人工验证反馈"已安装时打开安装程序，先说可以保留数据，随后卸载环节又机械性弹出
  是否保留数据；也不会自动定位到原来的位置"。根因：原脚本在 `InitializeSetup` 里
  "检测到旧版 → `MsgBox` 询问 → 静默执行旧卸载器"，而旧卸载器的 `CurUninstallStepChanged`
  自己还有一个"是否删除阅读数据"弹窗 —— 同一次操作里问了两次；旧卸载器同时删掉了卸载注册表项，
  Inno 随后读不到 `InstallLocation`，自然无法沿用原安装目录。
- **决策**：
  1. **删掉"先卸载旧版"整段逻辑**：同 AppId 下 Inno 原生支持就地覆盖升级，配合
     `UsePreviousAppDir / UsePreviousTasks` 沿用上次的目录与任务勾选。
  2. **升级检测改为只读**：`InitializeSetup` 只读 `DisplayVersion` / `InstallLocation` 与上次的
     `Bindings`，用于欢迎页文案与勾选回填，不再触发任何卸载动作。
  3. **自动定位安装目录**：旧目录可写则直接沿用；不可写（旧版装在 Program Files）才回落到
     每用户默认目录并说明原因。
  4. **卸载数据询问只出现一次**：仅在数据文件确实存在、且非静默卸载时，用 `TaskDialogMsgBox`
     给出明确按钮（"保留阅读数据（推荐）"/"一并删除"），默认保留；静默卸载一律保留，绝不误删。
  5. **运行中检测改回标准机制**：删掉"改名试探文件占用"的偏方，交给 `CloseApplications`
     （Windows 重启管理器）。
- **理由**：升级与卸载是两条不同路径，不该互相穿插；"数据去留"是**卸载**的语义，不该在升级
  流程里出现。用平台原生机制（AppId + 重启管理器）替代自写试探，才是"像真正的安装程序"的实质。
- **代价**：从旧版（管理员安装到 Program Files）迁移时，旧目录与旧的卸载登记项会残留，
  需用户手动清理（脚本已明确告知）。
- **后果**：升级不再弹两次、不再丢目录记忆；卸载只在真的有数据时问一次。交互流程验收列入
  [人工验证](04-人工验证.md)。

## ADR-054 输入映射收敛为命令表 + 按键自定义（2026-10-06，交互优化）

- **背景**：快捷键此前散落在 `handle_canvas_input` / `draw_shell` 里，一条命令一处
  `ImGui::IsKeyPressed`，改键无从谈起；"快捷键与帮助"窗口列的是**写死的字符串**，与实现
  天然会漂移。用户提出"用键位设定界面替代帮助界面，或并入设置分栏"。
- **决策**：
  1. **单一命令表**：`Cmd` 枚举 + `kCmds[]`（id / 分组 / 显示名 / 是否连发 / 是否全局 / 两个默认键槽）；
     生效键存在 `g_binds[Cmd][2]`。派发只有 `cmd_pressed(Cmd)` 一条路径。
  2. **两个键槽**：数字/算术类给主键盘+小键盘两槽，落实 ADR-027"两套都判"，不再写别名分支。
  3. **Esc 语义变更**：不再是"关文档→退出"的级联键（阅读中误触代价过大），改作**可绑定键**
     （默认与 `F11` 同为全屏）；"关闭当前对话框"是**固定**行为，不进命令表。
  4. **改键界面**：设置窗口新增「按键」分栏，删除「快捷键与帮助」窗口；`F1` 打开该分栏，
     `Ctrl+,` 打开设置。菜单里的快捷键文案取当前绑定（`menu_item_cmd`）。
  5. **持久化**：ini 新增 `[keys]` 节，值形如 `Ctrl+O|F11`，键名取 `ImGui::GetKeyName` 原文（ASCII）。
- **理由**：显示文案与 id 分离，改文案不动配置；帮助窗口是"第二份真相"，必然与实现漂移，
  而可改键的界面天然是"唯一真相"。
- **代价**：`kCmds` 的 id 成为**持久化契约**，一旦发布不得改名（改了用户配置即失效）。
- **后果**：新增/调整命令只动一处；帮助窗口下线，其"支持格式"等参考信息并入按键分栏与引导页。

## ADR-055 动效补齐：侧栏滑入/滑出 + 窗口开合（2026-10-06，交互优化）

- **背景**：Phase 6 的动效只覆盖了缩放/滚动/跳页/顶栏，人工验证指出"侧边菜单的弹出、
  设置窗口的打开关闭"没有动效。
- **决策**：
  1. **侧栏**：宽度做一阶滞后插值（`kSidebarAnimRate`），与顶栏同一手法。**内容仍按整宽排布、
     整体左移**，只是被裁剪 —— 若让内容按动画宽度重排，文字会逐帧跳行。
  2. **设置窗口**：用 alpha 一阶趋近做开合（本 ADR 初版为"整窗淡入淡出"）。
- **理由**：一阶滞后无过冲、必然收敛、帧率无关，且连续触发时自然叠加（与 ADR-047 一致）。
- **代价**：侧栏动画期间面板宽度小于整宽，右侧内容被裁 —— 视觉上等价于"滑出"。
- **后果**：动效覆盖到侧栏与设置窗口；窗口部分的开合方式在 ADR-056 中被取代。

## ADR-056 设置窗口开合改为缩放 + 淡入淡出（取代 ADR-055 的窗口部分）（2026-10-06，交互优化）

- **背景**：ADR-055 的"整窗淡入淡出"实测体感怪异 —— 关闭时窗口**原地保持原尺寸**、内容逐渐
  透明，既不像常见窗口动画，又留一个半透明大窗继续占着画面。用户明确反馈"逐渐消失的模式，
  很少有窗口动画是这样的"，并选定"缩放+淡入淡出（开合对称）"。
- **决策**：以窗口**中心**为不动点，尺寸 `96% ↔ 100%`（`kWindowScaleFrom`）与整体透明度
  `0 ↔ 1` 同步插值；关闭时**边缩边淡**。窗口加 `NoResize`（尺寸由动画驱动），位置在动画中
  强制、静止后交还 ImGui（仍可拖动）；用户拖动后的位置每帧实测记入 `g_settings_rest_pos`，
  下次开合即以该位置为中心缩放（不会"跳回屏幕中央"）。
- **理由**：现代桌面对话框（Win11/macOS）的通行观感就是"轻微放大 + 淡入"，关闭则收缩退场；
  对称开合读起来是"弹出来/收回去"，而不是"幽灵化"。
- **代价**：设置窗口不可调整大小（布局按固定宽度设计，正文可滚动，无功能损失）。
- **后果**：窗口开合观感符合常见桌面软件；跳页/密码两个**模态弹窗**仍为即时出现/消失
  （它们是 `AlwaysAutoResize` 的输入框，缩放会与自动尺寸互斥，且模态关闭语义不宜延迟）。

## ADR-057 swapchain 重建延到帧首（2026-10-06，交互优化）

- **背景**：全屏切换时出现"非常快的单帧闪烁"。根因：`WM_SIZE` 在 `SetWindowPos` /
  `SetWindowPlacement` 过程中**同步**到达，而全屏切换发生在命令派发时（ImGui 一帧中途）；
  原实现当场 `ResizeBuffers`，于是**本帧按旧尺寸排布的绘制数据被画进新尺寸的后备缓冲**，
  呈现为一帧拉伸/闪烁。
- **决策**：`WM_SIZE` 只记录 `g_resize_pending` / 目标尺寸，**不**动 swapchain；
  由主循环在**帧首**（`new_frame` 之前）统一 `g_gfx.resize()`。`Graphics::resize` 另加
  "尺寸未变即跳过"，并跟踪 `cur_w/cur_h`。
- **理由**：帧首重建保证"ImGui 视口尺寸 == 后备缓冲尺寸"在**同一帧内**成立；多次 `WM_SIZE`
  自然合并为一次重建，代价更低。
- **代价**：resize 延迟不超过一帧（< 16ms），肉眼不可见；窗口尺寸与画面同步性反而更好。
- **后果**：拖动窗口边缘改尺寸、DPI 变更、全屏切换都不再出现单帧拉伸。

## ADR-058 全屏退出：先提交样式再落位（2026-10-06，交互优化）

- **背景**：`Esc`（默认绑定全屏）退出全屏时窗口"变了又归位"。原实现为
  `SetWindowPlacement()` → 再补 `SetWindowPos(SWP_FRAMECHANGED)`：前者用**尚未生效的
  `WS_POPUP`（无边框）度量**摆放窗口，后者重算非客户区、把窗口**再挪一次**。
- **决策**：退出改为**先提交新样式**（`SetWindowPos(..., SWP_NOMOVE|SWP_NOSIZE|SWP_FRAMECHANGED)`，
  仍在全屏矩形上、几何不动）**再 `SetWindowPlacement` 落位** —— 几何只变一次。
  进入全屏同样收敛为单次 `SetWindowPos(FRAMECHANGED)`。
- **理由**：窗口的可见几何变化只应发生一次；把"帧重算"排在"落位"之前，重算就不会再产生位移。
  落位仍用 `SetWindowPlacement`（而非手工 `SetWindowPos` + `rcNormalPosition`）是因为后者是
  **工作区坐标**，多显示器下会偏。
- **代价**：进入/退出各多一次同步的帧重算调用（无可见中间态，因为同一消息处理内不重绘）。
- **后果**：全屏进出干净；与 ADR-057 配合，闪烁问题闭环。验收列入 [人工验证](04-人工验证.md) §9。
- **勘误（2026-10-06，人工反馈后）**：仅调整调用顺序**不够**。实测仍有"非最大化退出全屏闪一下、
  最大化退出全屏往左上缩一下再归位"。真正的原因在**执行时机**而非顺序：命令派发发生在
  `new_frame()` **之后**，此时改窗口几何，本帧的 ImGui 绘制数据仍是按**旧尺寸**排布的，
  会被 DWM 拉伸到新窗口矩形上 —— 几何变化越大（全屏 ↔ 最大化）越明显。
  已改为**帧间执行**（`g_request_fullscreen_toggle`，与"打开文档对话框"同一手法），
  见 ADR-060。本 ADR 的"先提交样式再落位"顺序仍然保留。

## ADR-059 弹出对话框的开合动效：淡入淡出 + 滑落（2026-10-06，交互优化）

- **背景**：ADR-056 只覆盖了设置窗口，跳页 / 密码两个模态弹窗仍是"啪"地出现与消失，
  动效覆盖不一致（人工反馈点名）。
- **决策**：
  1. 抽 `PopupAnim`（进度 t：0 = 可销毁，1 = 静止）驱动**透明度**与**滑落位移**
     （未收敛时整体下移 `kPopupSlidePx`，以视口中心为 pivot）。
  2. **延迟关闭**：逻辑关闭（`g_open_jump` / `g_open_password` 置 false）只把目标进度降到 0，
     等收敛后才真正 `CloseCurrentPopup` —— ImGui 的 popup 关闭是立即销毁的，不这样做则
     关闭路径没有任何动画可言。
  3. 淡出期间禁用弹窗内交互，避免重复触发（跳页重复跳转 / 密码重复提交）。
- **理由**：这两个弹窗是 `AlwaysAutoResize` 的输入框，**不做缩放** —— 缩小外框会让内部控件
  （页码输入框等固定宽度控件）被窗口裁剪，观感损失大于收益。淡入淡出 + 滑落既与设置窗口
  同一"开合对称"语感，又不会裁剪内容。
- **代价**：`AlwaysAutoResize` 弹窗无法得到与设置窗口完全一致的缩放观感（这是刻意的取舍）。
- **后果**：跳页 / 密码弹窗开合有了动效；`[ui] Motion` 关闭时直切。
  **未纳入动效**（刻意）：主菜单 / 右键菜单（ImGui 原生即时弹出，桌面惯例是菜单不播动画，
  加了反而显得迟钝）、调试浮层（F3 诊断 HUD，需要即按即见）。

## ADR-060 全屏切换改到帧间执行（2026-10-06，交互优化）

- **背景**：ADR-058 只调整了 Win32 调用顺序，实测仍有闪烁。根因是**执行时机**：
  `handle_global_commands` 在 `draw_shell` 内、即 `ImGui::NewFrame()` **之后**运行；
  此刻改窗口几何，本帧的 ImGui 绘制数据（视口尺寸、布局）仍是旧尺寸的，
  被 DWM 拉伸到新窗口矩形上 —— 全屏 ↔ 最大化这类大几何变化尤其刺眼。
- **决策**：命令只置 `g_request_fullscreen_toggle`，由主循环在**帧首**执行（排在"应用待处理
  窗口尺寸"之前），使"几何变更 → swapchain 重建 → ImGui 视口"三者在**同一帧内**一致。
  与"打开文档对话框放到帧与帧之间"（ADR-046 的既有手法）同一模式。
- **理由**：窗口几何是**帧级**状态，任何会改变它的操作都必须在帧边界完成；在帧中途改，
  这一帧就已经"不一致"了，无论怎么调顺序都救不回来。
- **代价**：全屏切换延迟至多一帧（< 16ms），无感。
- **后果**：普通（非最大化）窗口进出全屏的闪烁已消除。**但"最大化状态下退出全屏"仍有一次可见抖动**
  （窗口先向左上收缩再归位）—— 实测未解决，**暂列为已知缺陷**（记入根 README「已知问题」）。
  剩余疑点是 `SetWindowPlacement(SW_SHOWMAXIMIZED)` 内部的"先落 `rcNormalPosition` 再最大化"，
  属 Win32 单次调用的内部中间态，本 ADR 的"帧首执行"纪律管不到它。
  与 ADR-057（swapchain 重建延到帧首）是同一条纪律的两个面：**一切改变帧级几何的操作都在帧首做**。

## ADR-061 开合动画改定时缓出补间；最小化期间不渲染（2026-10-06，交互优化）

- **背景**：两条人工反馈 —— ① 设置窗口 / 弹窗的开合"再利落一点"；② **最小化窗口的过程会闪一下**。
- **决策**：
  1. **开合动画改为一**次性定时补间（`kOpenCloseDur = 160ms` + `ease_out_cubic`，`ToggleAnim`），
     替换原先的一阶滞后。**这是对 ADR-047 的局部例外**：ADR-047 用一阶滞后是因为滚动/缩放由
     **连续输入**驱动（补间需要反复重排时间轴）；而开合是**单向、有明确终点**的一次性过渡，
     定时补间反而更合适 —— 时长确定、末端干脆，没有"收敛到 99% 之后还拖一个时间常数"的长尾。
  2. **弹窗关闭闪烁修复**：动画收敛那一帧此前**没有**套用 alpha 样式，于是会以默认不透明度
     多画一帧再销毁 —— 即"关闭时闪一下"。改为**始终**套用动画样式（收敛帧 value 已是 0，
     全透明后再 `CloseCurrentPopup`）。
  3. **最小化期间整帧不渲染**：`WM_SIZE(SIZE_MINIMIZED)` 置 `g_minimized`，主循环在帧首
     `Sleep(10); continue;`（与 ImGui 官方 DX11 示例的 occluded 处理同一手法）。原因：最小化后
     客户区为 0，ImGui 在 0 尺寸视口下什么都画不出，整帧只剩**清屏色**，在收起动画里就是一闪。
     顺带省掉最小化期间的 CPU/GPU。
- **理由**：动画的"手感"由**时长与加速度曲线**决定，而不是由"用哪种插值"决定；开合这种
  一次性过渡应当有明确终点。最小化不渲染则是"窗口不可见时不该产生可见帧"的直接推论。
- **代价**：`kOpenCloseDur` 是固定时长，高刷屏与 60Hz 屏观感一致（这正是一致性的来源）；
  最小化期间若恰有 `g_request_*` 挂起，会延迟到恢复后再执行（无实际影响）。
- **后果**：开合更利落、关闭不再闪；最小化/恢复无闪烁。滚动/缩放/顶栏/侧栏仍用一阶滞后（ADR-047 不变）。

## ADR-062 阅读数据的身份：主键改内容指纹，路径键降为迁移/兜底；智能匹配三态（2026-10-06，阅读数据）

- **背景**：ADR-034 的主键是「路径 + 大小 + 修改时间」哈希，其代价被明确记为"可接受"：
  文件改名/移动后阅读位置丢失。实际后果比记录的更宽 —— 只要**修改时间**变了（重新下载、
  解压、备份还原、git checkout），即使路径一字未改也会丢；且用户完全不知道为什么丢。
  另一头，用户要求"移动文件后能接着读"，同时又不放心程序自作主张共用数据。
- **决策**：
  1. **主键 = 内容指纹**（`lr::file_fingerprint`）：头 128KB + 中间 64KB + 尾 128KB 的
     **稀疏采样**（≤320KB）叠上文件大小，FNV-1a 64（与既有文档键同一套哈希，不引新依赖）。
     开销与文件大小**无关**。PDF 的头（版本/元数据）与尾（xref、对象表）恰是最能区分两份
     文档的区域，中段补一刀防"头尾相同正文不同"的构造性碰撞。
  2. **指纹由工作线程计算**（`render` 的 `do_open`，随 `DocState::file_fingerprint` 发布）：
     UI 线程**不读文件内容**（ADR-009 已把"元数据调用"列为有界例外，读内容不在其内）。
     加密文档打开失败在 NeedsPassword 时也要留着指纹，供随后 authenticate 成功那次发布。
  3. **路径键降为兜底与迁移**：`document_key`（路径+大小+修改时间）仍算，存进记录的
     `path_key`；定位顺序为 内容指纹 → 路径键（`locate`）。命中即 `adopt`：把记录改挂到
     指纹主键下、刷新 `last_path` / `page_count` —— 从此换位置也能一次命中。
  4. **页数是继承的硬门槛**：记录里存 `page_count`，页数对不上就不继承（书签是页号，
     页数变了必然错位）。读不出来（0）视为未知、照常继承。
  5. **智能匹配三态**（ini `[reading] SmartMatch`，默认 1 询问）：关 = 只认路径（旧行为）；
     询问 = 命中指纹但换了位置时弹确认框；自动 = 静默沿用。**命中时先沿用再问**
     —— 绝不因为询问流程而丢进度；次按钮「从头开始」= 清掉阅读位置与书签（视图参数保留）。
  6. **格式升 v2**（magic `LRS2`）：记录增 `path_key` / `page_count` / `last_path`（UTF-8）。
     v1（`LRS1`）仍可解码并迁移：其 key 就是路径键 → 填进 `path_key`。
- **理由**：身份应当跟着**内容**走而不是跟着**位置**走 —— "我读到第 42 页"说的是这本书，
  不是这个路径。而"要不要共用"是**信任问题**不是识别问题，故交给三态开关而不是二选一。
  先沿用再询问，让"用户没理会弹窗/直接关掉"这一最常见分支落在**不丢数据**的一侧。
- **代价**：① 每次打开多一次 ≤320KB 的采样读（工作线程，与渲染抢一点 I/O）；
  ② 采样指纹把"头尾与中段采样区完全相同"的两份文档视为同一份（概率极低，且后果只是
  共用一条阅读记录）；③ **升级前就已经移动过的旧记录找不回来** —— v1 记录里没有路径也
  没有指纹，无从比对；未移动的旧记录在第一次打开时经路径键命中并完成迁移；
  ④ 内容被改动（哪怕只改一字节）的文档视为新文档，进度不继承 —— 这是刻意的。
- **后果**：`reader_state.bin` 升 v2（v1 仍可读）；新增 `src/utils` 的 `file_fingerprint`、
  `reader_state` 的 `DocIdentity/locate/adopt/primary_key`；`app` 层新增身份解析与确认弹窗。
  自动化：`reader_state_test` 增 v2 往返 / v1 迁移 / 分层定位 / 指纹不变性断言（共 80 例）。
- **后续（2026-10-06 同日）**：`last_path` 是单值，表达不了"一份数据、若干路径"，已由
  **ADR-065** 改为 `locations` 位置列表（格式升 v3）；次按钮「从头开始」的语义改为
  「另起一份」（拆记录，而不是清页码）。本文中"刷新 last_path""格式 v2"等描述以 ADR-065 为准。

## ADR-063 阅读数据可管理：清单窗口 + 通用确认弹窗（2026-10-06，阅读数据）

- **背景**：阅读数据此前只能"攒着"：文件删了、换机器了、不想留痕迹了都没有清理入口，
  `reader_state.bin` 会一直增长（上限 4096 条）。
- **决策**：
  1. **阅读数据管理窗口**（设置 → 阅读 → 「管理…」）：列出全部记录（文件名 / 位置 /
     第几页共几页 / 书签数），逐条 `×` 删除 + 底部「清空全部」。
  2. **确认弹窗一处实现、多处复用**：`request_confirm(kind, …)` + `draw_confirm_popup()`，
     承载 ① 智能匹配询问（主「沿用进度」/ 次「从头开始」，ADR-062）② 删除单条 / 清空全部
     的二次确认（主「删除/清空」/ 次「取消」）。与跳页、密码弹窗同一套开合动效（ADR-059）。
  3. **删除正在阅读的那条**：从库里移除并**解除本次会话的绑定**（`g_doc_key = 0`），
     即本次不再写入；下次打开按新文档重建记录。不做"删掉又立刻重写一条"的假删除。
- **理由**：确认弹窗的语义结构（标题 / 正文 / 两个动作按钮）在三处完全一致，各写一份
  必然漂移；复用一份，动效与 Esc 行为也一并统一。
- **代价**：Esc 在确认弹窗上只按"取消/沿用"处理 —— 对智能匹配询问来说就是保持已沿用的
  状态，不给 Esc 替用户做"从头开始"这种不可逆决定。
- **后果**：`ui.cpp` 增管理窗口与确认弹窗；`session.cpp` 增 `clear_reading_data` /
  `clear_all_reading_data` / `reset_current_progress`。
- **勘误（2026-10-06 同日）**：管理界面最初做成**独立浮动窗口**，实测它在界面上根本看不到
  （被先绘制的设置窗口整块盖住，且 z 序未处理），表现为"点了没反应"。改为**设置窗口的第 5 个
  分栏**（界面 / 阅读 / 性能 / 按键 / 阅读数据），「阅读」分栏的「管理…」按钮改为切到该分栏
  （`g_settings_open_tab = 4`），原独立窗口与 `g_show_reading_data` 一并删除。**教训**：一个界面
  "打开"另一个界面时，后者要么是前者的一部分，要么必须显式置顶；另开浮动窗口而不处理 z 序，
  等于没做。（实测定位细节见 [归档](archive/2026-10/ADR-过程记录归档.md#adr-063)。）
- **后续（2026-10-06 同日）**：该分栏的清单形态与按钮观感按人工反馈重做为**卡片式**
  （路径树 + 无底色危险色按钮 + "位置未知"记录分区），见 **ADR-065**；管理窗口本身
  "是设置窗口的一个分栏"这一结论不变。

## ADR-064 弹窗关闭路径的致命缺陷：透明度归零使 Begin 返回 false、模态永久残留（2026-10-06，阅读数据）

- **背景**：阅读数据功能首轮人工实测报告"选完之后**直接页面卡死，无法进行任何操作**"，
  同时确认弹窗"没有版式、很丑"。根因：弹窗关闭动画把收敛帧的 `style.Alpha` 推成 0，
  ImGui 的 `Begin()` 据此把窗口判为 Hidden 并返回 false，于是"收敛后再 `CloseCurrentPopup()`"
  永远执行不到，模态作为**永久残留**挡住整个窗口的全部输入。（headless 探针定位过程与根因
  链条见 [归档](archive/2026-10/ADR-过程记录归档.md#adr-064)。）
- **决策**：
  1. `popup_anim_apply` 里把**要套用的透明度留一个下限** `kPopupMinAlpha = 1/255`：
     收敛帧仍是"真实帧"，关闭逻辑得以执行。跳页 / 密码 / 确认三个弹窗共用该函数，一并修好。
  2. 确认弹窗版式改为**自绘**（`NoTitleBar` + 自绘标题/说明/明细行/右对齐按钮）：原先直接暴露
     ImGui 的标题栏（显示内部名"确认"）与一整块未排版的长文本，观感差且长路径把窗口撑变形。
  3. 记下**不变量**：**弹窗开合透明度不得为 0**（0 意味着"这一帧窗口被判 Hidden"）。
- **理由**：不去碰 ImGui 内部状态（备选方案是用 `imgui_internal.h` 的 `ClosePopupToLevel` 强制清栈，
  需引入内部头且治标不治本）；本修法改动最小、观感无损，且顺手修好另外两个弹窗的同一隐患。
- **代价**：收敛帧会多画一帧几乎不可见的窗口（无观感差异）。`IsPopupOpen` 仍是关闭判据的
  一部分，故"弹窗被其他原因裁剪导致 Begin 返回 false"这一类极端情形只能靠不变量规避。
- **后果**：`ui.cpp` 的 `popup_anim_apply` 加下限常量；确认弹窗改自绘版式，
  `request_confirm` 增加"明细行"参数（标签 + 值）以便长路径单独折行；
  人工验证清单新增 10-1（版式 + 关闭后不卡死）作为回归项。
- **自动化现状**：本轮用一次性 headless 探针定位（复刻弹窗逻辑 + ImGui 四文件链接，
  约 100 行即可重做，探针本身不入库）；长期防线可将"关闭弹窗后弹窗栈必须为空"做成
  headless 用例，尚未建立。

## ADR-065 阅读数据：一条记录 = 若干位置（列表）；管理分栏改卡片式（2026-10-06，阅读数据）

- **背景**：第二轮人工实测反馈（原文）："你这个排版不对啊，太丑了，而且也表达不出来某个文件
  下面有若干路径的视觉感受，按钮也很丑，而且其他内容甚至直接未知"，并附图。截图里 10 条记录
  有 8 条标题是"（未知文档）"、行尾清一色的灰方块 `×`。
- **查明**：三条各自独立（只有第 1 条是数据缺陷，其余是表达与观感）——① "未知文档"是 v1
  记录迁移后的形态（`key == path_key` 且 `page_count == 0`；v1 的键是"路径 + 大小 + 修改时间"
  的哈希，**路径本身从来没存过**，故永不能还原文档名）；② 一条记录只留最后一个路径（ADR-062 的
  `last_path` 是单值）；③ 行尾删除用了 ImGui 默认按钮（浅色下即灰方块）。（逐条定位细节见
  [归档](archive/2026-10/ADR-过程记录归档.md#adr-065)。）
- **决策**：
  1. `DocRecord.last_path_u8` → **`locations` 位置列表**（UTF-8，最近打开的在前、去重、
     上限 `kMaxLocations = 8`，由 `remember_location` 维护）。`locate` 的 `relocated`
     由"路径 != 记录里那条"改为**"当前位置不在已知位置里"**：同一份书在两处各存一份时，
     在已记过的位置上打开不再重复询问。格式升 **v3（`LRS3`）**；v2 的单路径迁进列表、
     v1 位置留空（不可还原）。
  2. 确认弹窗的次按钮由「从头开始」改为**「另起一份」**，语义改为"拆开记"。
     只把页码清零是**错的**：记录是共享的，清零会把另一处的进度一起抹掉。改为
     `detach_current_progress()`：把当前路径从共享记录里摘掉 → 留下的那份**改挂回它自己的
     路径键**（新增 `ReaderState::rekey`，顺带腾出内容指纹；不腾的话下次打开又会因"内容相同"
     反复询问，成了甩不掉的循环）→ 当前这份新起一条按路径键认的记录，两边互不影响。
  3. 「阅读数据」分栏改**卡片式**：标题行（文档名 + 行尾删除按钮）/ 统计行（第 N / M 页 ·
     K 个书签 · J 个位置）/ 缩进的**路径树**（左侧一条竖导引线把若干位置挂在标题下）。
     **不用 `TreeNode`** —— 那会带三角与整行选中态，而路径是只读信息、不该看起来可点。
  4. 路径**单行中间省略**（头 55% / 尾 45%，按 UTF-8 字符边界二分截断），完整路径给悬停提示；
     折行会让卡片高度参差、长路径的相同前缀堆在一起像糊成一团。
  5. 破坏性动作统一为**"默认无底色、悬停浮出危险色"**的按钮（删除图标 / 「清空全部」/
     「清理这 N 条」），不再用 ImGui 默认灰块；为此新增两个 MDL2 字形（U+E74D 删除、
     U+E8B7 文件夹），仍走启动时的字形校验、缺失即整体退化文字标签。
  6. v1 遗留的"位置未知"记录**单独成区**放在列表末尾，附一句解释（"再次打开那个文件时会
     自动认领"）与「清理这 N 条」（新 `ConfirmKind::PruneUnknown` /
     `clear_unknown_reading_data()`），不再混在主列表里显示成一堆"未知文档"。
  7. 「智能匹配」三态从「阅读」分栏**移到「阅读数据」分栏顶部**，「阅读」栏里那行
     「阅读数据 → 管理…」按钮随之删掉 —— 分栏名与按钮名撞在一起（「阅读」栏里写着
     「阅读数据」），本身就是混乱的一半；而智能匹配决定"要不要跨位置共用同一份数据"，
     与这一栏是同一件事。「阅读」栏从此只管页面间距与配色。
- **理由**：位置列表是"共享阅读数据"这一设定的自然归宿（也正是用户最初提的方案：识别到新路径
  且指纹相同 → 共享同一份阅读数据）。把它做进数据模型、界面只做表达，比在界面上拼字符串更诚实。
  「另起一份」拆记录而不是清页码，守住 ADR-062 定的"绝不因为询问流程丢进度"。
- **代价**：
  - 记录里每条位置最多 1024 字节、最多 8 条，`reader_state.bin` 比 v2 略大（可忽略）。
  - 拆开后的两条**都不再认内容指纹**（只能按路径认），从此各自移动位置会丢进度 ——
    这正是"用户说它们不是同一本书"的应有代价。
  - 已经移动过的 v1 老记录**仍然找不回来**（v1 里既没有路径也没有指纹可比对），
    只能等着被再次打开时按路径键认领，或由用户清理。这一点与 ADR-062 的遗留限制相同。
- **后果**：`reader_state.{ixx,cpp}` 增 `locations` / `remember_location` / `last_location` /
  `has_location` / `rekey`，格式升 v3（v1/v2 均可解码迁移）；`session.cpp` 增
  `detach_current_progress` / `clear_unknown_reading_data` / `unknown_reading_data_count`；
  `ui.cpp` 重写 `draw_settings_reading_data_tab`（卡片 / 路径树 / 危险色按钮 / 未知记录分区）；
  `platform.cpp` 图标校验串补两个字形；`tests/reader_state_test.cpp` 断言 80 → 110 例。
  人工验证项 10-5 按新形态改写。
- **自动化现状**：序列化/迁移/定位/位置记忆全部有断言（110 例）；**版式与观感无自动化覆盖**，
  靠人工验证 10-5。省略算法（UTF-8 边界二分）也只在人工目视范围内。

## ADR-066 输入与观感三处收敛：滚轮缩放修饰键可改 / 按键分栏补不可改操作清单 / 顶栏唤醒源收敛 + 页面淡入改为"眼前就绪才淡入"（2026-10-06，UI 优化）

- **背景**：第三轮体感反馈三条（原文）：①「按键设置界面少了一些操作的介绍，比如按住 ctrl
  然后滚轮可以缩放，这种功能也可以自定义，比如改成按住 alt 之类的，哪怕不适合自定义按键的
  功能，也要在界面列出，不然用户不一定知道」；②「渲染的时候我感觉好像没有页面预加载，
  我按照正常速度浏览，每次到换页的时候都有轻微闪烁，说明是我看到页面的一瞬间才开始加载的」
  ；③「跳转窗口出现和右键菜单出现的时候，上方栏也会跟着出现，可以去掉吗」。
- **查明**：① **不是没有预加载**（自 Phase 4 起就有，ADR-032）；换页闪烁的真实来源是**页面淡入的
  触发条件**——边框/投影先全不透明画出、内容再从 alpha=0 渐显，观感像"看到页面才开始加载"；
  ② 顶栏被唤醒是因为 `top_bar_should_show()` 把**画布右键菜单**也算作"菜单"；③ `Ctrl+滚轮` 的
  修饰键写死为 `io.KeyCtrl`，不在命令表里。（逐条定位细节见
  [归档](archive/2026-10/ADR-过程记录归档.md#adr-066)。）
- **决策**：
  1. **滚轮缩放的修饰键纳入命令表**：新增 `Cmd::ZoomWheelMod`（分组「缩放」）与
     `CmdDef::mod_only` 标志。它绑定的是**修饰键集合**（`ImGuiMod_*`，ini 里存 `Ctrl` /
     `Ctrl+Alt`，空 = 无），故不走 `cmd_pressed`（那条路径要求"有主键被按下"），
     改由 `wheel_zoom_mod_held()` 读取，且**修饰键严格相等**（绑 Alt 时按 Ctrl+Alt 不缩放，
     与 `chord_pressed` 同一纪律）。界面侧渲染成**下拉框**（无 / Ctrl / Alt / Shift / Ctrl+Alt）
     而不是捕获框；`chord_to_string` / `chord_from_string` 增补"无主键、纯修饰键"的表示。
     选"无"即"滚轮只滚动"。
  2. **按键分栏补「鼠标与固定键」一节**（列表末尾，只读参考）：滚轮滚动、按住修饰键+滚轮缩放、
     左键拖拽平移、右键菜单（及 Shift+F10 / 菜单键）、拖拽与点击滚动条、单击失败占位重试、
     鼠标移到窗口顶部重现顶栏、`Esc` 关对话框。判据是"**凡是用户能做的操作，界面里必须查得到**"；
     能改的在上面（命令表），不能改的在这里。
  3. **顶栏唤醒源收敛为三类**：鼠标靠近窗口顶端、设置窗口开着、**顶栏自身的弹出菜单**
     （主菜单 / 缩放档位，新状态 `g_toolbar_pinned`，由 `draw_top_bar` 每帧写）。
     画布右键菜单与跳页 / 密码 / 确认弹窗**一律不唤醒顶栏**。保留"顶栏自身菜单"这一类的理由：
     菜单挂在顶栏按钮正下方，顶栏若滑走菜单就悬空了。
  4. **页面淡入改为"纹理在眼前就绪才淡入"**：`PageFade` 增 `waiting`（本页当前正以占位显示）。
     纹理到达时若本页此前正是占位态 → 淡入（保留"内容换入"的柔和感）；若本页是被**预加载**
     好之后才滑入视野的 → **直接全不透明显示**（`seen=true, alpha=1`）。
- **理由**：三条反馈的共同点是"界面对自己的能力不透明"——能改的没告诉用户、不能改的没列出、
  自以为在做的事（预加载）被观感否掉。故修法不是加功能，而是把"**能力与触发条件**"讲清楚：
  修饰键进命令表（可改可查）、不可改的进参考节、淡入按"内容何时到达"触发而不是按"本页何时被画"。
  顶栏那条不去动"自动隐藏"本身（沉浸阅读要它），只砍掉无谓的唤醒源。
- **代价**：
  - 命令表多出一个"不像命令"的条目（无主键、不派发），读 `kCmds` 时要看 `mod_only` 才知道；
    用 `mod_only` 标志 + 注释把这处分叉显式化，`find_bind_conflict` / `update_key_capture`
    都跳过它（修饰键集合与主键组合不同域，谈不上冲突）。
  - ini 的 `[keys]` 里出现"纯修饰键"值（`Ctrl`），旧版本读它会得到 `ImGuiKey_None`（安全忽略、
    保留默认），降级无害。
  - 顶栏"钉住"多了**一帧延迟**（`draw_top_bar` 帧末写、`update_toolbar_visibility` 帧首读）；
    自动隐藏需要 1.6s 空闲，一帧延迟无观感影响。
  - 预加载页面不再淡入：从占位切到内容的柔和感仍在，只是"翻页"这一路上不再有渐显。
- **后果**：`app_internal.h` 增 `Cmd::ZoomWheelMod` / `CmdDef::mod_only` / `PageFade::waiting` /
  `g_toolbar_pinned` / `wheel_zoom_mod_held()`；`session.cpp` 增表项、修饰键串的读写、
  `wheel_zoom_mod_held()`，`handle_canvas_input` 改判它；`ui.cpp` 按键分栏增下拉框与
  「鼠标与固定键」参考表、`top_bar_should_show` / `update_toolbar_visibility` 改用
  `g_toolbar_pinned`、页面淡入按 `waiting` 触发。人工验证新增 11-1~11-3。
- **自动化现状**：**无**（app 层整体不在自动化范围内）。本轮唯一可自动化的点是
  "纯修饰键串的往返"（`chord_to_string` ↔ `chord_from_string`），但它在 app 层、
  不在 `tests/` 能链接的模块里；如需防线，可把这两个纯函数下沉到 `utils` 后补往返断言。

## ADR-067 配色按内容分层：纸墨层变换 + 图像层保留；chrome 与页面同向暖化（2026-10-06，UI 优化）

- **背景**：人工反馈两条，都在说同一件事：
  1. 深色（当时叫"反色"）模式把页面里的**照片直接变成负片**；暖色（当时叫"护眼"）模式把照片染黄，
     而且**界面颜色不跟着变** —— 页面暖、四周冷，整体不协调；
  2. 于是"带插图的文档"这两个模式**都不可用**。
  根因是**层次错了**：配色是"整页渲染成一张位图之后，对**整张位图**逐像素套一个 LUT"
  （ADR-036/043）。这一层已经拿不到"哪块是图像"的信息，必然对纸面、文字、照片一视同仁。
  所以修法不是调参数，而是把判断下沉到还知道"这一笔是什么"的那一层。
- **决策**：
  1. **在 MuPDF 设备层按内容分流**。`document` 层新增 `SplitDevice`（逐回调转发的自定义设备），
     夹在页面与 draw device 之间：**纸墨层**放行一切但拦下 `fill_image`；**图像层**只放行 `fill_image`。
     `render_page` 于是跑两遍、写**同一张 pixmap**：纸墨层 → 套配色 LUT → 图像层叠回。
     图像层按 `kImageDim = 0.88` 降 alpha 压暗 —— 暗环境里照片不刺眼，但色相不动。
  2. **分类规则**：只有 `fill_image` 算图像层；`fill_image_mask`（单色蒙版图，如 logo/图标）
     算**墨迹**、跟着变换 —— 它画出来的是"墨色形状"，深色模式下不跟着变浅就会是一块白。
     裁剪类（`clip_*`/`pop_clip`/`begin_mask`/`end_mask`）与容器类（group/tile/layer/structure）
     **两层都转发**，保证两层看到同一套状态；蒙版内容（`begin_mask`~`end_mask` 之间）两层都放行
     —— 它不进画面，只是各自栅格化一份，只放一边的话另一边的软蒙版会是空的、被蒙住的照片会整块消失。
  3. **整页扫描件回退**：图像覆盖面积 ≥ 页面面积的 **55%** 且纸墨层抽样墨迹覆盖率 < **0.5%** 时，
     判定"这一页就是一张图"，改走"图像原样铺满 → 最后整体套一次配色"。
     否则深色模式下扫描书会是一整页白（图像层被原样叠回、纸墨层什么都没有）—— 等于没开。
     反例（整页底图 + 正文的杂志封面）因纸墨层有文字而不触发，仍只变换文字、保留底图。
  4. **chrome 跟随纸张方案**：界面颜色拆成两个**正交**维度 —— **界面主题**（浅/深/跟随系统，
     用户偏好，管明暗）与**纸张方案**（原色/深色/暖色，管页面，并决定 chrome 的暖化强度：
     深色 0.6 / 暖色 1.0 / 原色 0）。深色仍强制深色 chrome（沿用 ADR-043 的判断：页面已是深纸，
     四周留亮边更累眼）。中性底**仍只有浅/深两套**，暖化变体由 `warm_apply` 现场派生，
     `g_pal`、ImGui 控件配色、`ui.cpp` 的强调色**都过同一个函数** —— 手写 4~5 套相近调色板
     既难保持一致，又必然漏改某几个色，而"页面暖、某个按钮冷"正是这么来的。
  5. **命名**：`ColorMode{Normal,Invert,EyeCare}` → `PageScheme{Original,Dark,Warm}`，
     显示名"原色 / 深色 / 暖色"（"反色"已名不副实）。**枚举数值 0/1/2 保持不变**（`reader_state.bin`
     的持久化契约）；命令表 `id` 也保留历史名（`ToggleInvert`/`ToggleSepia`）—— 它是 ini 的稳定标识，
     改了会让用户自定义的 `I`/`E` 绑定静默退回默认值，只更新显示名。
  6. **菜单宽度另立防线**：弹出菜单的宽度由**最长那一项**决定，一条超长文案会把整张菜单撑宽、
     其余短项显得空荡（人工反馈的"双页对开（书籍模式）"即此类）。处置：菜单文案上限 **12 个 CJK 列**，
     补充说明一律走 `menu_item` 的 `tip`（悬停提示）；新增 `tests/check_menu_width.py` 扫描
     `src/app/ui.cpp` 的菜单字面量并断言宽度上限，接进 `run_tests.ps1`，防止再次腐化。
- **勘误（2026-10-06，同日第二轮 UI 优化）**：第 4 条的"**暖化强度**（深色 0.6 / 暖色 1.0）"
  已被 ADR-068 取代 —— 实测发现"给整块调色板乘一个暖化系数"会同时坏掉三件事：冷蓝强调被污染成
  脏蓝、深色下文字被染成奶油色（"整屏变暖深色"）、界面侧还有一批颜色根本没走这条映射。
  现在改为"按角色分类的色调映射"（`src/app/tone.h`），第 4 条中"两个正交维度"的框架保留。
  第 6 条的菜单宽度断言继续有效。
- **理由**：配色需要"这块是不是照片"的信息，而这个信息**只在 MuPDF 的设备回调层存在**
  （`fill_image` vs `fill_text`/`fill_path`/`fill_shade`）。把判断放到那一层，两个模式才能同时做到
  "纸面舒服 + 照片真实"；chrome 暖化则是同一件事的另一个落点 —— 两边走同一条映射，局部不协调从源头消失。
- **代价**：
  - 非原色方案下页面要**跑两遍**（一遍纸墨 + 一遍图像）再叠一次 LUT；原色方案仍是单遍直绘，零回归。
    绝大多数页面的第二遍只画少量图像，代价有限。
  - 必须自写转发设备（约 30 个逐回调转发函数）：MuPDF **没有**内置的过滤设备，而"拷贝一份回调表"
    不可行 —— 派生设备的状态就存在基础结构之后，拷贝后回调会按派生类型读到越界内存。
  - 分类是"按绘制指令"而非"按像素"，复杂透明度组 / 软蒙版等边角行为可能与单遍渲染不完全一致。
- **后果**：
  - `document.ixx` 枚举改名与契约注释；`document.cpp` 增 `SplitDevice` / `paper_is_blank` /
    两遍渲染；`render.*`、`app/*`（`g_scheme`）、`reader_state`（字段 `scheme`）、`tests/*` 同步改名。
  - `platform.cpp` 增 `warmify` / `warm_apply` / `warm_palette`；`sync_theme(scheme)` 由
    "主题 + 反色 → 明暗"扩展为"主题 + 纸张方案 → 明暗 + 暖化"。
  - **自动化**：`doc_test` 新增两个样本与 4 条断言 —— `with_image.pdf`（文字 + 纯红图）断言
    "原色下照片为纯红""深色下照片仍是红的（若被一起变换会变青蓝，`b` 会很高）""深色下纸面仍变深"；
    `scan_only.pdf`（整页一张白图）断言"深色下整页整体变深（未留白）"。断言失败时打印实测 rgb。
  - 踩坑记录见[归档](archive/2026-10/配色分层与菜单宽度.md)：自定义设备的 `drop_device`
    **不得自己释放设备结构** —— `fz_drop_device` 会在调用 `drop_device` 之后自行回收整块内存，
    再 `fz_free` 一次就是**双重释放**，症状是 `0xC0000374` 堆损坏，且**只在 drop 那一刻炸**、
    与页面内容完全无关（极易误判成渲染 bug 去查像素）。

## ADR-068 色调映射按角色分类；主题切换必须整套重置 ImGui 样式（2026-10-06，UI 优化第二轮）

- **背景**：ADR-067 落地后人工实测，三条反馈：
  1. **深色下勾选框是一整块亮奶油色**，与周围完全割裂；
  2. **深色整体偏暖，"变成暖深色了"**，希望再中性一点；
  3. **暖色模式对比偏低**，有些地方看不清；顺带"颜色可以再丰富一点，但简洁为主"。
- **根因**（三条各自独立，都不是"参数没调好"）：① **跨主题残留**——深色分支只逐项覆盖了在意的
  35 项，未覆盖项（如 `ImGuiCol_CheckboxSelectedBg`）沿用上一次的浅色值，再被色调映射成亮色；
  ② **"全局暖化系数"只改色相、不分角色**——冷蓝强调被推成脏蓝、文字被染成奶油色（"整屏偏暖"
  其实主要是文字贡献的）；③ **局部漏改**——`ui.cpp` 自绘的 `col_text/col_dim/col_warn`、危险红、
  强调色没走暖化。（三条的实测取色与详细分析见
  [归档](archive/2026-10/ADR-过程记录归档.md#adr-068)。）
- **决策**：
  1. **把"暖化系数"换成按角色分类的色调映射**，落在新的 `src/app/tone.h`（纯函数、不依赖
     ImGui/Win32，故可被单测直接断言）。三类角色，各有明确保证：
     - **中性族**（色度 < `kChromaMin`）：表面、文字、边框、控件底。旋到方案色相并补饱和度，
       但**保持 WCAG 相对亮度** —— 各层"谁比谁亮"与中性方案逐字一致，层次不会因为换色而塌掉。
       其中**中间调**（相对亮度 0.02~0.50）再乘一次 `ink` 压深：色度对比**不**计入明度对比，
       彩色底的感知对比天生低于中性底，次要文字与边框需要额外压深一档来补偿。
     - **强调族**（有色、且色相 180°~305°，即冷色）：换到方案强调色的**色相与饱和度**上，
       **明度沿用原色** —— 常态/悬停/按下之间的明暗关系因此原样保留，只是整族换了色相。
     - **语义族**（有色、且非冷色：红/橙/绿）：只把色相向方案色相**拉近 25%**，
       保住"红=错误、橙=警告"的可辨识度 —— 全盘换色会把语义一起抹掉。
  2. **判"有没有颜色"用色度（max−min）而不是 HSV 饱和度**：近黑正文 `(0.13,0.15,0.18)` 的
     HSV 饱和度高达 0.28（会被误判成冷色强调），色度却只有 0.05 —— 肉眼就是中性。
  3. **色域上限用降饱和解决，不用硬钳**。目标亮度可能超出某色相在色域内能达到的上限
     （越接近白，能承载的饱和度越低）。此时在饱和度上二分到"亮度恰好等于目标" ——
     若改成直接把 RGB 钳到 1.0，近白的中性色（暖白文字、亮面板）会凭空变暗，
     "保持亮度"这条保证就破了。同理，**保亮度这条性质本身是可断言的**，写进了单测。
  4. **三套方案的 Tone 参数**（`platform.cpp`）：原色 `inactive`（一个通道都不动，是用户认可的基准）；
     深色 `hue 29 / sat 0.08`；暖色 `hue 40 / sat 0.155 / level 0.87 / ink 0.70`。
     色相取的就是**页面纸色所在色相**（深色纸 `#1F1D1B` ≈ 30°，暖色纸 `#F6EEDC` ≈ 41°），
     但**深色的饱和度故意压得很低**：深色主题的"暖"极易过量，暖意只留在强调色上。
     强调色：深色 = 柔沙 `#E0B37B`，暖色 = 赭石 `#A96F25`，原色 = 蓝（不动）。
     暖色 `level 0.87` 是为了让**米黄纸面成为全屏最亮的一层**（原先周围比纸还亮，纸面反而发闷）。
  5. **界面侧自绘颜色一律过 `tone_apply`**：`col_text/col_dim/col_warn`、危险红、强调色全部纳入。
     "暖色下看不清"的直接来源就是这几处没跟着走。
  6. **主题切换必须整套重置 ImGui 样式**：两个分支分别以 `StyleColorsLight` / `StyleColorsDark`
     打头，再逐项覆盖；并显式设置 `ImGuiCol_CheckboxSelectedBg`（**深底 + 彩色勾**，
     与浅色主题"近白底 + 蓝勾"的形状一致，只是换了明暗）—— 直接照搬 ImGui 默认会得到
     "整块强调色底 + 同色勾"，对比度很差。
- **理由**：配色要同时满足"表面成族""照片不被波及""文字看得清""强调色属于本方案"，
  这是四条互相拉扯的约束，**一个标量系数表达不了**。按角色分类之后，每条约束各自有归属：
  成族由色相统一保证、看清由"保亮度 + 中间调压深"保证、强调色由整族替换保证、
  语义由"只拉近 25%"保证。而且这些保证都能写成断言（见下），不再依赖"看着差不多"。
- **代价**：
  - 色调映射从"一次线性运算"变成"HSV 往返 + 至多 24 次二分"，但只在**主题/方案变化时**
    对 62 个颜色算一次（外加 ui.cpp 每帧几十次自绘色），量级可忽略。
  - `tone.h` 的规则比一个系数难解释，故把"为什么这么分类"完整写进了头注释与本节。
  - 深色主题的暖意被压到很低之后，chrome 与"暖黑纸面"的暖度差略大（纸面 r−b 差 4、
    chrome 差 3），在那个亮度下肉眼不可辨，属可接受的取舍。
- **后果**：
  - 新增 `src/app/tone.h`（色调数学）、`tests/tone_test.cpp`（113 条断言）、
    `tests/check_theme_reset.py`（主题重置防线），均接入 `tests/run_tests.ps1`。
    `warmify` / `warm_apply` / `warm_palette` / `g_warm_amount` 全部删除，改为
    `tone_apply` / `tone_palette` / `g_tone`。
  - `tone_test` 覆盖四类：**原色零改动**（逐通道）、**黄金值**（每套方案 13 个角色色的最终 RGB，
    改参数即红，逼你把这张表一起更新 —— 它就是配色的定义）、**对比度下限**
    （正文/次要文字/强调色/层次分隔各自的 WCAG 对比度）、**结构不变量**（换色不改变明暗次序、
    强调族不再偏冷、语义色仍是红/橙、中性族保亮度 = 原值 × level）。
  - `check_theme_reset.py` 断言两个分支持先整套重置 —— 跨主题残留这类 bug 在代码里毫无痕迹，
    只能靠这条结构性约束挡住。
  - 踩坑与实测取色过程见[归档](archive/2026-10/深浅配色-角色化色调映射.md)。
  - **人工验证（2026-10-06）**：13-1~13-5 五项全部通过。验证时另发现并**当场修掉**一处同类问题 ——
    **页面**（非界面）的深色 LUT 两端暖度不一致（正文 r−b 差 10、纸面差 4，源于逐通道斜率
    写成 R −185 / G −183 / B −179）。这与本条"亮、面积小、对比强的元素，一点色相就非常显眼"
    是同一条规律；把亮端改为 `kDark + 184`（三者等斜率）后两端暖度一致。
    详见归档第 7 节与 ADR-043 勘误。

## ADR-069 文本选择/复制、图片复制、超链接、全文搜索：坐标空间与线程归属（2026-10-06，文本与检索）

- **背景**：需要"纯文字可选择并复制（不做 OCR）"、"复制鼠标下的嵌入图片"、"超链接可用"
  以及"全文搜索"。这些能力都要碰 MuPDF 的文本层（`fz_stext_page` / `fz_load_links`），
  而本项目有一条硬纪律：**UI 线程零 `fz_*`、零阻塞**（ADR-006/012），文本抽取只能在渲染
  工作线程做。于是"谁算、算完怎么给 UI"成为本轮的主要设计问题。

- **决策**（六条）：

  1. **坐标空间只用"未旋转页面 pt"，旋转折算抽成纯函数。**
     `fz_stext_page` / `fz_load_links` 的坐标天然在**未旋转**页面空间（点，y 向下）。
     本模块一律原样输出，**不在 document 层做任何旋转**；app 层用
     `src/app/page_map.h` 的两个纯函数完成 屏幕 ↔ 未旋转页面 pt 的折算。
     理由：旋转 90° 的整数倍只是**归一化坐标的置换**（`(u,v) = (1-nv, nu)` 之类），
     与"页面包围盒原点是否为零"无关；把它独立出来之后，整套命中测试/高亮/复制
     在旋转视图下**没有任何分支**，且这份置换可以被单测逐角钉死
     （`tests/page_map_test.cpp`，27 条）。若把旋转塞进 document，同一份抽取结果
     就无法跨旋转复用，且 0° 正常、90° 整体偏一格这类错误只能靠肉眼发现。

  2. **文本布局抽成快照发布给 UI，UI 侧只做纯浮点命中测试。**
     工作线程按需抽一页的 `PageContent{chars, lines, images, links}` 并发布；
     UI 拿快照自己做"点在哪个字符/哪一行/哪个链接/哪张图"的判断与高亮计算。
     理由：命中测试要跟着鼠标每帧跑。若每帧回工作线程问一次，拖动选择会与渲染
     抢同一个线程（该线程同时负责出图），手感会明显发涩。

  3. **辅助请求走独立队列，不共用 open/close 的单命令槽。**
     `Renderer` 原有的 `cmd` 槽是"后到覆盖先到"语义（open/close/auth 都是用户显式动作，
     覆盖上一次待处理是合理的）。文本请求由**鼠标悬停**触发、频率高得多；若共用槽位，
     一次悬停就能把"待打开的文档"覆盖掉 —— 用户点了打开却没反应。故另开 FIFO 队列，
     与渲染请求同优先级、互不覆盖。

  4. **选区几何在确定时"冻结"，与内容快照解耦。**
     选区不只存"字符下标"，而是同时冻结**复制端点（页面 pt）+ 按行合并的高亮矩形**。
     理由：字符下标只在"当前页的内容快照"里才有意义，而快照只有一页（随鼠标移动到
     别的页就被换掉）。若只存下标，用户选好一段、把鼠标移到下一页再回来右键复制，
     就会复制失败或复制到错的内容。

  5. **复制文本走 `fz_copy_selection`，不自己拼字符。**
     自己拼会漏掉"两个词之间有间隙"这类**只有版式知道**的信息（英文尤甚，会得到
     `HelloWorld`）。代价是一次异步往返（用户点复制 → 工作线程算 → 下一帧写剪贴板），
     复制是低频动作，这点延迟不可感知。

  6. **检索增量、可取消、与渲染交替。**
     工作线程每轮只扫一小批页（`kSearchBatchPages = 24`），之后必然回到主循环让位给
     渲染请求；结果**渐进发布**，UI 边搜边显示；发起新查询即换 `id`，在途批次据此立即收工。
     理由：千页文档整段检索会让界面整段卡死。另设**全局**命中上限（5000）—— 单页上限
     （200）挡不住"几千页 × 每页 200 条"这种病态组合。

- **理由汇总**：这四条功能共享同一个约束（fz 只能在工作线程），但**共享方式不同**：
  布局快照是"一次算、多次用"（适合发布），复制文本是"低频、要准"（适合往返），
  检索是"长任务"（适合分批）。把它们按这个维度分开，比强行统一成一条通道更简单也更稳。

- **代价 / 已知限制**：
  - **选区限单页**。跨页选择需要"页序 + 页内偏移"的复合定位与跨页高亮，收益远小于代价。
  - **不做 OCR**：纯扫描件没有文本层，`PageContent::chars` 为空 → 该页不可选、搜索也搜不到。
     这是产品决定（用户明确要求不做 OCR），UI 侧表现为"没有 I 型光标"。
  - 文本布局**只请求鼠标所在那一页**（不是全部可见页）：抽一页 stext 与渲染一页同价，
    全可见页盲发会在滚动时把工作线程塞满。代价是首次悬停有约一帧的 I 型光标延迟。
  - `stext` 缓存**只有一页**（document 层）与**一页快照**（render 层），内存因此与页数无关。
  - "复制图片"取的是**嵌入图片本身**（`fz_get_pixmap_from_image`，原始分辨率），
     不是"该区域渲染出的位图"：矢量图/纯文本区域没有嵌入图片对象，该项会置灰。
  - 图片统一转为 RGB（保留 alpha 后按 3/4 分量展开为 RGBA8），其余色彩空间交给 MuPDF 的
     色彩管理；剪贴板走 `CF_DIB`（32bpp、自下而上、BGRA、alpha 恒 255 —— 沿用源图 alpha=0
     会让 Word/画图整张变黑）。

- **后果**：
  - `document`：新增 `TextQuad/TextChar/TextLine/PageImageRect/PageLink/PageContent/ImageData/SearchHit`
    与 `page_content / copy_text / image_at / search_page` 四个方法，外加一条 stext 缓存。
    全部遵守 ADR-009 的 setjmp 纪律：**遍历 stext 树（构造 std::vector/std::string）一律在
    `fz_try` 之外**，块内只有 POD 与裸指针。
  - `render`：新增辅助请求队列、页内容快照、复制结果槽、增量检索作业与 `SearchStatus`。
  - `app`：新增 `src/app/page_map.h`（纯函数）、`page_map_test.cpp`（27 条断言，接入
    `tests/run_tests.ps1`）；`session.cpp` 增选区状态机与坐标/命中/复制/链接/检索逻辑；
    `ui.cpp` 增页内叠加层（选区 / 命中 / 链接悬停）、侧栏「搜索」分栏、右键菜单四项；
    `platform.cpp` 增剪贴板读写（文本 `CF_UNICODETEXT` / 图片 `CF_DIB`）。
  - 命令表新增三条：`Copy`（Ctrl+C）、`SelectAll`（Ctrl+A）、`OpenSearch`（Ctrl+F）。
    三条都**非全局**：`handle_canvas_input` 的 `io.WantTextInput` 门保证搜索框获得焦点时
    Ctrl+C/Ctrl+A 归输入框，不被阅读命令抢走。
  - 图标新增三个字形（`E8C8` 复制 / `E8B9` 图片 / `E71B` 链接）。图标集是"全有或全无"
    （任一码位缺失则整套退化），故三个码位已用 fontTools 在本机 `segmdl2.ttf` 的 cmap 上
    逐个确认存在。
  - 人工验证清单见 [04-人工验证.md](04-人工验证.md) §文本交互与全文搜索（12-1~12-9）。

## ADR-070 Phase 8 实测反馈修复轮：命中测试分两档 / 侧栏区不参与顶栏唤起 / 分栏切换要真的切（2026-10-06，文本与检索）

- **背景**：ADR-069 落地后第一轮实测反馈六条（两条缺陷、两条手感、两条已确认正常：复制文本/
  图片/链接、链接跳转均可用），逐条定位到四个**接线处**的原因。（逐条定位细节见
  [归档](archive/2026-10/ADR-过程记录归档.md#adr-070)。）

- **决策**（四条）：

  1. **命中测试分两档**：`char_index_at(page, x, y, clamp_to_nearest)`。
     **悬停与按下走严格档**（`false`）：y 必须在某行"行框 ± 行高 1/4"内、x 必须落在行内字符
     ± 半个字高内，否则返回 -1 —— 如实报告"此处无文字"。**拖拽走宽松档**（`true`）：吸附到
     最近字符，于是拖到行尾之外选区仍能"到底"。两档必须分开：合成一档时，严格了拖不到行尾、
     宽松了整页都可选（正是本次缺陷）。
     行的"文字高度"取 **bbox 高与宽的较小者**：竖排文字的 bbox 高是**文字长度**，
     拿它当容差会让整页都算命中。
  2. **侧栏区不参与顶栏的唤起/收起**：鼠标在侧栏区（`x < 侧栏宽`）时**冻结**顶栏状态 ——
     既不因它而唤起（顶栏不会把侧栏推走），也不因离开顶端带而收起（否则侧栏会在光标下
     滑回去）。顶栏仍可从画布一侧的顶端带唤起。理由：侧栏的**可点内容就在窗口最上方**，
     "贴近顶端即唤出"与"点得到顶部内容"在同一块像素上直接冲突，只能让其中一个让位；
     顶栏有画布侧的等价入口，侧栏的标题栏没有。
  3. **分栏切换用一次性强制标志**：`g_sidebar_tab_want`，在被绘制的那一帧对该分栏带一次
     `SetSelected`，随即清掉。**不能每帧都带**：每帧都带等于把该分栏锁死，用户再也点不到
     别的分栏。标志要留到"真正绘制时"才消费 —— 侧栏是滑入的，`Ctrl+F` 可能发在侧栏尚未
     露出来的那几帧。
  4. **搜索的触发要有多条路**：回车 **+** 输入框下方的「搜索」按钮；关键字为空时状态栏提示
     "请输入要查找的关键字"（而不是毫无反应）。按钮不是装饰 —— 中文输入法下第一次回车是
     "上屏"，而 `EnterReturnsTrue` 只在回车真正送到控件时才为真。

- **理由汇总**：四个问题都**不在**算法或线程模型里，而在"用户的手落在哪个像素上、
  哪一次回车真的送达了控件"。这类接线故障的共同点是**只在人工操作里暴露**，
  所以本轮的防线是"把可程序判定的部分前移成断言"（见下"证据"），而不是再读一遍代码。

- **代价 / 已知限制**：
  - 严格档下，点在"行框 ± 1/4 行高"之外就不再是文本命中：单行文本的上方/下方各留约
    0.75 行高的"非文本"区。这是**刻意的** —— 那片区域本来就该是"平移/箭头"。
  - 侧栏区不再能唤起顶栏：顶栏在侧栏打开时要从画布一侧的顶端带唤起（或用固定显示）。
  - 「搜索」按钮占一行侧栏高度（约 1.5 行）。
  - 本轮**未**引入跨页选择、未与 `DocumentInfo::can_copy` 联动（仍记在已知限制里）。

- **后果**：
  - `app`：`char_index_at` 增 `clamp_to_nearest` 参数（三个调用点：悬停/按下 false、拖拽 true）；
    `g_sidebar_tab_want` 一次性标志 + `draw_sidebar` 的 `SetSelected`；`update_toolbar_visibility`
    增"侧栏区冻结"；`draw_search_tab` 增「搜索」按钮；`search_start` 空关键字给 toast。
  - `render`：`start_search` **不再**因"页表为空"提前返回（那会让故障变成"按了搜索什么都没发生"，
    无从排查）；无文档时由 `search_step` 立刻收敛、UI 如实显示"没有找到"。
  - `tests`：新增 `render_search_test.cpp`（渲染层检索通道端到端 10 条断言：跨页扫描、

## ADR-071 Phase 8 收尾轮：搜索改"防抖自动检索 + 可停止"，公式复制边界定性（2026-10-06，文本与检索）

- **背景**：ADR-070 之后第二轮实测反馈三条，其中前两条是交互设计问题、第三条需要定性：

  1. **搜索"没用"的真实原因是用户没按到「搜索」按钮**。当时只有"回车 / 点按钮"两条触发路，
     两条都要用户主动做一次动作；而用户的心理模型是"打完字它就该搜"。
  2. **搜索没有「取消」**：要中断在途检索，只能"把关键字删掉再按一次搜索"，反直觉。
  3. **公式复制"不完善"**：用户描述为"有时候可以复制符号，有时候一些内容复制不了或者无法选择"。

- **决策**（五条）：

  1. **输入防抖自动检索**（`kSearchDebounceSec = 0.4`）：输入框内容一变就作废旧查询并起计时，
     **停手 0.4s 自动发起检索**；回车与「搜索」按钮保留为"不等防抖、立刻检索"的快捷路。
     - **三件状态必须分开**：`committed`（结果列表对应哪个关键字）/ `seen`（上一帧的输入内容，
       用来判定"这一帧是否改了字"）/ `pending`（有改动、正在等计时）。若拿 `committed` 直接
       和输入框比，改字后 `committed` 尚未更新，会**每帧都判定"改了"**，计时器每帧被重置，
       永远等不到到期 —— 这是防抖实现最容易踩的一处。
     - **不做"逐键检索"**：千页文档上每敲一个字符扫全文会把工作线程持续占满。
     - **输入法安全**：Windows IME 的组字串在**上屏**时才进入 ImGui 的输入缓冲，
       故"按缓冲变化计时"天然不会在半成品拼音上触发检索。
  2. **改字即取消**：关键字一变就立刻 `cancel_search()` 并清空旧结果。
     - 取消在途是**必须**的：检索与渲染抢同一个工作线程，不停会明显拖慢出图。
     - 清空旧结果是**必须**的：结果列表必须与关键字一致，否则点进去跳到的地方与输入框里的词
       对不上（用户会当成"搜索不准"）。
  3. **「停止」按钮 + `Renderer::stop_search()`，与 `cancel_search()` 分成两条语义**：
     - `cancel_search()` = **作废**（换关键字 / 换文档 / 关文档）：进度与结果都不要了。
     - `stop_search()` = **收手**（用户不想再等）：只关 `active` 并换 id 让在途批次收工，
       `next_page / hits / pending / needle` **全部保留** —— UI 仍能如实报
       "已停止 · 已扫描 N / M 页 · 已找到 K 处"，也仍能取走最后一批命中。
     - 若两者共用一条实现，"停止"后会显示"已扫描 0 / M 页"，那是"从未搜过"的样子，
       与"搜到一半停下"是两回事。**这条区分有断言钉死**（`render_search_test`）。
  4. **状态文案必须区分"扫完"与"中途停下"**：以 `scanned < total` 判定未扫完；未扫完时不写
     "共 N 处"（那是"已扫完全文"的措辞），改写成"已停止 · 已扫描 N / M 页 · 已找到 K 处"。
  5. **公式复制的"不完善"是预期边界，不是缺陷**。用户现象"有时候能复制符号、有时候复制不了
     甚至无法选择"对应三类根因，**全部落在 PDF 文本提取的固有限制内**：
     - **不可选择** ⇒ 该处**根本没有文本层**：公式被画成矢量路径（字形轮廓）或位图。
       命中测试如实返回 -1 → 没有 I 型光标。**任何基于文本层的方案都无解**，
       只有 OCR 能覆盖，而"不做 OCR"是用户明确的产品决定。
     - **可选中但复制缺字/错字** ⇒ 字体没有可用的 `ToUnicode` CMap（子集字体、Type3、
       符号字体自定义编码），MuPDF 无法把字形码映射回 Unicode。
     - **顺序错乱** ⇒ 公式的上下标/分式在版面上是多个文本对象，`fz_copy_selection` 按
       **阅读顺序**（而非视觉顺序）拼接。
     - 结论：不投入改动，写进已知限制。UI 侧的表现是**诚实的**（不可选就是不可选，
       不会假装选中一段空内容）。

- **理由汇总**：前四条都指向同一个判断 —— **搜索的触发与中断要贴合"打字"这个动作的节奏**：
  停手即搜（防抖）、改字即弃（取消）、不想等就停（停止且保留结果）。
  第五条则相反：用户以为的"缺陷"实际是格式的固有边界，此时**正确的动作是不改代码、把边界说清楚**，
  避免为了"看起来能复制"而引入 OCR 这类与产品决定冲突的东西。

- **代价 / 已知限制**：
  - 防抖窗口内不检索：千页文档上"改一个字"到出结果的总延迟 ≈ 0.4s + 一批（24 页）扫描时间。
  - 清空关键字**不弹**"请输入要查找的关键字"（用户是在删除，不是在搜空词）；
    空关键字弹提示只在**显式**回车 / 点按钮时发生。
  - 「停止」后结果列表保留但**不完整**，UI 用"已停止"明确标注，不冒充"共 N 处"。
  - 公式复制边界不修（见决策 5）；纯扫描件同理不可选、搜不到。

- **后果**：
  - `app`：`app_internal.h` 增 `kSearchDebounceSec` 与
    `g_search_committed / g_search_seen / g_search_pending / g_search_edit_at`；
    `session.cpp` 增 `search_stop()`，`update_search()` 增防抖段与"改字即取消"；
    `ui.cpp` 的 `draw_search_tab` 改双按钮（搜索 / 停止）+ 五态文案，F3 浮层加 `pend` 读数。
  - `render`：新增 `Renderer::stop_search()`（保留进度与命中的"收手"语义）。
  - `tests`：`render_search_test` 增 3 条断言（10 → **13**）：
    `stop_search` 保留进度与命中 / 在途停止后保持静止 / `cancel_search` 清零与 `stop_search` 区分。
  - 人工验证：**12-6 / 12-7 因触发方式改变需复测**（已在 04 改写为"停手自动检索"与
    "停止 / 改词 / 边界"两节）；12-9（EPUB 与选区持久性）仍缺合适样本，
    **留在 04 待用户自备样本后执行**。已通过的 12-1~12-5、12-8、12-10、12-11 移入
    [归档](archive/2026-10/phase8-文本与检索.md)。

- **证据（本轮）**：编译 Release 0 警告 0 错误；`tests/run_tests.ps1` 全部通过（`render_search_test`
  10 → 13 全绿）。（完整断言计数与"停止/取消语义差"关键断言见

## ADR-073 资源档位统一控制缓存与大页面 tile（2026-10-06，资源与渲染）

- **背景**：页缓存的唯一旋钮是 `[cache] BudgetMB`（ADR-030）；超大页面（A0 / 长图式 PDF）则只有
  单边上限降采样一条路。两者本是同一个约束（机器可用内存），却分成两处设置，于是出现"缓存调高、
  单页分配照样爆掉；缓存调低、正常页面频繁逐出"的组合。
- **决策**：
  1. 资源设置只保留**低 / 中 / 高**三档，档位同时给出页缓存上限与 tile 单边上限，避免用户把缓存调高
     却仍在超大页面上分配巨型 pixmap。现定低档 256MiB/1536px，中档 512MiB/2048px，高档 768MiB/2560px。
     旧版 `[cache] BudgetMB` 仅在首次读取时映射到最近档位并写入 `ResourceTier`。
  2. 大页面 tile 使用**旋转后输出像素空间**坐标，由 `Document::render_page_tile` 生成有限尺寸 RGBA
     纹理，渲染器复用当前 D3D11 device 和两段式退役队列。MuPDF 文档上下文仍保持单线程归属；并发
     worker 数暂作为 profile 数据而非默认启用策略。
- **理由**：档位是用户能理解也容易解释的单位，MB 与 px 是实现细节；绑在一起后任何一档都不会落到
  "缓存够大但单页分配爆掉"的组合。tile 相对降采样的好处是只增加纹理数量与绘制调用，不会让超大页在
  放大时永久丢细节，因此只在页面超过当前档位单边时启用。
- **后果**：UI 不再提供独立 MB 滑块，设置语义稳定且容易解释。普通页面继续走单纹理快路径；并发 worker
  必须由基线证明吞吐收益覆盖内存峰值后再打开。

## ADR-074 外观入口合并与主题优先级（2026-10-06，UI 优化）

- **背景**：界面主题（跟随系统/浅色/深色）与纸张方案（原色/深色/暖色）原本分别出现在“主题”和“配色”入口，
  但纸张方案还会改变 chrome 的色调，深色纸张曾无条件强制深色 chrome。用户无法从入口名称判断两个状态的范围，
  也无法知道文档为什么覆盖了手动选择的界面明暗。
- **决策**：
  1. 菜单入口统一为“外观”，显式分成“界面（全局）”和“纸张（本书）”两组；设置页把界面主题与纸张方案
     放在同一栏的相邻行，并显示联动规则说明。
  2. 纸张方案命名统一为“原色 / 深色纸张 / 暖色”；状态栏、按键设置、菜单与设置下拉使用同一组显示名。
     历史命令 ID（`ToggleInvert` / `ToggleSepia`）与枚举值保持不变，避免破坏用户的快捷键和阅读状态。
  3. `sync_theme` 的明暗优先级为：显式浅色或深色由用户偏好决定；只有在“跟随系统”时，深色纸张才作为额外
     的变暗条件。纸张方案仍通过 `Tone` 协调 chrome 的色调，因此页面与周围界面保持同族，但不覆盖显式明暗选择。
- **理由**：两个状态的持久化范围不同（界面主题写入全局 ini，纸张方案写入文档阅读状态），入口和文案必须表达
  这种范围差异。保留色调协调可避免页面暖、界面冷的割裂；把暗/亮控制权交给显式界面主题则使选择具有稳定含义。
- **后果**：设置页在无文档时纸张方案置灰；外观菜单在无文档时仍可调整全局界面主题。新增 `check_theme_precedence.py`
  结构断言，人工验证项 14-1/14-2 覆盖入口、命名、优先级、跨文档记忆和色调协调。

## ADR-075 搜索「停止」改为「取消」：取消即清空查询状态（2026-10-06，文本与检索）

- **背景**：ADR-071 给长检索配了「停止」，与「取消」分成两条语义 —— 停止是"收手"（保留进度与已找到的
  命中），取消是"作废"（清零）。实机使用中这个区分没有兑现成用户收益：「停止」之后输入框仍留着旧词、
  列表仍留着旧结果、状态栏停在"已停止 · 已扫描 N / M 页"，用户既不知道还能不能接着搜，也不知道再点
  「搜索」会不会续上上次的进度。两个近义按钮反而要求用户先理解内部语义。
- **决策**：
  1. 搜索分栏只留「搜索」与「取消」。取消清空**输入框、在途检索、扫描进度、结果列表与画布高亮**
     （`search_cancel()` → `search_clear()`），界面回到"刚打开这一栏"的状态；无查询且无结果时置灰。
  2. `render` 层移除 `Renderer::stop_search()`，只保留 `cancel_search()`（换 `id` 让在途批次收工，
     并清零进度与结果）。
  3. 状态文案去掉"已停止"态，只留五种：未输入 / 待检索（防抖计时中）/ 检索中（`N/M 页 · 已找到 K 处`）/
     无匹配 / 扫完（`共 N 处`）。未扫完时不再出现"共 N 处"这类措辞。
  4. `render_search_test` 的 3 条 `stop` 相关断言随之删除（13 → **10**）。
- **理由**：中文界面里「停止」与「取消」几乎同义，用户无法从措辞推断"结果会不会被丢掉"；既然只能留
  一种收场方式，就选语义唯一的那种 —— 要么继续等，要么清空重来。"改字即取消"已覆盖收手场景：用户想换
  词直接改输入框，旧查询与旧结果立刻作废，不必先"停止"再"搜索"。
- **后果**：不再存在"中途停下、保留已找到结果"的路径，想留住结果只能等检索自然收敛（实测未成为实际需求）。
  功能面收窄换来语义唯一：一个输入框、两个按钮，各自只有一个含义。

## ADR-076 持续集成：GitHub Actions 跑构建与回归（2026-10-06，工程）

- **背景**：`tests/run_tests.ps1` 已是一键可跑的完整回归（直调 `cl.exe` 编译各模块 + 全部断言 +
  字体/图标/菜单/主题资源检查，退出码即结论），但只在开发机手动执行。"本地绿、提交后无人复验"意味着
  回归只能靠个人纪律守住，外部贡献与换机开发也没有统一的验证入口。
- **决策**：
  1. 新增 GitHub Actions 工作流 `.github/workflows/pr.yml`，在 `pull_request` 与 push 到 `main` 时
     触发，在 `windows-2025` runner 上跑 **Release 构建（MSBuild + vcpkg）** 与
     **`tests/run_tests.ps1` 全量回归**，失败时上传 `_build` / `samples` / `build` / `bin` 供排查。
  2. vcpkg 安装根与二进制缓存都放在 runner 临时目录下（**在仓库检出目录之外**）——libmupdf 端口有一条
     未加引号的 `/LIBPATH`（ADR-010），仓库路径含空格会把该参数截断。
  3. manifest 的 `builtin-baseline` **只在 CI 内临时注入**（写到 runner 临时目录的 `vcpkg.json` 副本），
     不改仓库里的 `vcpkg.json`，避免与并行进行的功能改动冲突。
  4. 依赖二进制用 `actions/cache` 缓存；平台工具集按 runner 上已装的 MSVC 探测（优先 `v145`，
     没有则回落 `v143`）。
- **理由**：构建与测试的全部知识已固化在 `run_tests.ps1` / `build.bat` 里，CI 复用它即可，**不新增
  第二套构建定义**——否则会反向漂移成"CI 能过、本地不能过"。把工具链探测与依赖落点写进工作流，
  可让 runner 镜像升级时不至于整条流水线卡死。
- **后果**：PR 与推主干都会得到一次干净环境的构建与回归；首次运行需从零构建 vcpkg 依赖（较慢），
  命中缓存后显著变快。工作流是一份自足的 YAML，不引入额外服务或凭据。
- **勘误（2026-10-06）**：首次真实运行即失败（C1083）。根因：vcxproj 依赖**经典 vcpkg MSBuild
  集成**注入 include/lib 路径，而该集成来自开发机 `vcpkg integrate install` 留下的**机器级状态**
  （不在仓库里），runner 上不存在。修复：工作流新增「Enable user-wide vcpkg MSBuild integration」
  步骤，显式执行 `vcpkg integrate install`。教训：**本地能编过的前提里凡属机器级状态的，CI 都必须
  显式重建。**（详细根因链条见 [归档](archive/2026-10/ADR-过程记录归档.md#adr-076)。）
- **勘误二（2026-10-06）**：构建通过后测试步骤再挂——`make_samples.py` 打印中文日志抛
  `UnicodeEncodeError`（Python 子进程 stdout 为管道时用系统 ANSI 代码页，`[Console]::OutputEncoding`
  管不到）。修复：`run_tests.ps1` 顶部设 `$env:PYTHONUTF8 = "1"`，由回归唯一入口统一约束 Python
  子进程编码，本地与 CI 同源。

## ADR-077 自实现轻量日志，不引入 spdlog（2026-10-06，稳定性）

- **背景**：Phase 7 需要日志来定位问题（渲染失败、线程异常、设备错误的时间线）。旧宿主项目带
  spdlog，迁移计划把宿主依赖列为"不带入"；是否为稳定性单独引入，需要一次正式决策。
- **决策**：不引入 spdlog，自实现 `src/log/`（`lilithreader.log` 模块）。能力只保留本项目
  实际需要的：Debug/Info/Warn/Error 四级、时间戳 + 线程 ID + 模块 + `name=value` 字段、
  后台线程落盘（写入侧只入队，UI 线程零阻塞）、单文件 2 MiB 写满轮转为 `.log.1`、
  未初始化时安全退化（Debug 走 OutputDebugString，Release 丢弃）。
- **理由**：
  1. spdlog 即使只编核心 + 内嵌 fmt，Release 静态链接也是数百 KB 量级，而本项目只需要
     "等级 + 时间 + 线程 + 模块 + 一行文本"；单 exe、静态链接、少依赖是既定纪律（迁移计划 §0.2）。
  2. 崩溃路径**不能**用它：进程崩溃时堆与运行库可能已损坏，普通日志模块不可信。
     崩溃转储因此单独用 Win32 原生 API 实现（ADR-080），与日志彻底解耦——spdlog 的异步
     sink 在这条路径上没有任何额外价值。
  3. 引入 spdlog 还要确认许可证与构建集成（vcpkg 依赖图、CI 缓存体积），收益不成比例。
- **纪律**：调用点只允许**低频事件**（打开/关闭文档、渲染失败、重试、线程异常、设备错误、
  退出），禁止进入每帧/每页/每 tile 的热路径；日志不写用户隐私正文。
- **后果**：exe 体积几乎不变（<10 KiB）、无新依赖；代价是格式化能力弱（无 fmt 风格占位符），
  字段靠 `log::kv()` 拼接。日志定位是"事件时间线"，不是结构化遥测，够用。

## ADR-078 ImGui 栈操作全面 RAII 化 + 帧级栈平衡自检（2026-10-06，稳定性）

- **背景**：ImGui 的 Push/Pop 与 Begin/End 是手工配对的栈操作。绘制中途抛出 C++ 异常
  （最常见是拼串触发的 `std::bad_alloc`）会留下脏栈，此后每帧的样式/窗口/弹窗栈全部错位，
  轻则界面错乱、重则在 ImGui 断言处崩溃。靠 catch 事后"补 Pop"不可行：抛出点在哪、压了几层，
  catch 处无从得知。ImGui 1.93 同时新增了官方"错误恢复"机制（`ConfigErrorRecovery` +
  `ErrorRecoveryStoreState`/`ErrorRecoveryTryToRecoverState`）。
- **决策**：
  1. 新增 `src/app/imgui_raii.h`：把每一对操作包成**词法作用域对象**——无条件配对
     （Window/Child/Disabled/全部 Push*，析构即 Pop）与条件配对（Menu/Popup/PopupModal/
     TabBar/TabItem/Table/TreeNode/Combo/Tooltip，`operator bool` 表达可见性、仅可见才 End）。
     包装器全部 noexcept、不分配、不写日志、不可拷贝不可移动（保证析构恰好一次）。
     `dismiss()` 表达"提前收口"（最典型是 `PushStyleVar(WindowPadding,0)` 只覆盖 `BeginChild`
     那一瞬），且**幂等**：dismiss 过的析构不再重复 Pop。
  2. `ui.cpp` 全量改用包装；此前"跨函数配对"的 `settings_rows_begin/end` 也收敛为一个
     组合两个包装的局部对象，消灭最后一处跨作用域配对。
  3. 新增 `src/app/imgui_stacks.h`：帧首 `capture_stacks()` 快照 → 帧尾 `format_stack_diff()`
     比对（Debug 构建），任何漏配对当帧点名（哪个栈、差几层）。**判据只能是"帧尾 == 帧首"**
     —— ImGui 在 NewFrame 里就自动开隐式窗口并压默认字体，"各层是否为 0"永远为假。
     实现细节上有个必踩的坑：取"当前窗口"必须用**只读**的 `ImGui::GetCurrentWindowRead()`，
     公开的 `ImGui::GetCurrentWindow()` 会把窗口标记为 `WriteAccessed=true`，而帧首快照恰恰
     在 NewFrame 之后调用——标的正是隐式回退窗口 Debug##Default，EndFrame 就不再隐藏它，
     屏幕上凭空多出一个空 "Debug" 窗口（人工试用时抓到，已修，见归档 2026-10 §6.1）。
  4. 主循环帧级 try/catch：`draw_shell` 抛异常 → 记日志 + `ErrorRecoveryTryToRecoverState`
     拉回基线 + 跳过本次 Present（保留上一帧画面，不提交半帧）；`ImGui::Render()` 仍必须调用，
     否则下一帧命中 "Forgot to call Render()" 断言。
  5. 接管 ImGui 错误：`ConfigErrorRecovery = true`、Tooltip 保留（错误必须浮出水面）、
     `ErrorCallback` 接 `lr::log`。断言仅在 Debug 保留，Release 降级为"记录 + 自愈"。
- **理由**：栈的收口交给 C++ 栈展开保证，语言机制比任何"小心一点"都可靠；try/catch 只负责
  把错误截住转成状态，不做状态修复。恢复必须发生在 `Render()` 之前，否则带脏栈进 EndFrame。
- **后果**：`ui.cpp` 不再有任何手工 Push/Pop；漏配对从"几帧后的怪现象"变成"当帧日志里的
  一行"。代价是每处作用域多一个栈上小对象（可内联，正常路径无堆分配）。headless 测试
  `imgui_raii_test` 断言：配对、异常展开、dismiss 幂等、200 帧不累积、诊断能检出注入的漏配对。

## ADR-079 渲染线程入口封死 + D3D 资源所有权集中（2026-10-06，稳定性）

- **背景**：`std::jthread` 工作线程入口若逃出异常，直接 `std::terminate`——这是整个程序里
  最危险的路径。同时 D3D 纹理仍以裸指针存放在 `PageSlot`/tile/退役队列里，靠人工保证释放，
  tile 渲染中途抛异常时 `std::vector` 不会替裸指针调 `Release()`。
- **决策**：
  1. 工作线程入口 lambda 标 `noexcept`，`run()` 最外层 try/catch 兜底（捕获即记日志并置
     故障状态）；单页渲染、tile 渲染、文档打开、认证、辅助请求、检索**各自**捕获并转成
     文档级/页级失败状态。异常不允许逃出线程函数。
  2. 纹理创建函数先校验 stride ≥ w×4 再上传（避免 D3D 按 pitch 跨步读取越过缓冲区尾部），
     尺寸/数量上限检查集中在入口。
  3. 纹理所有权只在三处收口：发布进 `PageSlot`、入退役队列、`shutdown()` 全量释放；
     文档切换时迟到结果直接退役，不悬空。
  4. 新增 `tests/render_fault_test.cpp`：在真实线程边界上断言"一个错误不拖垮调度器"——
     5 种坏文件全部文档级 Failed 且带错误详情、失败后仍能正常打开、越界页码/请求被夹住、
     25 轮 open/close 无累积、400 轮请求洪峰 + 检索起停后仍收敛、1200 页文档可打开可检索、
     A0 幅面（2384×3370pt）tile 路径收敛后调度器仍健康。
- **理由**：线程边界是"程序崩溃"与"一个页面显示错误占位"的分界线；资源所有权收口是把
  "靠人工纪律"变成"靠结构"。MuPDF 区域继续遵守 ADR-009 的 `fz_try/fz_always/fz_catch`
  纪律——不能把带析构的 C++ 对象放进 `fz_try`（longjmp 会跳过析构），两边纪律不混用。
- **后果**：压力测试项（损坏文件批量、请求洪峰、超大文档、超大页面）全部自动化进回归；
  代价是 `render.cpp` 的失败路径分支变多，但每条分支都有测试钉住。

## ADR-080 进程级崩溃防线：MiniDump + 崩溃标记（2026-10-06，稳定性）

- **背景**：前四层边界（模块/输入/线程/帧）覆盖的是**可捕获**的错误。访问违规、纯虚调用、
  CRT 参数校验失败、noexcept 违约这类崩溃没有"捕获后继续"的可能，但**必须留痕**——否则
  用户只会看到"程序消失了"，开发者拿不到任何线索。
- **决策**：新增 `src/app/crash.h/.cpp`，入口最早期安装：
  1. `std::set_terminate`（未捕获 C++ 异常）、`SetUnhandledExceptionFilter`（SEH 崩溃）、
     `_set_purecall_handler`、`_set_invalid_parameter_handler`；
  2. 崩溃时动态加载 `dbghelp.dll`（`LOAD_LIBRARY_SEARCH_SYSTEM32`，防劫持、不加依赖）写
     MiniDump 到 exe 同目录 `crash/LilithReader_<时间戳>.dmp`，另写 `last_crash.txt`
     （阶段标记 + 异常码 + 崩溃地址 + 日志尾部）；
  3. `running.flag` 运行中标记：正常退出删除；残留且无 `last_crash.txt` = 被强杀/断电，
     下次启动同样提示；
  4. 下次启动 `take_last_crash()` 读走标记（归档为 `.reported.txt`，只提示一次），复用既有
     通用确认弹窗（ADR-063）展示摘要，主按钮直接打开报告目录。
- **理由**：崩溃处理器里**不能用** `lr::log`（堆可能已损坏），只用 Win32 原生 API + 栈缓冲；
  处理器**只记录、不尝试恢复**——use-after-free / 数据竞争 / 栈破坏是未定义行为，任何
  "继续运行"的尝试都会把现场破坏得更难定位。`dbghelp` 动态加载使正常路径零新增依赖。
- **后果**：任何漏到进程顶层的故障都有转储与摘要；验收项"48 小时零崩溃、crash 目录为空"
  由此可判定。Debug 构建提供 `crash::debug_trigger()` 主动触发以验证整条链路，Release 不编译。

## ADR-081 应用层线程职责与异步结果代次契约（2026-10-06，架构加固）

- **背景**：迁移动能收口后复查发现，架构文档承诺的"UI 线程零磁盘、零阻塞"并未在所有路径落实：
  `session.cpp` 打开文档时在 UI 线程做 `file_exists`/`is_supported`，阅读位置在关闭文档、书签增删、
  删记录、退出时**同步** `save_state` 写盘；`platform.cpp` 剪贴板失败时 `Sleep(10)` 重试；
  `main.cpp` 退出时同步落盘。同时 app（`UiDoc`）、render（`DocState`/`DocPhase`）、`session.cpp`
  的 `g_*` 各持一套文档状态，异步结果靠 `request_id` 与 `g_doc.kind` 多处配合验收，
  存在"旧结果晚到污染新文档"的窗口。多数时候无感（文件小、本地盘），但网络盘、杀软、
  文件锁、损坏状态文件都可能让界面卡住。
- **决策**（本批只落地第 1 条的持久化部分与 ADR-083 document 边界；其余入 [计划](01-计划.md) 分批）：
  1. **UI 线程职责收窄**为"产生状态快照 + 投递命令 + 读取快照"，不再做任何磁盘访问（读或写）。
     阅读状态的写盘移交独立的持久化服务（ADR-082）；打开流程的文件**存在性**判定不再在
     UI 线程预检（那是磁盘 I/O），改由后台打开结果（`NotFound`）如实呈现；扩展名闸门是
     纯字符串策略、不涉及磁盘，保留在 UI 线程做即时拒绝（ADR-013）。
  2. **异步结果必须携带代次**：文档代次（打开/关闭推进）+ 请求代次。UI 只在少数验收点比对代次，
     不匹配即丢弃。render 层现有的 `DocState.id` 即请求代次，本批明确其语义并在注释中固化；
     文档代次的统一（SessionController）列为后续批次。
  3. **异步辅助请求有界化**：文本/图片/复制这类高频请求改"latest-wins + 有界"，不再无限 FIFO
     积压。本批**不实现**，列入计划后续批次（页内容请求已按页去重，保持不动）。
  4. 剪贴板的 `Sleep` 重试改为"下一帧重试"状态（见 [计划](01-计划.md) 遗留项）。
- **理由**：把"零阻塞"从口号变成可验收的契约；代次是跨线程结果归属唯一可靠的判据，
  "在哪个函数验收"比"在每个分支各判一次"更不易漏。
- **后果**：本批交付 ADR-082（持久化）与 ADR-083（document 边界）；状态模型统一、输入映射拆分、
  剪贴板重试改帧驱动等属后续批次，已在计划中列条目。不改变现有外部行为，只改变"在哪个线程做"。

## ADR-082 阅读状态异步持久化服务（2026-10-06，架构加固）

- **背景**：`save_reading_state()` 当前在 UI 线程同步 `encode_state` + 原子写盘，被关闭文档、
  书签增删、删除阅读数据、退出窗口调用。磁盘慢（网络盘、杀软扫描、文件锁）会卡 UI；
  而程序崩溃或被系统强杀时，最近阅读位置只可能停留在"上次显式保存点"，容易丢进度。
- **决策**：
  1. 新增模块 `lilithreader.persist`（`src/state/persist.ixx` + `persist.cpp`），持有
     `reader_state.bin` 路径与**一条独立工作线程**（与 render 工作线程并列，互不交互）。
  2. UI 线程只产快照：`request_save(const ReaderState&)` 在**调用线程**做纯序列化
     （`encode_state`，不碰磁盘）得到字节，交给服务；服务在**防抖窗口**（默认 1s，可注入）
     过去后于工作线程落盘。高频小改动（拖动、翻页）因此合并为一次写。
  3. 退出路径 `flush()`：阻塞至最近一次快照写完；服务析构同样 flush。`main.cpp` 的
     `WM_DESTROY` 与关闭文档路径改为"请求保存 + 退出 flush"。
  4. 为让服务能直接写字节，把 `reader_state` 的 `save_state` 拆为 `encode_state`
     （已有）+ 新的导出 `write_state_bytes(path, bytes)`；`save_state` 保留为二者的组合。
  5. 写失败经 `lr::log` 记录，并由 `last_save_failed()` 暴露（供将来 UI 提示）。
  6. **ReaderState 仍由 UI 线程独占**（身份解析、管理窗口不变）：服务只接受已编码字节，
     从不触碰 `ReaderState`，故两端无共享可变状态、无数据竞争。
- **理由**：磁盘 I/O 与 UI 解耦；防抖把高频改动合并；flush 保证退出不丢；编码留在 UI 线程
  避免跨线程共享 `ReaderState`。快照语义与 ADR-081 第 1 条一致。
- **后果**：崩溃/强杀最多丢 ~1s 内的进度（此前可能丢整段会话）；UI 不再因写盘卡顿。
  代价：进程多一条线程；退出时一次短暂阻塞（毫秒级）。新增 `tests/persist_test.cpp` 钉住
  防抖、flush、失败上报与析构 flush。

## ADR-083 document 层 MuPDF 边界函数化（PageBitmap）（2026-10-06，架构加固）

- **背景**：`document.ixx` 头顶铁律第 1 条要求"任何 `fz_*` 调用都必须被 `fz_try/fz_catch` 包住"，
  但 `PageBitmap::reset`（`fz_drop_pixmap`）、`Impl::drop_stext`/`destroy`（`fz_drop_stext_page`/
  `fz_drop_document`）都直接调用 `fz_*`；`PageBitmap` 的 `width/height/stride/samples` 访问器
  更是**每次调用都回调 MuPDF**。这些函数实际不抛错，但纪律成了"经验性假设"而非结构保证 ——
  换 MuPDF 版本、扩大异常处理范围或引入更多资源类型时，longjmp 可能穿透 C++ 对象生命周期。
- **决策**：
  1. 新增边界函数：`pixmap_attrs(ctx, pix)` 在 `fz_try` 内一次性读出 w/h/stride/samples/分量数，
     `fz_catch` 归零；`drop_pixmap_safe` / `drop_stext_safe` / `drop_document_safe` 以
     `fz_try/fz_catch` 覆盖对应 `fz_drop_*`。
  2. `PageBitmap::Impl` 在构造时快照像素属性；`width/height/stride/samples` 变为**纯访问器**
     （零 `fz_*` 回调），既合规又更快。
  3. 所有"销毁路径"（`PageBitmap::reset`、`Impl::drop_stext`、`Impl::destroy`）改走
     `drop_*_safe`；已处于 `fz_try/fz_always/fz_catch` 内的销毁调用保持原样（已在边界内）。
  4. 同步 `document.ixx`/`document.cpp` 头注释：说明属性访问器为快照、销毁集中在边界函数内。
- **理由**：把"通常不抛"的假设升级为结构性保证，集中评审点；不改变对外语义与零拷贝约定。
- **后果**：每页渲染多一次属性读取（相对光栅化可忽略）；`PageBitmap` 访问器无 MuPDF 回调。
  完整静态检查（扫描所有 `fz_*` 是否在边界内）本批未做，规则由"边界函数 + 代码评审"保证，
  见 [计划](01-计划.md) 遗留项。

## ADR-084 CI 扩展：Debug/Release 矩阵 + 安装包体积门禁（2026-10-06，工程）

- **背景**：PR CI（ADR-076）全绿后仍有两个无人验证的缺口。其一，**Debug 配置**从未在干净环境
  编译过——STL 迭代器检查、`_DEBUG` 分支、`crash::debug_trigger()`（ADR-080 只在 Debug 编译）
  全部依赖"本地记得跑"；其二，**安装包**（`installer\LilithReader.iss`）与体积预算（docs/05 §5）
  只在发版人工打包时才见分晓，"iss 与 app.rc 版本漂移""字体意外回全量"这类问题会在发布当天
  才暴露。
- **决策**：
  1. `build-and-test` 改 **Debug/Release 矩阵**；**Debug 只编不测**——`run_tests.ps1` 用自己的
     cl.exe 编译测试、不消费主工程产物，对 Debug 产物重跑回归没有信息增益，纯烧时间；Debug
     实例的价值在编译+链接期的断言与分支检查。诊断包 artifact 名带配置后缀（v4 不允许同名
     artifact 重复上传）。
  2. 新增 **installer** job（`needs: build-and-test`）：下载 Release exe artifact，**复用仓库
     自带的 `installer\build_installer.bat`** 打包（ISCC 路径探测与 exe 存在检查都在里面，
     不在 CI 另写第二套打包定义），产物过 `tests/check_installer_size.py` 体积门禁
     （**上限 35 MiB**）后上传 artifact。
  3. 上限 35 MiB 的依据：0.6.0 打包实测 24.9 MiB（对应裁剪前 40 MiB exe，docs/05 §5），
     字体裁剪后 exe 38.06 MiB、预计安装包约 23 MiB；35 MiB 的余量专防"字体意外回到全量"
     一类大回归（lzma2 后约 40 MiB 会触发），日常微膨胀不报警。检查脚本仅标准库、本地可跑，
     输出自带 `reconfigure(encoding="utf-8")`（不重蹈 ADR-076 勘误二的 locale 覆辙）。
- **理由**：两条都是"把纪律变成门禁"——Debug 编译期检查从"本地自觉"变"CI 必须绿"；体积从
  "docs/05 事后记录"变"超预算即红"。打包走 bat 维持单一打包定义；iss 内的编译期版本一致性
  校验（读 exe 版本资源对比 `MyAppVersion`）在 CI 上顺带成为版本漂移的自动防线。
- **后果**：每次 CI 多一个 Debug 编译实例（vcpkg 缓存命中后约等于一份编译时间）；安装包
  artifact 使 docs/04 的人工安装验证有了固定取材处；docs/05 §5 待 CI 首次实测后补充一行
  CI 环境数据。

## ADR-085 render 后台服务的内部组件边界与共享状态归属（2026-10-06，架构加固）

- **背景**：`Renderer::Impl` 已不是"渲染调度层"，而是一个大型后台应用服务：同时管文档生命周期、
  渲染、缩略图、全文检索、文本抽取、图片复制、LRU 缓存、D3D 纹理所有权、退役队列、工作线程
  调度与故障隔离。加新功能只能继续往 `Impl` 加字段和分支；页状态由 `Entry` 的
  `status / stale / manual_retry / auto_retries / failed_scale` 多个字段拼出，存在理论上不应
  出现的组合。这是外部复查报告 §五 第 4 步。
- **决策**：
  1. **单工作线程不变、外部 API 不变**。`render.ixx` 导出的类型与 `Renderer` 方法集保持不变，
     以把回归面压到最小；参数/返回值语义一律不动。
  2. `Renderer::Impl` 拆为五个**内部组件**：`TextureStore`（页/缩略图条目、字节记账、两段式
     退役队列、LRU 逐出、缓存统计）、`DocumentWorker`（`Document` 实例、文档快照、目录、
     视图变换旋转/配色）、`PageScheduler`（渲染请求/缩略图请求去重调度、tile 拆分、失败定格、
     资源档位）、`ContentService`（辅助请求队列与一次性结果槽）、`SearchJob`（检索代次、
     增量扫描、结果发布）。`Impl` 退化为"唯一互斥量/条件变量/工作线程 + 命令槽 + 按优先级分派"。
  3. **组件是同一实现单元（`render.cpp`）内的结构体，不设独立模块/子单元**。理由：D3D 纹理
     路径的自动化覆盖薄（测试用例传 `nullptr` 设备，纹理创建必失败），跨 TU 拆分线程与所有权
     的收益不抵竞态/悬垂风险；可脱离硬件的纯策略已由 `page_cache` / `page_state` 独立成模块。
  4. **共享状态归属**：唯一互斥量仍是 `Impl::mtx`（组件不各自持锁，`*_locked` 约定不变）；
     `Document` 实例归 `DocumentWorker`（仅工作线程访问）；纹理句柄与退役队列归 `TextureStore`；
     渲染/缩略图请求队列与资源档位归 `PageScheduler`；辅助请求与结果槽归 `ContentService`；
     检索作业与其代次归 `SearchJob`。
  5. **页状态机显式化**：`Entry` 的五个拼字段收进新纯模块 `lilithreader.page_state` 的
     `PageState`，以转移函数（`plan_render` / `on_loaded` / `consume_retry` / `set_failed` /
     `request_retry` / `on_evicted` / `on_invalidated` / `on_staled`）取代字段组合；
     `PageStatus` 随之迁入该模块，由 `render.ixx` 重导出以维持 `lr::PageStatus` 可见。
     UI 侧快照 `PageSlot::status` 由 `PageState` 派生，不再单独维护一份。
- **理由**：把"哪些状态归谁、转移在哪发生"从"注释约定"变成结构保证；检索/内容/纹理/文档四类
  状态的修改点各自收敛，加功能落到对应组件而非继续摊在 `Impl`。显式状态机让"手动重试 / 自动
  重试 / 旧纹理保留"成为可单测的转移语义（`tests/page_state_test.cpp`），而非散落的字段判断。
- **后果**：`render.cpp` 仍是单一实现单元、体量相近（无新翻译单元），但内部职责分区；新增
  `lilithreader.page_state` 纯模块与单测。不改变任何外部行为、线程模型与锁纪律；文档代次统一
  （ADR-081 第 2 条）仍留第三批（SessionController）。

## ADR-086 应用层单一会话状态源与异步结果代次验收（AppContext + SessionController）（2026-10-06，架构加固）

- **背景**：外部复查报告 §五 第 5 步指出应用层"三套状态模型"——app 的 `UiDoc`、render 的
  `DocState`/`DocPhase`、`session.cpp` 的一堆 `g_*` 各持一套文档状态；异步打开/认证结果靠
  `g_doc.request_id` 与 `g_doc.kind` 在 `poll_document` 里多处配合验收，一旦再加异步请求
  （如关闭与打开交错）就容易出现"旧结果晚到污染新文档"的窗口。结构上，`app_internal.h`
  有约 130 个跨 TU 可变的 `inline` 全局，状态归属靠注释约定而非结构保证，两个巨型 TU
  （`ui.cpp` / `session.cpp`）里任何函数都能读到任何状态。
- **决策**（本批落地第 1、2 条；第 3、4 条的范围与后续见 [路线图 §4](06-架构加固路线图.md)）：
  1. **跨 TU 状态收进 `AppContext`**：`app_internal.h` 里所有跨 TU 可变的 `inline` 全局
     移入 `struct AppContext`，以单例 `inline AppContext g_app` 暴露。类型/常量/函数声明
     保持原位；`px()` / `ui_scale()` / `gap_ratio_pref()` 等内联辅助移到 `g_app` 之后。
     这是一次**纯迁移**（逐处 `g_x` → `g_app.x`），不改任何行为。
  2. **单一会话状态源 `SessionController`**：文档状态机（`UiDoc`）、身份（`DocIdentity`）、
     阅读数据（`ReaderState` 与持久化服务）、阅读位置恢复、视图变换（旋转/纸张方案）、
     逐页尺寸、目录、密码框状态收进 `AppContext::session`（`SessionController`）。
     它对外提供状态机方法：`open` / `close` / `poll` / `reset` / `enter_reading` /
     `submit_password` / `save` / `resolve_identity`。UI 层与渲染层都只是它的**投影**
     （UI 只读快照，渲染经 `Renderer` 队列）。`app_internal.h` 原有的自由函数
     （`request_open_document` / `close_document` / `poll_document` / `submit_password` /
     `save_reading_state` / `reset_doc_state`）保留为**薄包装**，外部 API 与调用点不变。
  3. **异步结果代次在统一处验收**：新增**文档代次** `session.doc_gen`（每次 `open` / `close`
     推进）与既有的**请求代次** `UiDoc::request_id`（`Renderer` 的命令序号）。打开/认证
     请求发出时把两枚代次一起记入 `UiDoc`；`SessionController::poll()` 是**唯一**验收点，
     只在"快照 `id` == 请求代次 且 请求发出时的文档代次 == 当前文档代次"时才落定结果，
     否则原样丢弃。这落实 ADR-081 第 2 条：代次是跨线程结果归属唯一可靠的判据，
     "在哪个函数验收"比"每个分支各判一次"更不易漏。
  4. **本批不拆 UI 绘制模块**：`ui.cpp` 的绘制模块化、以及 InputBindings / ViewMotion /
     TextInteraction / SearchController / SettingsController 的独立拆分留待本批后续切片
     （路线图 §4 已明确 UI 绘制模块化允许留尾到第五批）；本批先把状态**归属**立起来，
     使这些拆分有明确的宿主。
- **理由**：把"状态归谁、异步结果在哪验收"从注释约定变成结构保证——`SessionController`
  是文档状态的唯一写入口，UI 读的是它的快照（投影）；`AppContext` 让跨 TU 可变状态的
  全集可见、可枚举。两者都不改变线程模型与外部行为，回归面靠"纯迁移 + 单点验收"压到最小。
- **后果**：无新翻译单元，`app` 仍是"普通 TU + 内部头"；`app_internal.h` 从"散落全局"
  变为"一个容器 + 若干子状态"，为后续按职责拆分提供接缝。代价是约 130 个全局各改一次
  引用写法（纯机械、编译器可校验）；`SessionController::poll()` 取代 `poll_document()`
  的分散判据，行为保持不变。

## ADR-087 应用层会话侧控制器切片：独立 TU 与单向依赖（2026-10-06，架构加固）

- **背景**：ADR-086 把跨 TU 状态收进 `AppContext` 与 `SessionController`，但 `session.cpp`
  （≈1600 行）仍把命令表/按键绑定、视图动效、文本交互、全文搜索与文档状态机混在一个 TU 里，
  任何函数都能读到、改到任何状态。ADR-086 第 4 条把五个控制器与 UI 绘制模块化的独立拆分
  留作本批后续切片，但**未定 TU 边界与依赖方向**。
- **决策**：
  1. **会话侧四个控制器各自成 TU**：命令/按键绑定 → `input_bindings.cpp`；视图动效 →
     `view_motion.cpp`；文本交互/剪贴板 → `text_interaction.cpp`；全文搜索 → `search.cpp`。
     `session.cpp` 只保留 `SessionController`（文档状态机/身份/阅读数据/阅读位置）、视图变换与
     逐页尺寸、画布输入映射、缩放防抖与渲染请求。
  2. **状态归属不变**：跨 TU 可变状态仍在 `AppContext`（单例 `g_app`，ADR-086）；切片只搬函数、
     不搬状态，`g_app.session` 仍是会话状态的唯一真源。
  3. **单向依赖、互不 include**：app 层各 TU 一律只 `#include "app_internal.h"`，切片之间只经
     本头声明的自由函数互调，不互相 `#include`。依赖方向 `main → { platform, session, ui }`；
     `ui → { platform, session, input_bindings, view_motion, text_interaction, search }`。
  4. **对外 API 不变**：被搬动的自由函数仍是 `app_internal.h` 里的原声明，调用点零改动，
     故这是**纯迁移**，行为与线程模型均不变。
  5. **`ui.cpp` 绘制模块化与 SettingsController 留待第五批**：`ui.cpp` 被多条源文本门禁脚本
     （`check_menu_width.py` / `check_theme_precedence.py`）按文件路径与函数名读取，拆分须同步
     改门禁，其风险/收益不属于本批的最小切片（路线图 §4 已允许留尾第五批）。
- **涉及文件**：`src/app/session.cpp`（拆出四段）；新增 `src/app/{input_bindings,view_motion,
  text_interaction,search}.cpp`；`src/app/app_internal.h`（文件划分与依赖方向注释）；
  `src/LilithReader.vcxproj`（源文件清单）。
- **理由**：这是"纯迁移"——不改行为、不改声明，符号错误由编译器全量校验，回归面被压到最小；
  每个 TU 单一职责后，后续给某一控制器加功能不再牵动整份会话代码。
- **后果**：`session.cpp` ≈1600 → ≈670 行，四个新 TU 合计 ≈980 行；无新头部、无新状态、
  无新线程。`tests/run_tests.ps1` 不编译 app 层，源文本门禁只读 `platform.cpp` / `ui.cpp`，
  故两者均不受影响；SettingsController 与 UI 绘制模块化的接缝保留在 `ui.cpp`。

## ADR-088 显示设备丢失的处置：如实告知并干净退出，不重建（2026-10-07，架构加固）

- **背景**：`Present` 或 `ResizeBuffers` 返回 `DXGI_ERROR_DEVICE_REMOVED/RESET` 时，
  `Graphics::render_frame` 只置 `device_lost` 标记并停止呈现，注释称"由界面如实告知用户"，
  但**界面从未读过该标记** —— 实际表现是窗口定格在最后一帧、无任何提示，用户只能强杀进程。
  这是"注释承诺了、实现没落地"的缺口（外部复查报告 §五 第 6 步）。
- **决策**：
  1. **不重建** device/swapchain。重建必须连带让 ImGui DX11 后端 `InvalidateDeviceObjects` /
     `CreateDeviceObjects` 重建字体纹理，并把 `Renderer` 持有的全部 D3D 纹理重挂到新设备上，
     失败面覆盖整个渲染层；而本项目的纪律是"开发中不实际运行软件"，该路径**无法验证**，
     贸然实现等于引入一条没人跑过的崩溃面。
  2. 改为**如实告知 + 干净退出**：主循环帧尾检测到 `device_lost` 且未提示过时，用**原生弹窗**
     （`MessageBoxW`；此时 ImGui 已画不出来）说明原因并告知重启；随后 `save_reading_state()`
     更新阅读位置快照、`PostQuitMessage` 走正常退出路径（持久化服务 flush，不丢进度）。
  3. `device_lost_notified` 保证只提示一次；原始 HRESULT 与 `GetDeviceRemovedReason` 继续写日志供追溯。
- **理由**：设备丢失是罕见的高破坏性事件（驱动更新/重置、GPU 被移除），此刻进程已无法呈现任何界面，
  能让用户"看到原因、保住数据、干净重来"就达到了可接受的下限；重建是收益不确定、风险与验证成本都高的
  大改，应作为独立批次评估（本批不做）。
- **后果**：设备丢失从"静默定格"变为"明确告知 + 退出"；无新增依赖、无新线程。代价是概率极低的
  一次进程退出（用户需重启），换取不引入未经验证的重建路径。

## ADR-089 失败提示体系：打开 / 渲染 / 落盘三类失败的呈现契约（2026-10-07，架构加固）

- **背景**：用户可感知的失败分散在三处，此前表现不一致：打开失败经 `describe(DocError)` 画在
  画布引导页（已有）；单页渲染失败显示"渲染失败 · 点击重试"占位（已有，ADR-031）；而
  **落盘失败**（`PersistService::last_save_failed()`）只写了日志，UI 完全不知情 ——
  阅读进度静默丢失，用户无从察觉（外部复查报告 §五 第 6 步）。
- **决策**：三类失败各归其位，形成一致的"呈现面"契约：
  1. **打开失败**：`UiDoc::error` 经 `lr::describe` 呈现在画布引导页（保持既有行为）。
  2. **渲染失败**：页占位"渲染失败 · 点击重试"，保留旧纹理（保持既有行为，ADR-031）。
  3. **落盘失败**：帧首从 `persist->last_save_failed()` 采样到 `g_app.persist_failed`；
     首次出现弹一次 toast 提醒，并在**状态栏常驻**一条告警色文案（"阅读数据保存失败"），
     直到下一次写盘成功（服务复位 `failed`）。日志仍是唯一的细节来源（含路径）。
  4. **文案准确性**：MuPDF 把"压缩方式不受支持"（如 MOBI 的 HUFF/CDIC）也抛成
     `FZ_ERROR_FORMAT`；`document::classify` 在该分支读消息特征词，命中 `unknown compression`
     时改判 `Unsupported`（"暂不支持的格式"），不再误报"文件已损坏"（见 ADR-090）。
- **理由**：失败提示的**呈现面**（画布 / 页 / 状态栏）按"错误影响的最小作用域"选取 ——
  打开失败影响整份文档、渲染失败只影响一页、落盘失败不打断阅读但必须持续可见；用状态栏常驻而非弹窗，
  避免每次翻页都弹一次。分类修正把"技术原因"如实映射到用户看得懂的措辞。
- **后果**：落盘失败不再静默；`g_app.persist_failed` 是唯一新增状态。无新界面类型，复用既有 toast
  与状态栏。新增 `doc_test` 用例钉住 `mobi_huffcdic.mobi → Unsupported`。

## ADR-090 MOBI 支持边界：保留声明，限定压缩方式（2026-10-07，架构加固）

- **背景**：README 一直声明支持 MOBI，但**从未有真实样本验证**（外部复查报告 §五 第 6 步）。
  实测（构造 TEXtREAd/PalmDOC 样本 + `mupdf_probe`）：MuPDF 1.26.10 编译时 `FZ_ENABLE_MOBI=1`、
  MOBI 处理器已注册，**未压缩与 PalmDOC 压缩可正常打开**（`FZ_META_FORMAT = "MOBI"`）；
  但 **HUFF/CDIC 压缩（Kindle 常见，17480）未实现**，会以 `unknown compression method` 拒绝。
- **决策**：
  1. **保留 MOBI 支持声明**，但在 README「已知问题」如实交代压缩方式的边界（不是降级为不支持）。
  2. 新增**格式合法的**构造样本 `real.mobi`（无压缩）、`real_palmdoc.mobi`（PalmDOC）与边界样本
     `mobi_huffcdic.mobi`（HUFF/CDIC），在 `doc_test` 断言前二者 Open 且 format 含 "MOBI"、
     后者 `Unsupported`（见 ADR-089 第 4 条的分类修正）。
  3. `FormatFamily` / `extension_family` 暂不为 MOBI 增设族（`classify_format` 仍返回 Unknown，
     与扩展名一致即视为相符）；扩展名策略归一属第五批。
- **理由**：不做无法验证的声明——先把"哪些 MOBI 真能打开"钉进自动化，再据实修改文案；
  HUFF/CDIC 是 MuPDF 的固有限制（非本项目策略），归为"暂不支持的格式"比"文件已损坏"诚实。
- **后果**：`tests/samples/` 增加三个 MOBI 样本；README 增一条已知问题；新增 `doc_test` 三例。
  真实 Kindle 生成的多章节 MOBI（HUFF/CDIC）仍打不开，属已知边界。
