## ADR-001 自研画布替代 ImPlot（2026-10-05）

- **背景**：Lilith 的 PDF 查看器用 ImPlot 当网格画布（多列并列 + 缩放查看）。
- **决策**：不引入 ImPlot 作产品画布，用纯 ImGui + ImDrawList 自研（缩放/平移/网格布局自管）。
- **理由**：缩放手感完全可控（以鼠标为中心的平滑缩放、惯性滚动）；网格、单列滚动、双页对开统一一套代码；减少一个依赖。
- **后果**：需自写约 300~500 行交互代码；ImPlot 仍下载引入，作为交互参考基准与调试可视化备用。

## ADR-002 D3D11 替代 D3D12（2026-10-05）

- **决策**：图形后端用 D3D11（FLIP_DISCARD 翻转模型）。
- **理由**：初始化与纹理管理大幅简化；单窗口阅读器性能与 D3D12 无差别；降低崩溃面（Lilith main.cpp 中 D3D12 的长 RAII 释放链即复杂度代价）。
- **后果**：放弃 D3D12 独占的特性（无需理会）。

## ADR-003 保留 MuPDF 多格式支持（2026-10-05）

- **决策**：MuPDF 静态链接，保留 PDF/epub/mobi/fb2/cbz/xps 多格式。
- **理由**：MuPDF C API 已有成熟使用经验；多格式是差异化功能。
- **风险**：epub/mobi 排版质量不完美，PDF 永远最高优先级；AGPL 协议——自用/开源无碍，闭源商用需商业授权或换 PDFium（Core 层接口预留抽象）。

## ADR-004 C++20 modules 组织（2026-10-05）

- **决策**：沿用 Lilith 的 `.ixx` modules 风格（stdcpp23，`import std` 可用）。
- **理由**：与现有代码风格一致，原模块搬运改动最小；单人 Windows 项目无兼容性顾虑。

## ADR-005 去除 OpenCV 中间层（2026-10-05）

- **决策**：渲染管线改为 MuPDF RGBA pixmap → 直接上传 GPU 纹理，删除 `pixmapToMat`。
- **理由**：原管线含一次全页 RGBA→BGR 逐像素拷贝，纯浪费；体积也大幅缩小。

## ADR-006 线程模型规范化（2026-10-05）

- **决策**：废弃"双 Document（两个 fz_context）绕线程限制"的做法，改为渲染线程 `fz_clone_context`（或 fz_locks），优先单渲染线程串行化。
- **理由**：原方案是脆弱的隐式约定，扩展即踩坑。

## ADR-007 静态链接单 exe（2026-10-05）

- **决策**：vcpkg manifest + `x64-windows-static` triplet + MSVC `/MT`，产出单文件 exe（目标 < 30MB）；UI 字体子集化嵌入 exe（约 1.5~2MB 常用汉字 + Latin，imgui_freetype 渲染），可选运行时 fallback 系统 msyh.ttc 补生僻字。
- **理由**：便携、零依赖、`exe <路径>` 直接打开。

## ADR-008 最新工具链（2026-10-05）

- **决策**：使用 VS 18 (2026) Community，PlatformToolset v145（MSVC 14.51），不使用 VS2022/v143。
- **理由**：机器已装最新版本（14.44/14.51 并存，取 14.51）；C++23 `import std` 支持更完善。

## ADR-009 MuPDF 异常模型约束：setjmp/longjmp，不是 C++ 异常（2026-10-05，Phase 2）

- **背景**：`mupdf/fitz/context.h` 中 `fz_try/fz_catch` 定义为
  `if (!fz_setjmp(*fz_push_try(ctx))) …`，即 C 的 `setjmp/longjmp`。
  MuPDF 以 C 编译（vcpkg 端口 glob `source/**/*.c`），不存在任何 C++ 异常互通。
- **决策**：在 `src/document/document.cpp` 中强制两条纪律，并在文件头写明：
  1. **`fz_try` 块内绝不构造带析构函数的 C++ 对象**（`std::string`/`std::vector`/`std::optional`…），
     跨越 `fz_try` 存活的对象同样禁止——`longjmp` 不调用析构函数，会直接泄漏。
     所有需要 C++ 对象的准备工作放在 `fz_try` 之外，块内只出现 `fz_*` 裸指针与 POD 缓冲（`char[]`）。
  2. 跨 `fz_try`/`fz_always`/`fz_catch` 使用的局部变量一律用 `fz_var()` 标记
     （MuPDF 官方要求的防寄存器优化破坏手段）。
- **附带修正**：`fz_drop_device` **不会**隐式关闭设备（device.h 明确写 "This is NOT called
  implicitly on fz_drop_device"）。Lilith 原版 `createPageDisplayList`/`renderPage` 都漏了
  `fz_close_device`，Phase 2 一并修正。错误路径上 `fz_always` 内不调用可能抛异常的
  `fz_close_device`，直接 drop（MuPDF 会给出 "dropping unclosed device" 警告，不泄漏）。
- **后果**：新增 fz 调用时必须遵守上述两条，否则是"能跑但会漏内存/偶发错值"的隐性缺陷。

## ADR-010 vcpkg 依赖落地：libmupdf 静态端口 + 安装根目录移出含空格路径（2026-10-05，Phase 2）

- **背景**：
  1. 项目路径 `F:\programs\Lilith Reader` **含空格**；vcpkg 的 meson 端口（harfbuzz）生成
     链接命令行时未给 `/libpath:` 加引号，路径从空格处被截断成两个参数 → `LNK1181`。
  2. vcpkg 的 MSBuild 集成把 triplet 拼了两次：传给 vcpkg 的 `--x-install-root` 已含
     triplet（`…\vcpkg_installed\x64-windows-static\`），vcpkg 内部（`scripts/ports.cmake`）
     又拼一次 `CURRENT_INSTALLED_DIR = ${_VCPKG_INSTALLED_DIR}/${TARGET_TRIPLET}`；
     而 MSBuild 侧 `_ZVcpkgInstalledDir` 的默认值里已经带了 triplet，导致实际写入
     `…\x64-windows-static\x64-windows-static\`，而 MSBuild 读 include/lib 也走
     `_ZVcpkgCurrentInstalledDir = VcpkgInstalledDir + triplet`，两侧错位。
- **决策**：
  - 依赖端口用 vcpkg 官方 `libmupdf`（1.26.10，Windows 下强制静态库），覆盖
    PDF/XPS/HTML(reflow → epub/mobi/fb2)/CBZ/SVG，与 `x64-windows-static` + `/MT` 完全匹配。
  - 在 vcxproj 显式设 `<VcpkgInstalledDir>F:\programs\.Environment\vcpkg-roots\LilithReader</VcpkgInstalledDir>`
    ——**不含空格、不含 triplet**。于是"传给 vcpkg 的安装根"与"MSBuild 读取的
    `根\ triplet`"两种口径同时成立，两个问题一并消除。
  - 镜像 libmupdf 端口的 **PRIVATE** 编译定义（`FZ_ENABLE_ICC=0` 等）到本项目。
    该端口没有把这些宏传播给消费方，而 `FZ_ENABLE_ICC` 会影响 `fz_context` /
    `fz_colorspace` 的结构体布局。当前代码只通过指针传递这些不透明类型、未访问任何
    受保护成员，故今天无实际暴露；镜像取值属于低成本消除隐患。
- **后果**：vcpkg 安装产物在项目之外（`F:\programs\.Environment\vcpkg-roots\LilithReader`），
  项目内不再生成 `vcpkg_installed/`（`.gitignore` 条目保留以防回退）。升级 libmupdf 端口后
  需复核其 PRIVATE 定义是否变化。

## ADR-011 gumbo 覆盖端口：修正上游归档哈希（2026-10-05，Phase 2）

- **背景**：构建时 `gumbo` 端口报 `download … had an unexpected hash`。实测
  codeberg 的 `https://codeberg.org/gumbo-parser/gumbo-parser/archive/0.13.2.tar.gz`
  与 `refs/tags/0.13.2.tar.gz` 两个 URL 返回同一份、`gzip -t` 通过的归档，
  SHA512 = `9f5996…`，而 vcpkg 内置端口钉的是 `1513e8…`。
  即 Forgejo 的 tag 归档**不是字节稳定的**（tag 重指或服务端重新打包都会改变字节），
  vcpkg 里钉的哈希已过期——非网络问题（手工完整下载可复现同一哈希）。
- **决策**：新增覆盖端口 `overlay-ports/gumbo/`（配 `vcpkg-configuration.json` 注册），
  改为按**提交号** `322c54c178590ba42b8b04e8c0e4840595a1f717` 拉取自包含归档（锚定
  不可变对象），并把 SHA512 换成实测值；`port-version` 递增到 1。
- **备选与放弃**：全局关掉下载校验（`--x-no-verify-downloads`）会削弱全部依赖的
  供应链校验，不可接受；降级到 Google 镜像上的 gumbo 0.10.1 属于无必要降级。
- **后果**：新增 3 个端口文件 + 1 个配置文件；上游若再次改动归档需重算哈希并递增
  port-version。若将来 vcpkg 内置端口自行修正，可删除覆盖端口。维护说明写在
  `overlay-ports/gumbo/portfile.cmake` 头部。

## ADR-012 文档核心的线程归属、零拷贝渲染结果与错误码（2026-10-05，Phase 2）

- **决策**：
  1. **线程归属**：`fz_context` 以 `nullptr` locks 创建（单线程上下文），`Document`
     实例**非线程安全**，约定"一个实例只属于一个线程"。Phase 2 起 UI 线程永不触碰
     `fz_*`，打开动作经一个专用工作线程串行执行；ADR-006 里"线程池 + `fz_clone_context`"
     的路留待确有并发渲染需求时再启用。
  2. **零拷贝**：`render_page` 返回 `PageBitmap`（RGBA8，4 字节/像素，行主序），
     直接指向 `fz_pixmap` 内部缓冲，可直接上传 `DXGI_FORMAT_R8G8B8A8_UNORM`，
     全程无像素拷贝（落实 ADR-005）。清屏用不透明白底（`fz_clear_pixmap_with_value(…, 0xFF)`）：
     目标 alpha 恒为 255，页面内容以 SRC_OVER 合成后 alpha 仍为 255，无需反预乘。
  3. **错误码**：`DocError { Ok, NotFound, NotOpen, Unsupported, NeedsPassword, Corrupt,
     TooLarge, Internal }`，分类优先用 MuPDF 的 `fz_caught()` 错误码，仅在
     `FZ_ERROR_GENERIC` 时回退到消息特征（加密 PDF 走的就是 GENERIC + "password"）。
     任何 `fz_*` 失败都以错误码出模块边界，不逃逸。
  4. **尺寸钳制**：`render_page` 接受单边像素上限（默认 8192），超限时等比下调实际
     scale，并通过 `PageBitmap::effective_scale()` 告知真实值——只缩不放，保证不 OOM。
  5. **PIMPL 隔离**：`fz_*` 类型完全不出现在模块接口，为换 PDFium 留出解耦（ADR-003）。
  6. **context 共享所有权**：MuPDF 没有 `fz_keep_context`（context 不可引用计数），
     而释放 `fz_pixmap` 必须用创建它的 context。若 `PageBitmap` 只存裸 `fz_context*`，
     一旦比 `Document` 活得久就是 use-after-free。因此 `fz_context` 由
     `shared_ptr<CtxHandle>` 持有，`Document` 与 `PageBitmap` 各持一份，
     **ctx 必定后于所有位图析构**，从结构上消除悬垂指针（而非依赖"调用方注意顺序"的约定）。
     代价：Document 关闭后若仍有位图存活，ctx（及其内部 store，上限 128MB）会延后释放。
- **已知取舍**：UI 线程为即时反馈仍会做 `GetFileAttributesW` 之类的元数据调用（微秒级、
  不读文件内容）；网络路径下可能变慢，属可接受的有界例外。Phase 3 起并入调度层的
  任务队列后再统一评估。

## ADR-013 格式闸门用扩展名白名单，而不是"全交给 MuPDF"（2026-10-05，Phase 2）

- **背景**：`fz_register_document_handlers` 实际还会注册 img（png/jpeg 嗅探）、html/xhtml、
  gz 等处理器。若一律交给 MuPDF，拖入 `.png` 会当成文档打开、`.gz` 也可能被接受，
  与 README 承诺的格式集合不符，且行为不可预测。
- **决策**：`utils` 里的扩展名清单（pdf/epub/mobi/fb2/cbz/xps）作为**策略闸门**：
  不在清单内直接判"暂不支持"，不进后台线程。清单内的文件再交给 MuPDF，
  此时 `DocError::Unsupported` 仅用于"后缀对但内容不对"的情况。
- **理由**：行为可预测、与文档承诺一致、UI 反馈无需线程往返。
- **后果**：想放开更多格式只需改 `utils.ixx` 里的一张常量表；若将来做"任意格式"开关，
  闸门处留一个入口即可。

## ADR-014 改名为受支持扩展名的图片，按内容当单页文档打开（2026-10-05，Phase 2 修订）

- **背景**：ADR-013 的后果里写"后缀对但内容不对"→ 报损坏，人工验证项 2-8 也据此要求
  "PNG/JPG 改名 .pdf 必须报损坏"。实测（Phase 2 手工验证）发现 MuPDF 会按内容嗅探，
  一张 PNG 改名 `.pdf` 会被 img 处理器接走，正常打开成 1 页文档，不报任何错。
- **决策**：**接受这一行为**，为此专门做内容签名比对（magic 白名单）不值当：
  ① 阅读器多支持一种"单页图片文档"对用户只有好处，没有正确性损失；
  ② txt 改名 `.pdf` 依然会报损坏——MuPDF 没有纯文本处理器，"能打开"不等于"什么都能开"，
     策略闸门仍然有效；
  ③ 内容签名比对会引入"用户明明有张图却打不开"的负面体验，以及一张需要长期维护的
     magic 表（PDF 变体、EPUB 的 zip、MOBI 的 PDB 头各有各的偏移）。
- **边界（要说清的三条）**：
  1. 闸门仍是**扩展名**白名单：原生 `.png` / `.jpg` / `.txt` 一律"暂不支持"，不进后台线程；
     只有"图片被改名成受支持扩展名"才会走内容嗅探这条路。
  2. 于是任何文件只要 MuPDF 认得出（图片、html 等），改名后都可能被打开——
     这是**有意**的宽松，不再视为缺陷。
  3. 不引入新的 `DocError`，`Corrupt` 只用于"MuPDF 也认不出"的情况（空文件、截断、
     纯文本、无效 zip）。
- **对既有文档的修订**：ADR-013「后果」中"后缀对但内容不对即报损坏"的表述作废；
  `docs/04-人工验证.md` 的 2-8 判据已同步改为"应能正常打开"，2-10（纯文本改名）保留
  "报损坏"作为兜底验证。
- **后续修订**：本 ADR 的「边界 3」（不引入新 `DocError`）已被 **ADR-016** 取代 ——
  归档类错配（zip 图集冒名单文档）必须拒绝。其余内容仍然有效。

## ADR-015 用 MuPDF 自己的识别结果做实测，而不是自己写 magic 表（2026-10-05，Phase 2）

- **背景**：要做"内容与扩展名是否相符"的判定，先得知道 MuPDF 到底把文件认成了什么。
  MuPDF 公开 API 里唯一能问出这件事的就是 `FZ_META_FORMAT` 元数据，但各处理器实现不一，
  必须先摸清实测值（哪些格式会上报、上报成什么字符串、查不到时怎么办）。
- **调研方式**：项目纪律不允许"开发中运行软件做测试"，但**允许自动化测试**。因此写了
  一次性探针放在 `build/mupdf-probe/`（该目录被 gitignore，不进仓库）：① `make_samples.py`
  用 Python 合成 20 余个样本（合法 PDF/EPUB/FB2/XPS/CBZ、图片与 zip 的各种改名组合、
  空文件、截断文件）；② `probe.cpp` 直接调 MuPDF 打印 `FZ_META_FORMAT`/页数/首页尺寸；
  ③ `probe2.cpp` **链接项目自己的 `lilithreader.document` 模块**，对同一批样本跑真实的
  `Document::open()`。要复现，按下面表格重建样本即可。
- **决策**：判定依据用 `fz_lookup_metadata(doc, FZ_META_FORMAT)`（MuPDF 各处理器上报的
  格式串），**不自己写内容签名表**。实测值（1.26.10）：

  | 样本 | MuPDF 上报 | 页数 |
  |---|---|---|
  | 正常 PDF / EPUB / FB2 / XPS | `PDF 1.4` / `EPUB` / `FictionBook2` / `XPS` | 正确 |
  | 正常 CBZ（zip 图集） | `zip`（归档格式名，不是 "cbz"） | 图片条目数 |
  | PNG 改名 `.pdf` / `.epub` / `.cbz` | `Image` | 1 |
  | EPUB 改名 `.pdf` / `.xps` | `EPUB` | 正确 |
  | FB2 改名 `.epub` | `FictionBook2` | 正确 |
  | **zip 图集改名 `.epub` / `.pdf` / `.fb2`** | **`zip`** | **图片条目数（假的）** |
  | zip 改名 `.cbz`（内含 PDF 或 txt） | `zip` | **0** |
  | 纯文本改名 `.pdf` / 空文件 / 截断 PDF | 打开失败 | — |
- **识别机制（为什么会出现上面这些"能打开"）**：MuPDF 给每个处理器同时算内容分与
  扩展名分：`recognize_content` 的内容分可达 25~200，而扩展名命中只给 **1** 分（弱信任），
  两者都命中才是 `100+内容分`。于是"内容分 25 的 CBZ"会压过"扩展名分 1 的 EPUB"，
  zip 图集就这样以漫画身份被打开。详见 `source/fitz/document.c` 的
  `do_recognize_document_stream_and_dir_content`。
- **理由**：① 该元数据是 MuPDF 的权威结论，比自己嗅探字节准确、且不随格式演进腐化；
  ② 处理器没实现该元数据时返回 `-1`，天然提供了"无法判定 ⇒ 不拦"的保守回退；
  ③ 顺带得到 `DocumentInfo::format`，UI 能如实显示"实际格式"，比只显示扩展名更诚实。
- **后果**：`document.ixx` 暴露 `format_matches_extension()`（纯提示用）；判定与提示共用
  同一张"格式族"映射表，位于 `document.cpp`；`utils.ixx` 的扩展名白名单仍需同步维护
  （`.mobi` 等未实测格式串的扩展名一律"不判定"）。

## ADR-016 内容优先：能认出格式就打开，只拦"归档冒充单文档"（2026-10-05，Phase 2）

- **背景**：ADR-014 的宽松与 ADR-015 的实测共同暴露了一个口子：内容能认出来就照认出的
  格式打开（图片、改名文档都无害），但**归档（zip/tar）冒充单文档**是有害的 ——
  CBZ 处理器把归档条目当页，于是 zip 图集改名 `.epub` 会显示"2 页电子书"，
  用户完全被误导；Phase 3 渲染时还会得到一堆与预期无关的图片。
- **决策**：**内容优先，只拦会骗人的**：
  1. 能识别出格式 ⇒ 打开，不管扩展名写什么；UI 在"扩展名与实际不符"时如实标注
     （`已打开 · 实际格式 EPUB（扩展名 .pdf 不符）`）。图片改名、文档互相改名都属于这类。
  2. 拒绝只有两种情形，都归入新的 `DocError::Mismatched`（中文文案
     **"这是压缩包，不是单个文档"**）：
     - 实际是 `zip`/`tar` 归档，而扩展名不是 `.cbz`；
     - 扩展名是 `.cbz`（归档类），但归档里一个可显示图片页都没有（页数 0）。
  3. 连 MuPDF 都认不出的（空文件、截断、纯文本改名 `.pdf`、坏 zip）仍是
     `DocError::Corrupt`，文案不变。
  4. 两侧任一无法判定时一律放行（不设"扩展名契约"，避免误伤）。
- **理由**：与用户口径一致 ——"能认出格式就无所谓后缀，除非有影响"。"有影响"的判据取
  "页数/内容类别会被处理器凭空编造"，即归档类；其余错配内容能如实呈现，拦下来只是添堵。
- **代价**：`DocError` 增加一个枚举值（`Mismatched`），`DocumentInfo` 增加 `format` 字段；
  UI 的 `draw_failed` 为 `Mismatched` 专门给一句中文建议
  （"若是图片集，请把扩展名改回 `.cbz`"）。C++ 侧所有 `switch (DocError)` 都必须覆盖新值
  （`to_string` / `describe` 已补；GCC/Clang 下请留意 `-Wswitch`）。
- **已知缺口**：`.mobi` 的上报格式串未实测（无法程序化构造样本），故 `.mobi` 不做任何
  判定 —— 极端情况下"zip 改名 `.mobi`"仍会以漫画打开。把关方式：真实 `.mobi` 用例
  （已归档，见 [archive/2026-10/phase2-文档核心.md](archive/2026-10/phase2-文档核心.md) 2-16h）+ 该缺口记录在此。
- **未做（留待决策）**：扩展名白名单（ADR-013）仍会拦下**原生** `.png`/`.jpg`，因此按
  "内容优先"的口径看来，图片要么改名才能在阅读器里打开、要么彻底打不开，两者都不理想。
  可选后续：把图片扩展名加入白名单，甚至把闸门改成"不看后缀、直接嗅探 + 本 ADR 的拒绝规则"。

## ADR-018 画布坐标模型与缩放语义（2026-10-05，Phase 3）

- **背景**：自研画布需要一套可预测、可单测的坐标/缩放约定。架构文档 §2.1 只列了
  `zoom/scroll_y/columns/page_gap/fit_width`，未定义坐标单位、留白语义与缩放锚点算法。
- **决策**：
  1. 文档内部坐标以**点（pt）**为单位；`zoom` 表示"每点多少屏幕像素"
     （`zoom = 1.0` 即 72dpi 原始尺寸）。屏幕坐标 = 内容点坐标 × zoom + 原点偏移。
  2. `margin_px`/`gap_px` 是**屏幕像素**常量，换算进文档坐标时除以 zoom
     （`margin_pt = margin_px / zoom`），使缩放时页间距在视觉上恒定。
  3. `fit_width` 模式下 zoom 派生：
     `zoom = (viewport_w − 2·margin_px − (cols−1)·gap_px) / (cols · max_page_w_pt)`。
     该式保证 `content_width_px` 恒等于 `viewport_w`（实测断言见 canvas_test）。
  4. 内容窄/矮于视口时**居中**；否则按 scroll 偏移。`scroll_x/scroll_y` 钳制到
     `[0, content − viewport]`。
  5. **以鼠标为锚的缩放**：记下锚点对应的文档点，缩放后令其仍落在同一屏幕点
     （`scroll = doc_pt · z_new − anchor`），再钳制；缩放即切到固定模式。
  6. 派生量（内容尺寸、行顶前缀和）做**可失效缓存**；滚动**不**使缓存失效
     （滚动只影响原点，不影响布局），保证每帧滚动仍是 O(1) 查询。
  7. 本期**所有页面按统一尺寸布局**（取首页尺寸）。异构尺寸页的逐页布局留待后续：
     接口 `set_page_sizes` 已就位，布局函数无需改动。
- **与架构文档的偏差**：新增 `scroll_x`——放大到超过视口宽度后横向平移是必需的；
  已在 [02-架构设计](02-架构设计.md) §2.1 同步。
- **后果**：布局是**纯函数**，可脱离 UI 单测（`tests/canvas_test.cpp`，61 例）。

## ADR-019 纹理生命周期：渲染线程建纹理 + 帧首退役队列（2026-10-05，Phase 3）

- **背景**：架构文档 §2.3/§3.3 要求画布**不持有裸纹理指针**，且不能删除
  "正在被本帧 draw list 引用"的纹理。
- **决策**：
  1. 渲染线程用 `ID3D11Device` 直接建纹理（`CreateTexture2D` + 初始数据，
     `D3D11_USAGE_IMMUTABLE`；device 方法 free-threaded，可跨线程调用），
     上传完成即释放 `PageBitmap`。
  2. 被替换/逐出的纹理进**退役队列**；UI 线程在**帧首** `drain_retired()` 统一 `Release`。
  3. 正确性依据：帧 N 引用的纹理若在帧 N 期间被退役，只会在帧 N+1 帧首（即帧 N
     `Present` 之后）释放；D3D11 的 `Release` 在 GPU 仍在用时由运行时延迟回收，
     故不存在悬空引用。**不引入** D3D11 延迟上下文，保持简单。
  4. 画布只读快照 `PageSlot{status, texture, …}`；`texture` 以**不透明 `void*`** 暴露
     （UI 侧转 `ImTextureID`），所有权始终在渲染层。
- **后果**：Phase 4 的"纹理延迟释放队列 + 错误占位 + 重试"在本接口上完整化。

## ADR-020 渲染调度层取代 DocSession；Phase 3 用"保留窗口"缓存（2026-10-05，Phase 3）

- **决策**：
  1. 新增 `lilithreader.render`：单工作线程独占 `Document`（延续 ADR-006/ADR-012），
     UI 线程零 `fz_*`、零阻塞。**Phase 2 的 `DocSession` 临时线程随之删除**。
  2. 页状态机 `Unloaded → Loading → Loaded / Failed`；渲染请求**去重**
     （同页同倍率不重复渲染）。
  3. 缓存：Phase 3 用**保留窗口**（可见 ± 预加载，外扩 `kRetainMargin = 4` 页）
     逐出窗口外的已加载页；Phase 4 改为**按字节预算的 LRU**，本层接口不变。
     **勘误（2026-10-05，Phase 4）**：接口确有新增 —— `set_cache_budget` / `cache_stats` /
     `retry_page`（失败重试需要）。"不变"指的是 `PageSlot` / `RenderWant` / `DocState` 等
     既有契约不变，逐出策略的替换对上层透明；详见 [ADR-030](#adr-030-页缓存改为字节预算-lru策略抽成零依赖纯模块2026-10-05phase-4)。
  4. `set_wanted` 与上次请求相同则不去重投递，避免每帧空转唤醒渲染线程。
  5. 接口不引入 `d3d11.h`：设备以 `void*` 传入（模块内不透明），保持后端解耦
     （与 document 层隐藏 `fz_*` 同一思路）。
- **后果**：Phase 4 的失败重试、方向感知预加载、字节预算在本层落地；
  `Renderer` 必须在 D3D11 设备之前销毁（main 中已保证）。

## ADR-022 画布按**逐页真实尺寸**布局（2026-10-05，第三轮调试）

- **背景**：实测发现"**部分 PDF 渲染有形变**"。画布用**首页尺寸**对全部页做
  统一布局（`set_uniform`），而渲染层用 `fz_bound_page(page)` 各自的 bounds 出图。
  两者纵横比一致时无事；**PDF 允许各页 MediaBox 不同**（封面页、横向插页、扫描裁切
  不一），此时纹理被拉伸进"首页纵横比"的矩形 → 形变。
  （测试样本生成器曾因 `Kids` 偏移生成非法 PDF、掩盖了该问题，过程见归档 §8.1。）
- **决策**：
  1. `Document::info()` 额外探测**逐页**尺寸：每页一次 `fz_load_page` + `fz_bound_page`
     （不跑内容流、不解码图像），结果放进 `DocumentInfo::page_sizes`（点，长度 = 页数）。
  2. 探测放在 `fz_try` **之外**（要构造 `std::vector`，longjmp 不会析构它）；
     **每页一个独立 `fz_try`**（`bound_page_pt`），单页损坏只让该页回退为 `{0,0}`，
     绝不把整篇 `info()` 拖成错误 —— 与渲染路径的容错粒度一致。
  3. 上层用 `canvas.set_page_sizes()` 逐页布局：**列宽取最宽页、行高取行内最高页、
     每页按自身纵横比绘制**。尺寸为 0 的页回退到首页尺寸（画布已有该回退）。
  4. 页 0 复用 `info()` 已取到的 bounds，省一次 `load_page`。
  5. **页数上限**：页数 > `kMaxSizeProbePages`(10000) 时**整表留空**（上层回退统一尺寸布局）。
     理由是探测为 O(页数)，而损坏/构造的文档可能上报天文数字的页数，不设上限会在"打开"
     阶段长时间卡住。实测成本约 **20µs/页**（1000 页 ≈ 18ms，PyMuPDF 同源函数实测），
     真实书籍远低于阈值，故该上限不构成实际影响。
- **理由**：这是唯一能同时消除形变**并**让异构文档排版正确（行高、页间距）的做法；
  `set_page_sizes` 接口本就在 Phase 3 备好，布局函数无需改动。
- **代价**：打开时多 N 次 `fz_bound_page`（后台线程，不阻塞 UI；1000 页约 18ms 量级）。
- **后果**：`doc_test` 新增"逐页尺寸"断言表（均匀页 + 异构页各 1 例），
  把"逐页尺寸"本身钉成规格；形变在自动化层面有了防线。

## ADR-023 翻页改用**显式阅读游标**（2026-10-05，第三轮调试）

- **背景**：实测发现"**左右翻页连续按到某一页会卡住**"。根因：翻行以 `visible_first()`
  为游标，而 `visible_first()` 由滚动位置反推。当**视口比"一行"还高**时（横向页 /
  缩小 / 多列），末尾若干行的 `row_top` 会超过 `max_scroll_y`，**无法**被对齐到视口顶部；
  滚到底后 `visible_first()` 仍停在倒数第二行 → 连续按右键不再有进展。
- **决策**：
  1. 画布引入唯一的有状态成员 `nav_row_`（**阅读游标**）：`current_row()`/`current_page()`
     直接读它；`scroll_rows(dir)` 在游标上推进一行，再 `scroll_to_page(目标行)`。
     **游标推进与滚动钳制解耦**：即使 `scroll_y` 被钳到 `max_scroll_y`，游标仍前进一步，
     因此末尾几行（此时必然已整行可见，不漏内容）能逐页走完并在末行正确终止。
  2. 游标**不参与任何布局计算**，只在"到底"时有一个语义特例：`row_from_scroll()` 在
     `scroll_y ≥ max_scroll_y` 时返回**末行** —— 这样页码显示的是末页而非倒数第二页。
  3. 回同步点（手动滚动 / 缩放 / fit）统一走 `sync_nav_row()`；显式跳页
     （`scroll_to_page`）直接把游标设为目标行。
- **与架构文档的偏差**：ADR-018 声称画布"无隐藏状态"。现修正为：**布局**无隐藏状态
  （仍是纯函数 + 可失效缓存），**阅读游标**是唯一的有状态量，且只服务翻页与页码指示。
  已在 [02-架构设计](02-架构设计.md) §2.1 同步。
- **后果**：`canvas_test` 新增 3 组用例（矮页视口、多列按行推进、游标与手动滚动同步），
  含"恰好 N 次下翻走到末页、再多按无操作"这类**可程序判定**的回归断言。

## ADR-024 重渲染时**保留旧纹理**（2026-10-05，第三轮调试）

- **背景**：实测发现"**缩放时有时会闪烁**"。根因在 `render_one`：进入 `Loading` 时用
  `PageSlot{}` 覆盖整个槽位，**旧纹理立刻从快照消失** → UI 先退回"载入中…"占位框，
  等新纹理就绪再换入，肉眼就是闪一下。同一个覆盖动作还导致旧 SRV 指针被直接丢弃、
  未进退役队列 —— **每重渲染一次泄漏一个纹理**（缩放越频繁，显存涨得越快）。
- **决策**：
  1. `mark_loading(page)` **只改状态，绝不动 `texture`/`scale`**。UI 在重渲染期间继续
     显示旧纹理（双线性放大，略糊但不闪），新纹理就绪时在**同一把锁内原子替换**。
     这正是架构文档 §2.4"防抖期间用现有纹理显示（不闪白、不错位）"的原意，此前未落地。
  2. 替换路径统一 `retire_locked(旧纹理)` 入退役队列（由 UI 帧首 `drain_retired()` 释放）。
  3. `mark_failed(page, err)` **保留已有纹理**：宁可继续显示旧图，也不要闪回"渲染失败"
     占位框；从未成功渲染过的页 `texture` 为空，UI 自然显示失败占位。
- **后果**：缩放不再闪烁；纹理泄漏消除（配合 ADR-019 的退役队列）。
  Phase 4 的失败重试/退避在此语义上继续演进。

## ADR-025 界面按 DPI 缩放 + 预留字号设置（2026-10-05，第三轮调试）

- **背景**：实测反馈"**字有点小，怀疑没考虑屏幕缩放**"。核查：字体固定 18px、
  ImGui 样式与自绘像素常量都不随 DPI 变化；而进程是 Per-Monitor V2 DPI aware，
  ImGui 的 `DisplaySize` 是**物理像素**，故在 125%/150% 显示器上文字相对变小。
- **决策**：
  1. `style.FontScaleDpi = 窗口所在显示器 DPI 缩放`（`ImGui_ImplWin32_GetDpiScaleForHwnd`），
     `WM_DPICHANGED` 时刷新并重建样式（消息在帧间到达，改样式安全）。
     1.92 起的动态字体系统会按新尺寸重新栅格化，不必手工重载字体。
  2. `style.ScaleAllSizes(dpi × user)` 缩放内边距/间距/滚动条；每次都从**留底的基准样式**
     重算，避免多次缩放累积。
  3. 本项目自绘的像素常量（状态栏高、画布留白/间距、滚动步长、居中文本偏移、最小窗口
     尺寸）统一过 `px()`；`ScaleAllSizes` 管不到它们。
  4. 引入 `g_user_scale`（**字号/界面主缩放**，现固定 1.0）→ `style.FontScaleMain`：
     这是将来"全局设置"的接入点，与 DPI 自动缩放正交。
  5. 基准字号 18 → **20**（直接回应"字有点小"）；状态栏 30 → 34，画布留白 16/12 → 18/14。
- **后果**：100%/125%/150%/200% 下视觉大小一致；F3 调试浮层新增 `dpi/ui/font` 显示。
  将来加"全局设置"只需驱动 `g_user_scale` 并重算一次样式。

## ADR-026 阅读态快捷键**不再依赖 ImGui 窗口焦点**（2026-10-05，第四轮调试）

> **重要澄清（同日修订）**：本条记录的是一处**旁路隐患**，**不是**"按 1/2/3/4 不切列"的根因
> —— 根因见 **ADR-028**（输入法吞键）。第四轮实测中 `focus 1`（画布有焦点）时数字键仍无效，
> 已证伪本条的因果假设。之所以仍保留这条决策，是因为它本身确实是一处会让快捷键**静默失效**
> 的缺陷，值得修掉并留档。

- **缺陷**：`handle_canvas_input` 开头有 `if (!focused) return;`，其中
  `focused = ImGui::IsWindowFocused(RootAndChildWindows)`。
- **它为什么会是 false**：窗口结构是「无边框 shell 根窗口 + `##canvas` 子窗口」，两者都带
  `ImGuiWindowFlags_NoNav`，而 **`NoNav` = `NoNavInputs | `NoNavFocus`**；`NoNavFocus`
  使 ImGui 在窗口出现时**不**把它设为 `g.NavWindow`（`Begin()` 里的 `want_focus` 被否），
  于是**启动后、首次点进画布之前 `IsWindowFocused()` 恒为 false** —— 这段时间内所有
  画布快捷键（1~4 切列、F、G、F11、方向键…）全是死的。调试浮层/弹窗取得焦点时同样会让
  快捷键莫名失效。
- **决策**：阅读态的键盘快捷键改为**应用级**处理，只以「阅读态（调用方保证）+ 无弹窗
  （`g_open_jump`）+ 无文本输入（`io.WantTextInput`）」为门，**不再看 ImGui 窗口焦点**。
  鼠标（滚轮/拖拽）仍要求悬停在画布上。
- **理由**：整个窗口只有一个阅读视图，快捷键本就是应用级语义；把它绑在 ImGui 的窗口焦点上
  既脆弱又不可见（用户看到的只是"按键没反应"）。`io.WantTextInput` 已足以在文本输入时让路。
- **代价**：将来若加入需要独占方向键的 UI 控件（列表 / 滑块），需在此处补
  `io.WantCaptureKeyboard` 或按控件状态放行 —— 已在代码注释中标注。F3 浮层新增
  `canvas hover / focus / text-input` 三项，便于下次"某个键没反应"时一眼定位。

## ADR-027 快捷键语义：不区分主键盘与小键盘（2026-10-05，第四轮调试）

- **背景**：用户明确要求"小键盘的数字也要能切列"，暴露出一个更普遍的问题：
  用 `ImGuiKey_N` 只能匹配主键盘，用 `ImGuiKey_KeypadN` 只能匹配小键盘。
- **决策**：**凡有"数字/算术"含义的快捷键，一律同时接受两套键**：
  - 列数：`ImGuiKey_1..4` 与 `ImGuiKey_Keypad1..4`（见 `pressed_column_key()`）
  - 缩放：`ImGuiKey_Equal`/`ImGuiKey_Minus` 与 `ImGuiKey_KeypadAdd`/`ImGuiKey_KeypadSubtract`
- **理由**：小键盘数字在 ImGui 里与主键盘数字**是不同的键**，不是同一键的不同扫描码；
  只判一套就会出现"主键盘行、小键盘不行"（或反之）这种看起来像玄学的缺陷。
- **后果**：新增带数字语义的快捷键时，必须两套都判 —— 已写入 `docs/02-架构设计.md` 的按键表。
- **实测澄清**：在 ADR-028 修复前，小键盘数字**同样被输入法吞掉**，所以这条改动当时看不出效果；
  脱离输入法之后它才真正生效。

## ADR-028 阅读窗口**脱离输入法**：VK_PROCESSKEY 吞掉字母/数字键（2026-10-05，第四轮调试）

- **背景**：用户反馈"按 1/2/3/4 不切换列数（主键盘与小键盘都不行），**但其他快捷键貌似能用**"。
  后半句很关键 —— 它否定了 ADR-026 的焦点假设：若焦点是原因，方向键会一起失效。
- **根因**：**Windows 输入法接管了字母/数字键**。输入法启用时，系统会把这类键的
  `WM_KEYDOWN` 的 `wParam` 换成占位码 **`VK_PROCESSKEY (0xE5)`**（真实键码只交给输入法），
  同时用 `WM_CHAR` 把字符交给应用。而 ImGui 的 win32 后端
  `ImGui_ImplWin32_KeyEventToImGuiKey()` 的 switch **没有 0xE5 这个 case**（已全文件检索确认），
  于是 `key == ImGuiKey_None` → `AddKeyEvent` 被跳过 → **`ImGuiKey_1..4` 根本不置位**。
  字符则经 `io.AddInputCharacter` 正常入队 —— 表现为"**字符到了、按键没到**"。
- **影响面**：不止数字键 —— **所有字母键（`G` 跳页、`F` 回 fit-width）以及数字键**都被吞；
  只有 F 系列、Esc、方向键、PgUp/PgDn 等"输入法不接管"的键能穿透。
- **决策**：窗口创建后立即 `ImmAssociateContext(hwnd, nullptr)` —— **让阅读窗口脱离输入法**，
  键盘回归原生语义。
- **理由**：
  1. 本阶段**没有任何需要输入法的文本输入**（唯一的文本框是纯数字页码），输入法关联在这里
     只有害处没有用处。
  2. 这是唯一能让**所有**键（含将来的快捷键）可靠工作的做法，且不依赖"输入法是否把字符透传"；
     改从 `io.InputQueueCharacters` 判快捷键的字符兜底方案，换一个输入法就不保证成立。
  3. 改动最小、可逆：一行调用 + 链接系统库 `imm32.lib`。
- **代价与后续（重要）**：整窗脱离输入法意味着**将来加入中文输入（搜索框/批注）时必须重新关联**。
  届时做法是"仅在文本输入激活时关联"（`io.WantTextInput` 变化时在
  `ImmAssociateContext(hwnd, saved)` / `nullptr` 之间切换），或按控件粒度处理。
  **这条约束写在这里，避免将来有人加了中文输入框却忘了这回事。**
  另：切换输入语言（`WM_INPUTLANGCHANGE`）会让系统重新关联输入法，需再脱离一次（代码已处理）。
- **验证**：修复后 F3 读数从 `WM_KEYDOWN: E5` 变为真实键码（定位过程与实测读数见归档 §9）。
- **教训**：症状"某些键不响应"时，**先在窗口消息层取原始数据**，不要在应用层推理。
  本轮第一次修复（ADR-026）方向错了，代价是一轮返工。

## ADR-029 页/列间距改为**列宽比例**（随缩放变化）（2026-10-05，第四轮调试续）

- **背景**：ADR-028 修复并实测通过后，用户反馈"**页面的间隔貌似是固定的**，理想情况最好
  随着缩放改变，不然页面缩小的时候感觉上的间距会显得太大"。
- **根因**：`gap_px` 原本是**屏幕像素常量**，`ensure_layout` 里除以 zoom 换算进文档坐标 ——
  于是屏幕间距恒为 `gap_px`，与缩放无关。缩小时页面变小而间距不变，视觉比例失衡。
- **决策**：把间距从"屏幕像素常量"改为"**列宽（最宽页）的比例**"：
  `gap_pt = gap_ratio × max_page_w_pt`，屏幕间距 = `gap_pt × zoom`，**严格正比于 zoom**。
  - `CanvasState::gap_px` → `gap_ratio`（默认 0.013）；`set_margin_gap(margin_px, gap_ratio)`。
  - `fit_width` 方程把间距项放进**分母**：
    `zoom = (viewport_w − 2·margin_px) / (cols·max_page_w_pt + (cols−1)·gap_pt)` ——
    "内容宽度恰等于视口宽"的不变量**仍然严格成立**：把
    `content_w_px = inner_w_pt·zoom + 2·margin_px` 代回即得 `viewport_w`。
  - 留白 `margin_px` **保持屏幕像素**：它是"窗口边缘的呼吸空间"，属界面 chrome，不该随缩放。
- **为什么用比例而不是固定 pt**：固定 pt 无法同时保住不同页幅文档的观感 —— 例如取 16pt 时，
  1191pt 宽的扫描件在 fit-width 下间距恰好（约 21px），而 A4 会变成两倍（约 42px）。
  比例则让任何页幅的文档视觉比例一致；且在 fit-width 单列下屏幕间距 = 比例 × 视口宽，
  与本轮修改前的观感一致（约 1.3% 视口宽），**默认视图无可见回归**。
- **代价**：低倍率下间距会很小（zoom 0.2 时约 1.6px）。**刻意不加屏幕下限**：间距出现在
  fit-width 方程的分母里，加了下限后方程不再自洽（会破坏"内容宽恰等于视口宽"的不变量）。
  低倍率下页面本就很小，细缝是正常观感；将来若确需下限，应改为"限制缩放范围"或把下限并入方程求解。
- **验证（自动化，无需人工）**：`canvas_test.cpp` 新增 `test_gap_scales_with_zoom`（5 例）：
  间距 = 比例×页宽×zoom、zoom 翻倍则间距翻倍、fit-width 视口减半则间距约减半、
  含间距后 fit-width 仍严格铺满视口宽。同时把 7 处按旧语义写死的期望值改为**按定义独立重算**
  （测试装置里加了 `gap_at(zoom)` / `fit_zoom(cols)` 两个独立推导的辅助函数）。

## ADR-030 页缓存改为**字节预算 LRU**，策略抽成零依赖纯模块（2026-10-05，Phase 4）

- **背景**：Phase 3 的缓存是**保留窗口**（可见 ± 预加载外扩固定页数）逐出窗口外的页，
  预算以**页数**计。但单页纹理大小随渲染倍率变化极大：A4 在 zoom 1.0 约 2MB、zoom 4.0
  约 32MB，A0 海报可达数百 MB。按页数计预算会在高倍率下 OOM、低倍率下浪费显存；
  且"保留窗口"与滚动速度无关，快速滚动时窗口频繁移动、反复重渲。
- **决策**：
  1. 缓存改为按**字节预算**的 LRU：默认 **512MiB**，可设范围 **128MiB~2GiB**。
     逐出时先按 LRU（最久未用先出）逐出**非本帧需要**的页，直到驻留总量降到预算内。
  2. **本帧需要的页（可见 + 预加载）pinned，永不逐出**。因此当可见页自身的字节数就
     超过预算时，总量会短暂高于预算 —— 这是**有意**的：宁可超预算，也不能把正在显示的页
     抽走（抽走会闪回占位框）。预算的真正作用是给"窗口外的历史页"设上限。
  3. 逐出选择抽成**零依赖纯模块** `lilithreader.page_cache`（`select_evictions`）：
     输入是 `CachePageView[]`（字节数/LRU 序号/pinned）+ used + budget，输出逐出下标表。
     这样"选谁逐出"可脱离 D3D11/线程单测（`tests/page_cache_test.cpp`），
     与 canvas 把布局纯函数化同一思路（ADR-018）。
  4. 预算可由 exe 同目录 ini 的 `[cache] BudgetMB` 配置（缺省 512），
     `Renderer::set_cache_budget` 统一钳制到合法区间；调小会立即触发一次逐出。
- **理由**：字节预算是唯一能在"高倍率不 OOM"与"低倍率不浪费"之间自洽的口径；
  LRU 比"保留窗口"更贴合真实阅读（跳读、回翻都不再反复重渲）。
- **代价**：需在渲染线程维护 `used_bytes` 与 LRU 时钟（O(1) 记账 + 逐出时 O(N) 扫描，
  N = 页数，可接受）；`select_evictions` 每次逐出扫描一次视图数组。
- **后果**：`CacheStats`（预算/驻留字节/驻留页数/累计逐出）经 F3 浮层可见；
  逐出与重试的规则进入自动化断言，回归有防线。

## ADR-031 渲染失败状态机：自动重试 ≤1 + 点击重试（2026-10-05，Phase 4）

- **背景**：Phase 3 的 `mark_failed` 只把页标为 `Failed`，但 `handle_wants` 的跳过条件
  只认 `Loading`/`Loaded` —— 于是**每次 wants 变化都会重渲失败的页**。快速滚动时
  wants 每帧变，等于对确定性失败的页（损坏、超大页分配失败）无限重试，白耗渲染线程。
- **决策**：
  1. **自动重试上限 1 次**（`kMaxAutoRetries`）：初次渲染失败后立即自动再试一次
     （可救"瞬时"失败，如一时分配不到显存）；仍失败则**定格为 `Failed`**，不再自动重试。
     **"定格"绑定失败时的倍率**：同倍率的重复请求被抑制，倍率一变即视为**新请求**、
     重置额度。否则"曾成功渲染过、重渲失败仍保留旧纹理"的页会永久卡在旧倍率上
     （旧纹理还在，点击重试又无从触发）。
  2. `Failed` 页显示**错误占位**（"渲染失败 · 点击重试"）；用户点击占位 →
     `Renderer::retry_page(page)`：重置自动重试计数并重新排队。
  3. 判定规则抽成纯函数 `should_render_failed(manual, auto_retries_used)`（同 ADR-030 模块），
     手动重试恒真、自动重试受上限约束，进入自动化断言。
  4. 重试/加载期间**保留旧纹理**（沿用 ADR-024）：曾成功渲染过的页即使重渲失败也继续
     显示旧图，只有"从未成功渲染过"的页才显示失败占位（此时才有得点）。
- **理由**：区分"瞬时失败可自愈"与"确定性失败需人判断"，既避免空转，又给了用户出口；
  上限为 1 是因为更激进的重试对确定性失败无益，反而拖慢滚动。
- **代价**：`Entry` 增加 `auto_retries` / `manual_retry` 两个字段；`retry_page` 需重新
  武装一次调度（否则 `set_wanted` 的去重会拦住"同参数"的再次投递）。
- **后果**：失败页不再随滚动无限重渲；`Failed` 成为**可终止**状态，由用户或文档切换解除。

## ADR-032 预加载改为**方向感知**（2026-10-05，Phase 4）

- **背景**：Phase 3 的 `emit_wants` 无条件预加载可见行**上下各一行**。滚动有方向，
  反向那一行在下一帧多半就被逐出，等于白渲染。
- **决策**：预加载仍为"可见行 ±1 行"，但**只在与滚动方向一致的一侧**多取一行 ——
  向下滚只预取下方、向上滚只预取上方；**方向未定**（刚打开 / 跳页后）时两侧都预取，
  避免首个方向反转时出现空档。方向由内容坐标 `scroll_y` 的变化判定（阈值 0.5px 抑制抖动）。
- **理由**：与用户直觉一致（往下翻就该先备好下面），且直接减少渲染线程与显存的无效占用。
- **代价**：新增 `g_scroll_dir` / `g_prev_scroll_y` 两个 UI 侧状态（打开文档与跳页后复位）。
- **后果**：滚动时 wants 的页数近似减半；配合字节预算 LRU，快速滚动下缓存更稳。

## ADR-033 纹理退役改为**两段式队列**（2026-10-05，Phase 4）

- **背景**：ADR-019 定下"渲染线程只入队、UI 帧首 `drain_retired()` 释放"。原实现是
  单队列：退役即入 `retired`，下一次帧首整体释放。正确性依赖"drain 恰好在帧首"这一约定 ——
  一旦有人把 drain 挪到帧末（或插入别处），就可能释放"本帧 draw list 仍引用"的纹理。
- **决策**：改为**两段式**：渲染线程把退役纹理放入 `retired_pending`（本帧）；
  `drain_retired()` 先释放 `retired_ready`（上一帧的 pending），再把 pending 移入 ready。
  于是任何纹理都**至少活过一个完整帧**才被 `Release`。
- **理由**：把"帧内引用安全"从**约定**升级为**结构不变量** —— 不依赖调用位置，
  将来挪动 drain 也不会引入悬空句柄。
- **代价**：显存回收延迟约一帧（对阅读器无感）。
- **后果**：配合 D3D11 `Release` 自身对在途 GPU 引用的延迟回收，悬空纹理从机制上被排除。

## ADR-034 阅读状态持久化：reader_state.bin 的键、格式与原子写入（2026-10-05，Phase 5）

- **背景**：Phase 5 要"记住每本书读到哪、有哪些书签、用什么视图参数"，需要一个持久化载体。
  `LilithReader.ini` 是 `GetPrivateProfileStringW` 的键值文本，不适合存"每文档一条、含变长书签表"的结构。
- **决策**：新增**零依赖模块** `lilithreader.reader_state`，独立二进制文件
  `reader_state.bin`（exe 同目录）：
  1. **键 = 路径 + 文件大小 + 修改时间 的 FNV-1a 64 哈希**（`document_key`）。这样文件被替换/改名后
     不会串到别的记录上；哈希冲突只会让两个文档共享一条记录（代价可接受，不会损坏用户文件）。
     取不到属性（文件不存在）返回 0，视为无效键、不参与存取。
  2. **格式**：magic `LRS1` + u32 版本 + u32 条数 + 逐条记录（全小端）。含阅读位置
     （页/缩放/列/旋转/对开/fit/配色）与书签表。上限（条数/书签数/标签长度）写死在接口里。
  3. **解析失败一律安全拒绝**：magic/版本不符、截断、超限 → 返回空状态且**不改动输出**。
     阅读状态是"锦上添花"，绝不能因它损坏而崩溃或影响打开文档这条主路径。
  4. **原子写入**：写同目录临时文件 → `MoveFileExW(REPLACE_EXISTING)`。与架构文档 §5 的承诺一致。
  5. **纯序列化与磁盘 I/O 分离**：`encode_state`/`decode_state` 不碰 Win32，可脱离磁盘单测
     （`tests/reader_state_test.cpp`，43 例）——与 canvas 布局纯函数化、page_cache 纯策略同一思路。
- **理由**：二进制 + 版本号是"变长结构 + 向前兼容"的最省心做法；哈希键省掉一张需要维护的
  "路径→记录"映射；纯序列化单测把"坏输入必须拒绝"钉成规格。
- **代价**：文档改名/移动后阅读位置丢失（键含路径）——可接受，且不会误配到别的文档。
- **后果**：`reader_state.bin` 与 `LilithReader.ini` 并列，都在 exe 同目录。

## ADR-035 目录（outline）展平为前序序列（POD 缓冲 + `fz_page_number_from_location`）（2026-10-05，Phase 5）

- **背景**：MuPDF 的 `fz_outline` 是 `next`（同级）/`down`（子级）构成的树；UI 侧需要能直接线性绘制。
  且 `fz_outline::page` 在 1.26 是 `fz_location{chapter,page}`（不是裸 int），epub 有章节维度。
- **决策**：
  1. `Document::outline()` 把树**展平为前序序列** `std::vector<OutlineItem>{title,page,depth}`：
     depth 表层级，顺序即阅读顺序。UI 只需一次线性遍历（缩进按 depth），接口不引入递归容器。
  2. 遍历用 `walk_outline` 写入**预先分配的 POD 缓冲**（`new (nothrow) OutlinePOD[]`，
     raw 指针跨 `fz_try` 安全）；转 `std::vector<OutlineItem>` 一律在 `fz_try` **之外**完成。
     严格遵守 ADR-009：`fz_try` 内不构造任何需析构的 C++ 对象，连"跨块存活的 C++ 对象"也不引入。
  3. 页号解析：优先用 MuPDF 已解析的 `fz_location`（`fz_page_number_from_location`）；
     无目标时退回按 `uri` 解析（`fz_resolve_link`）。两者都解析不出则 page = -1。
  4. 上限：节点数 2048、深度 32（防病态文档深树递归爆栈），超出截断。
  5. 加载时机：打开/解锁成功后由**工作线程**一次性加载，存入 `Renderer` 的 `outline_` 快照；
     UI 进入阅读态时取一次（**不得每帧调用**，会拷贝整张表）。
- **理由**：展平让 UI 侧零递归、零树遍历；POD 缓冲让 ADR-009 纪律在"要建容器"的场合也成立。
- **代价**：目录表在 `Renderer` 里常驻一份（通常几百项，可忽略）；节点数超上限会截断（真实书籍远未及）。
- **后果**：`doc_test` 用带两级目录的合成 PDF（`outline.pdf`）把"顺序/层级/页号"钉成规格。

## ADR-036 旋转与配色在渲染层完成，变化即整篇重渲（2026-10-05，Phase 5）

- **背景**：需要页面旋转（0/90/180/270）与配色（正常/反色/护眼）。纹理是
  `IMMUTABLE` 且零拷贝上传，"像素进 GPU 后"无法再改属性。
- **决策**：
  1. **旋转在光栅化阶段完成**：`render_page` 的 ctm 加入旋转
     （`fz_pre_rotate(fz_scale(s,s), deg)`；等比缩放与旋转可交换，顺序无关）。
     `clamp_scale` 按**旋转后**包围盒钳制——否则 8000×100 的横幅旋转后会得到 8000 高。
  2. **配色在像素上传前完成**：反色逐像素 `RGB ← 255−RGB`、护眼用 LUT 把黑/白线性映射到
     暖色端点（`#2B2318`/`#F6EEDC`）。**不用** `fz_invert_pixmap`/`fz_tint_pixmap`：这两者面向
     RGB/Gray，对**带 alpha 的 4 分量 RGBA** 行为不在公开契约里；自写逐像素变换（只改 RGB、
     保留 alpha）行为完全可控且可单测（`doc_test` 断言背景白→黑、alpha 不变、护眼 R>B）。
  3. **旋转/配色是文档级视图状态**（`Renderer::set_view_transform`）：任一变化即
     **让全部页纹理与缩略图失效并整篇重渲**（变换已固化进像素）。失效走既有的两段式退役队列。
  4. 旋转折算成**页尺寸宽高互换**交给画布：画布本身不感知旋转，布局/翻页/缩放全部复用。
- **理由**：把变换放在唯一的像素入口（渲染线程）而非 UI 叠加 shader，最省心且与"UI 线程零阻塞"一致；
  自写配色变换消除对 MuPDF 未定义行为的依赖。
- **代价**：切换旋转/配色会触发一次整篇重渲（可见页优先，预加载随后）；频繁切换有短暂重渲。
- **后果**：`doc_test` 断言 0°/180° 尺寸不变、90° 宽高互换、反色/护眼的背景像素与 alpha。

## ADR-037 缩略图走**独立通道**，不占页缓存预算（2026-10-05，Phase 5）

- **背景**：侧栏缩略图需要低 DPI 页面图像。若复用页纹理槽位，缩略图与正文会互相覆盖倍率。
- **决策**：`Renderer` 增加一条**并行的缩略图通道**：
  1. `set_thumbs_wanted(pages, target_px)` 声明需要的页与目标最长边；工作线程按
     **旋转后**页尺寸算目标倍率（最长边 ≈ target_px）渲染，存入独立的 `thumbs[]` 缓存。
  2. 缩略图**独立字节记账**（`thumb_bytes`），不参与页缓存的 LRU/预算——缩略图很小，
     挤占正文预算不合理。
  3. 缩略图渲染**不自动重试**（侧栏是辅助视图，失败留空占位）；视图变换变化或重开文档会重置状态自然重试。
  4. 侧栏只请求**当前页 ±40 页**一段，随当前页滚动扩展，避免一次性渲染整本书。
- **理由**：与页缓存解耦后，缩略图的存在与否不影响正文的清晰度策略与逐出行为。
- **代价**：`Renderer` 多一份缓存与一条处理分支；缩略图请求按 (页列表, target_px) 去重。
- **后果**：F3 浮层/调试可扩展显示缩略图状态（当前仅接口就位）。

## ADR-038 双页对开（书籍模式）＝ 2 列 + 封面单独成页（薄扩展，复用网格）（2026-10-05，Phase 5）

- **背景**：Phase 3 已有 1~4 列**均匀网格**（`row=i/cols, col=i%cols`）。Phase 5 计划另列"双页对开（书籍模式）"。
  两者**不是同一件事**：真实书籍装订是封面单张、正文成对——网格会把封面与第 2 页凑成一对。
- **决策**：**不重写布局**，在网格上加一个薄层：
  1. `CanvasState::spread` 开关；开启时**等效 2 列**（columns 被忽略）。
  2. index→slot 映射改为：页 0 独占第 0 行；页 i≥1 → `row = 1+(i-1)/2, col = (i-1)%2`。
     第 0 行页数恒为 1，其余行最多 2。
  3. 映射集中在 `eff_cols/row_first_page/row_page_count/row_of` 四个函数里分支；
     缩放/滚动/钳制/游标/翻页全部复用网格逻辑。
  4. 单独成页的行（封面、末页）在**整行宽度内居中**，避免单独一页贴左。
  5. **`spread=false` 时映射与行为逐位不变**——由 `canvas_test` 的回归守卫钉死。
- **理由**：与既有网格共享 95% 逻辑，风险最小；差异只在"奇偶偏移 + 单独页居中"。
- **代价**：`page_rect`/行高计算改为按"该行页数"而非固定列数；切换对开时按当前页重新锚定
  （锚点页须仍在可见范围内）。
- **后果**：`canvas_test` 新增 27 例对开断言（映射/居中/翻页/回归守卫/切换锚定）。

## ADR-039 加密文档密码框 + 权限位读取（2026-10-05，Phase 5）

- **背景**：Phase 2 已实现加密识别（`DocError::NeedsPassword`）与 `Document::authenticate`，
  但缺 UI；且 PDF 标准加密可声明"禁复制/禁打印"，UI 层应尊重。
- **决策**：
  1. `UiDoc::Kind` 增加 `NeedsPassword`：打开返回该错误时弹**模态密码框**，
     提交 → `Renderer::authenticate(pwd)`（文档仍处于打开态）；失败重弹并提示"密码错误"；
     取消/Esc → 关闭文档回引导页。
  2. `DocumentInfo` 增加 `can_copy`/`can_print`（`fz_has_permission`）。无加密或无法判定时
     **一律 true**（保守放行，避免误禁）。当前尚无复制/打印功能，字段先就位供后续置灰。
  3. 密码输入为 UTF-8 明文缓冲（`char[256]`），提交后立即清零。
- **理由**：识别与 authenticate 早已就位，本阶段只补 UI 接线，改动面小。
- **代价**：`UiDoc::Kind` 增加一个枚举值，所有 switch 需覆盖（调试浮层名字表已补）。
- **后果**：`doc_test` 的加密三态断言（Phase 2 已建）覆盖解锁路径；密码框为交互项，入人工清单。

## ADR-040 输入法关联随"文本输入激活"切换（落实 ADR-028 的后续要求）（2026-10-05，Phase 5）

- **背景**：ADR-028 让阅读窗口**整窗脱离输入法**（否则输入法吞掉字母/数字键），并明确要求
  "将来加入中文输入时必须改回仅在文本输入激活时关联"。Phase 5 引入了密码框等文本输入。
- **决策**：启动时保存默认输入法上下文（`g_saved_ime = ImmAssociateContext(hwnd, nullptr)`），
  之后每帧按 `io.WantTextInput` 切换：文本输入激活 → 关联回来（可输入中文），否则 → 脱离
  （快捷键回归原生语义）。`WM_INPUTLANGCHANGE` 后按当前状态重新应用（系统会重新关联）。
- **理由**：同时满足两个互相冲突的需求——快捷键可靠 + 中文可输入；且这是 ADR-028 预留的既定路径。
- **代价**：每帧一次状态比较（无变化即不调用 Win32）；`io.WantTextInput` 用上一帧状态，切换有 1 帧延迟
  （对输入法关联无实际影响）。
- **后果**：ADR-028 的"后续约束"解除；将来加搜索/批注框无需再处理此事。
